# 代码阅读顺序与核心文件导航

> 本文解决“具体先开哪个文件、在文件里看什么、下一步跳到哪里”。它是阅读路线，不是源码清单；工程目录中存在的文件不一定都进入当前构建。

## 1. 总原则：从系统边界进入，从单条链路深入

顶层 [top_tf_hdmi_audio.v](../../src/top_tf_hdmi_audio.v) 集成了时钟、存储、音视频、交互、显示和外部接口。它包含许多模块和长段连接逻辑，适合作为索引，不适合逐行通读。

每次进入代码都按以下顺序：

1. 在 [VinylFPGA.al](../../prj/VinylFPGA.al) 确认工程纳入的源文件和顶层。
2. 在顶层搜索模块实例名，确认真实连接和参数。
3. 打开子模块先读 module 端口与参数，再读状态机、关键数据路径。
4. 追踪一个输入信号到消费端，再追踪完成/错误信号回到控制者。
5. 找针对这一行为的 testbench，确认它到底验证了什么。
6. 回顶层补上时钟、复位、跨域和外设上下文。

## 3. 顶层文件如何读

### 第一遍：只读结构

在顶层找这些区域：模块端口、include 列表、PLL/时钟输出、各域 reset、SD/SDRAM 接口、播放控制、媒体加载、音频预取、PCM 流播放器、背景/MV、显示处理、HDMI、扩展板和事件桥、时间基准。

如果本地编辑器支持符号搜索，按实例名称和信号名称搜索比记忆行号可靠。顶层在持续开发中会改行号，学习笔记应记录实例名/信号名/功能，行号只作为临时定位帮助。

### 第二遍：画实例树

选定一个顶层实例，记录：

- 实例名与 module 类型；
- 输入输出中最重要的 5–10 个信号；
- 时钟/复位；
- 上游是谁、下游是谁；
- 参数表示什么，以及单位是什么。

### 第三遍：追完成信号

完成信号经常比数据更能说明设计边界。例如：

- SD 扇区完成：卡接口层完成一段扇区事务；
- DMA 写完成：数据已进入 SDRAM；
- 帧可提交：目标 bank 的数据写入已确认；
- PCM 消费：播放器确实从采样缓存取出一个有效样本。

先弄清一个 done 的语义，再读调用者如何使用它。不能仅凭信号名推断。

## 4. 有代表性的阅读锚点

顶层是综合性较强的文件，建议用关键实例/信号名定位，而不是线性阅读：

- 时钟、reset、SD 卡与 SDRAM 实例；
- audio_prefetch_sdram 与 wav_stream_player；
- mv_frame_scheduler、mv_stream_player 和 s6_video_layer；
- ui_param_csr 与参数持久化；
- expansion_integration、ui_event_bridge；
- timebase_48k 和 HDMI 像素/音频接口。

具体连接请以当前 [顶层源码](../../src/top_tf_hdmi_audio.v) 为准。读任何子模块之前，先确认当前顶层是否实例化它，且对应配置是否启用。

## 5. 按功能选最小入口

### 我想理解旋钮选歌

消抖/编码器 → 扩展 IO Hub → UI Event Bus → Command Router → ui_event_bridge 的源域逐类 toggle → 目标模块同步/检沿 → 浏览状态机、封面导航或播放控制。ui_event_bridge 只在 50 MHz UI 域编码；真正的目标域同步/检沿由 browse_fsm、play_ctrl 等接收者完成。分别记录事件排队、编码器计数合并/差值重放和目的状态门控。

### 我想理解声音为什么连续

从消费者反向读：HDMI PCM 桥 → 音频源选择/音量 → 48 kHz 消费 tick → wav_stream_player BRAM → 音频预取与 SDRAM DMA → SD 扇区请求 → INDEX 中的媒体起始 LBA。这样先知道终点的时间要求，再理解前端如何供数。

### 我想理解 MV 怎么不撕裂

显示端反向读：帧 bank 选择 → frame_start → 完成 bank mailbox → SDRAM 写完成 → 每帧扇区计数/像素写入 → 调度器目标帧与请求 LBA。重点检查数据写完的确认和显示 bank 切换边界。

### 我想理解参数为何重启还在

参数输入 → 业务事件/CSR 后分两路：运行时分支经 CDC 原子快照送到 25 MHz 视频/音频域，ROT 另送 100 MHz 调度域；保存分支在同一 50 MHz UI 域进入 ui_param_persistence → W25Q64 SPI 事务 → 双槽/CRC/读回/提交。Flash 启动恢复数据再回写 CSR。保存分支不需要先经过运行时 CDC。播放位置不属于这五项。

### 我想理解歌词与素材如何进入产品

先读 [媒体打包工具](../../tools/vinyl_packer.py)、[歌词生成工具](../../tools/gen_lrc_assets.py) 和 [歌词准备流程](../../tools/prepare_s3_lyrics.py)，只读其输入、输出和格式约定。当前歌词正文、时间戳和字形来自预生成的 [song_text_rom](../../src/display/song_text_rom.v)、[song_font_rom](../../src/display/song_font_rom.v)，顶层连接 lrc_window_controller 等显示模块。INDEX 的歌词标志不等于运行时从 TF 卡解析任意 LRC 文本。素材更改是否需要重新生成 ROM/bitstream，要依据对应资产路径判断。

## 6. 源码阅读时容易走错的路

- 从顶层第一行读到最后一行，几小时后仍无法解释完整链路。
- 只看文件名推断功能，不确认端口、实例和数据单位。
- 只看写端，不看消费端和背压。
- 把 valid 当成对方已接收，忽略 ready 或完成反馈。
- 看到 CDC 双触发器，就误以为多位总线也安全；多位数据要看稳定窗口、握手或原子快照。
- 把 testbench 文件名当成当前接口证明；历史 bench 可能针对旧版本。
- 把 src 下的所有模块都当作当前 .al 工程的一部分。

读完一个模块后，先合上源码，尝试用五句话解释：输入是什么、输出是什么、在哪里运行、怎样握手、失败时怎么处理。解释不出来的地方就是下一次回到代码的入口。
