## 3. 媒体包与固件的对应规则

### 路径 A：更新媒体卡数据

当文字/字形、曲目 ID 关系和硬件格式保持不变时，可通过现有素材工具更新音频、封面、背景或 MV，并重新生成相关索引和资源元数据。仍要检查：

1. 最多四曲，song_id 与 ROM 曲目对应；
2. PCM 规格、有效样本长度及尾部；
3. 音频/MV 的物理连续区域与 INDEX 地址；
4. BMP 尺寸、格式、目录短名与资源长度；
5. 根目录首个扇区内的目录项；长文件名项也会占用32B槽位；
6. 索引、背景扩展、帧数量和资源范围；
7. 整卡镜像哈希与实际写入介质的对应结果。

这条路径不保证任意文件替换都可用。新增音乐若导致标题、艺人、歌词内容变化，就同时涉及路径 B。

### 路径 B：同时更新 ROM 与固件

修改标题、艺人、歌词、字形、开机图或硬件算法时，应按生成器更新资产，检查生成结果，再建立新的工程构建和固件记录。

特别注意：当前 prepare_s3_lyrics.py 不只是向输出目录写资源，它还会把生成的 song_text_rom.v、song_font_rom.v、song_text_geom.vh 复制到 --project 对应的源码目录，默认project为当前目录。以后执行它时应把该动作计入源码变更；本轮仅审阅脚本，没有执行这项生成操作。

典型路径：

~~~text
原始音视频/图片/字幕 + 校准JSON
  → PCM / BMP / RGB565 MV / 背景等数据
  → INDEX / FAT32镜像与资源清单

字幕/标题/艺人/字形
  → 歌词处理与ROM生成
  → song_text_rom / song_font_rom / 几何定义
  → 新固件与对应媒体包
~~~

生成 LRC/LYRICS.BIN、生成 ROM、改写完整镜像、写入实体 TF 卡是不同动作。2026-10-19 收尾记录明确该次流程没有据新歌词资源改写物理卡，不能用资源文件的生成结果证明实卡内容已更新。

### 当前工具的分工

S1/S2/S3 素材处理、INDEX、MV、背景及 ROM 工具入口见 [24 源码索引第6节](./24_源码依赖与关键接口索引.md)。未来可将它们封装为统一入口；现有代码已经包含多个工具，文档不应写成从零缺少所有打包能力。

## 4. 工程复现与新版本的边界

以后需要构建新版本时，先固定输入和输出目录，再执行项目既有流程：

1. 确认 .al、顶层、器件、源文件、include 与生成 ROM。
2. 核对 TD 版本、时钟/引脚约束、策略和 seed；不要仅凭旧工程名继承结果。
3. 检查与变更相关的模块和集成用例，保留原始失败和输出。
4. 完成综合、物理实现、时序和 bitgen，保存各阶段日志。
5. 为新 bit、报告、输入和媒体生成新清单。
6. 若引用实物效果，记录实际下载文件哈希、板卡、显示设备、卡片、接线和场景。

新流程结果写入独立目录，避免覆盖本报告所引用的 r2 固定验收材料。迁移到新机器时，需要重绑定快照工程中的绝对路径；保留原文件作为归档，再制作工作副本。

## 7. 故障定位顺序

| 现象 | 先核对 | 再看链路 |
|---|---|---|
| 无法发现曲目 | 卡布局、首扇区目录项、8.3短名、INDEX校验 | volume_scanner → file_streamer → song_index_db → readiness |
| 有封面但不能播放 | 音频元数据、有效长度、挂载/播放准备 | play_ctrl → session → prefetch → WAV启动门 |
| 音频断续或静音 | 实际PCM格式、underflow、储备、水位、介质延迟 | SD owner → DMA →样本缓存 → HDMI桥 |
| 首帧等待或旧MV帧 | 索引格式/帧数、会话失效、write_finish与bank | scheduler → reader → writer → frame_start提交 |
| 歌词与新歌曲不符 | 曲目ID、ROM版本与媒体配套 | 歌词生成 → ROM → 媒体时基；不先怀疑LRC运行解析 |
| 画面/文字错位 | RGB与DE/坐标延迟、层级覆盖、帧源选择 | 顶层像素链与帧读出 |
| 参数未恢复 | 保存使能、CSR状态、NVM忙/错误、CRC/槽记录 | 同域保存/恢复支路；不是配置Flash |
| 电机/灯带不工作 | 使能状态、接线、驱动和供电 | IO控制与外部驱动分开核对 |

“先核对”是定位路径，不是在没有证据时认定该处存在缺陷。保留日志和故障时刻，避免同时改多个模块丢失因果关系。

## 8. 十个答辩追问的简答

1. **为什么使用 PCM？** 固定样本格式便于在 FPGA 上做直接缓存和实时输出，代价是离线转换与较大媒体容量。
2. **为什么有这么多缓存？** SD 扇区、SDRAM 搬运和固定采样消费的粒度/延迟不同，各级缓存隔开这些节奏。
3. **共享存储最特殊的设计是什么？** RGB888用高24位，音频字节用低8位；掩码和事务尾部需受控。
4. **三缓冲解决什么？** 将显示、完成待显和写入角色分离，并以帧边界提交；它不等于四曲或四张封面。
5. **为什么不是 FFT？** 本工程选择了波形/电平可视化方向，不把它说成频谱算法。
6. **为什么没有缩放？** 当前固定素材和画布已经定义输入契约；缩放模块未进入当前链路，扩展需另做资源和验证预算。
7. **歌词从卡里读吗？** 当前运行歌词、标题和字形来自预生成 ROM，更新文字资料需要同步生成和构建。
8. **断电后能续播吗？** 当前保存五项参数，未将播放位置与会话状态纳入该保存协议。
9. **WNS为正证明什么？** 证明该次约束模型下的时序报告结果，不直接证明音质、功耗或现场长时表现。
10. **当前应交付哪个 bit？** 本报告引用固定 accepted_artifacts bit；Runs 副本哈希不同，若选用它需另外确认来源和证据。
