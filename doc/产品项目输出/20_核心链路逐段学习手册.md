# 核心链路逐段学习手册

> 本文按“一个事件/样本/像素怎样穿过系统”的方式解释主要路径。目标是让读者能拿源码逐段对照，并在每段都回答谁产生、谁消费、在哪个时钟域、何时算完成。

## 1. 全局链路图

~~~mermaid
flowchart LR
  INPUT[旋钮 / 按键 / 红外] --> EVENTS[同步消抖与事件路由]
  EVENTS --> CONTROL[浏览 / 播放 / Seek 控制]
  CONTROL --> META[SD 扇区读取与 FAT32 / INDEX]
  META --> AUDIO[PCM 扇区预取]
  META --> VIDEO[MV 元数据与连续帧请求]
  AUDIO --> SDRAM[SDRAM 缓存与仲裁]
  SDRAM --> PCM[PCM 样本 BRAM]
  PCM --> HDMI_A[音量 / 淡变 / 音频源选择]
  HDMI_A --> HDMI[HDMI 音视频输出]
  VIDEO --> FRAME[帧写入 / bank 管理 / 帧读出]
  FRAME --> LAYERS[封面 / 歌词 / 播放页 / 波形 / OSD]
  LAYERS --> HDMI
  EVENTS --> PARAM[参数 CSR / CDC / 用户 Flash]
~~~

这里的“共享”意味着功能竞争 SD 扇区服务、SDRAM 读写带宽或显示时间；具体仲裁发生在不同层。SD 扇区仲裁与 SDRAM 控制器仲裁不是同一个机制。

## 2. 音频：从一个 PCM 样本反向追踪

建议先从消费者往生产者读。消费者有严格的 48 kHz 节奏，更容易理解为什么前面需要缓存和预取。

### 第 1 段：采样消费节拍

顶层根据视频时钟域中的分数累加节拍生成音频采样时刻，并由播放状态进行暂停门控。实际样本被播放器成功消费后，timebase_48k 推进播放时间，歌词和进度可以跟随实际输出样本。

要看：

- 一个 tick 代表一次计划取样还是一次成功消费；
- 暂停时 tick 如何处理；
- 欠载时系统是否停止时钟，还是保持节奏并输出静音。

本工程选择保持输出时序并在欠载时输出静音；对学习者而言，关键是区分“播放时钟继续”和“有效样本存在”。

### 第 2 段：PCM 双时钟缓存

[wav_stream_player.v](../../src/audio/wav_stream_player.v) 的写侧接收字节流，将先到的低字节和随后到的高字节拼成 16-bit 有符号样本；读侧按样本节拍从片上环形缓存取数。写侧与读侧时钟不同，指针/状态需要安全跨域。

推荐观察的信号组：字节写入、低/高字节配对、写指针、读指针、Gray 指针同步、有效消费、欠载、输出样本。重点追踪哪一侧更新指针和满/空判断在哪里使用。

输入不是待解析的 WAV 容器。本链路消费已整理好的单声道、16-bit 有符号、小端、48 kHz PCM 字节流；WAV 文件名或模块名不代表它读取并解析了 WAV 文件头。

### 第 3 段：音频效果与 HDMI 音频选择

样本经过音量/淡变处理，之后在媒体音频与其他音源之间选择，再由 HDMI PCM 桥接到 HDMI 音频数据接口。读这段时要确认样本位宽、左右声道复制/映射、静音条件、valid 节奏以及下游接口的消费规则。

可对照：

- [音量与淡变](../../src/audio/pcm_volume_fade.v)
- [音频源选择](../../src/audio/audio_source_mux.v)
- [HDMI PCM 桥](../../src/audio/hdmi_pcm_source_bridge.v)

### 第 4 段：SDRAM 音频环形缓存

当 PCM BRAM 有可写空间并发起扇区请求时，音频预取模块从 SDRAM 缓存返回扇区字节流。SDRAM 级缓存是大块、长延迟隔离；PCM BRAM 是小块、采样级时钟隔离，两者职责不同。

可对照：

- [预取控制](../../src/audio/audio_prefetch_sdram.v)
- [预取数据阶段](../../src/audio/audio_prefetch_stage.v)
- [音频 DMA](../../src/audio/audio_sdram_dma.v)
- [SDRAM 仲裁](../../src/audio/audio_sdram_arbiter.v)

检查请求是否按块发起、DMA 是否保持 ownership 到响应彻底完成、返回数据是否会因为 seek/session 变化被误认为新歌数据。

还要区分“地址空间”和“字节通道”：当前 audio_sdram_dma 以 mem_wr_data={24'd0,stage_dout}、mem_wr_mask=4'b1110 仅更新 32-bit SDRAM 字的低 8 位；视频 RGB888 使用高 24 位。两类数据允许复用同一个字地址而占不同字节通道，不能把逻辑音频缓存画成必然与所有图像字地址完全分离的区域。字节掩码极性与控制器连接必须一起阅读。

### 第 5 段：SD 扇区供数

INDEX 元数据给出媒体区起始 LBA 和长度。音频预取逻辑从 SD 卡请求扇区，整扇区接收后再提交到后级缓存。这样可让卡侧的突发延迟与实时的样本消费节奏分离。

以 48,000 样本/秒、每样本 16 bit 单声道计算，原始 PCM 约为 96,000 字节/秒；512 字节扇区包含 256 个样本，约覆盖 5.33 ms 音频。这只是格式和速率的理论换算，不是 SD 卡实测吞吐结论。

### 第 6 段：播放、Seek 与会话边界

[play_ctrl.v](../../src/audio/play_ctrl.v)、[seek_controller.v](../../src/audio/seek_controller.v) 和 [stream_session.v](../../src/audio/stream_session.v) 管理播放生命周期。取消一个逻辑请求，不代表硬件控制器已经撤销在途 SD/SDRAM 事务。旧请求需要被排空或隔离，再复用暂存空间，避免旧歌数据污染新会话。

学习时给每个请求画状态：

~~~text
发起 → 等待 SD → 收齐扇区 → 请求 SDRAM → 等待返回 → 提交缓存 → 消费
                    ↘ 错误/超时/取消 → 清理与 drain → 新会话可启动
~~~

务必分清三个完成点：卡侧扇区读完、SDRAM 搬运写完、PCM 样本被实际消费。它们用于不同的控制决策。

## 3. 视频与存储：从显示 bank 反向追踪一帧

### 第 1 段：帧显示时刻

显示逻辑按 HDMI 光栅时序读取当前显示 bank。帧 bank 只能在安全边界切换，避免显示过程中切到正在写入的帧。观察 frame start、当前 bank、待显示 bank 和 bank 提交确认。

### 第 2 段：帧调度

当前 [s6_video_layer.v](../../src/video/s6_video_layer.v) 只接受格式号 1、10 fps 的 MV 元数据。[mv_frame_scheduler.v](../../src/video/mv_frame_scheduler.v) 按固定 100 ms 帧间隔跟随音频播放时间，并以 start_lba + frame_index × 300 计算连续区域中的帧起始 LBA。帧调度的目标是让视频跟随媒体时间，而非简单按照某个独立计数器永远播放。

### 第 3 段：连续扇区流

[mv_stream_player.v](../../src/video/mv_stream_player.v) 读取目标帧所需的数据，统计扇区/像素位置，将 RGB565 little-endian 像素转换并写向帧存储数据通道。有效数据形式为 320×240、RGB565，每帧 153,600 字节；一个 512 字节扇区可容纳 256 个像素，因此每帧是 300 个扇区。若帧率为 10 fps，理想连续读取需求约为 3,000 扇区/秒，即 1.536 MB/s；这是静态格式计算，不是当前硬件测量值。

### 第 4 段：写完成与帧提交

最后一个 SD 字节到达不代表帧已经写进 SDRAM。必须等写入流水和 SDRAM 事务返回完成，再把完整 bank 标记为可显示。待显示 bank 在安全的 frame_start 才切换。这是理解三缓冲用途的关键：显示、待提交、正在写入的资源生命周期要彼此隔离。

可对照 [媒体写入流水](../../src/video/media_write_pipeline.v)、[视频层](../../src/video/s6_video_layer.v) 和顶层帧读写/帧 bank 实例。不要根据模块名称推断它实现了不存在的几何效果；当前 s6_video_layer 主要承担调度和窗口/银行控制，像素内容由上游和显示流水组合。

### 第 5 段：一次 MV 帧请求的事务追踪表

| 步骤 | 当前代码锚点 | 发生了什么 / 尚未保证什么 |
|---|---|---|
| 目标帧选择 | mv_frame_scheduler 的 target_frame、next_frame、next_bank、can_issue | 依据媒体时间挑帧并选择不属于当前显示/待提交的 bank；尚未取得任何帧字节。 |
| 请求发布 | request_lba、request_bank、request_toggle | LBA/bank 保持稳定，通过 toggle 发命令；这不是扇区完成。 |
| 写资源握手 | mv_stream_player 的 ACK → CLEAR | 保持 write_req，等待 write_ack 拉高再拉低，准备帧写入通道；尚未取得完整帧。 |
| 读取 300 扇区 | REQ → READ、sector_count、byte_count | 每个扇区检查 512 字节及错误，RGB565LE 每两字节展开为 {RGB888,8'b0}；末扇区接收完仍有写流水待排空。 |
| 存储完成 | DRAIN、write_finish_toggle、finish_mark | 等 SDRAM 帧写完成 toggle 变化；成功路径至此才认为整帧落入存储。 |
| 返回结果 | COMPLETE、done_toggle、failed | 返回与本次 request_toggle 对应的完成；failed/取消结果不得当成完整帧。 |
| 待显示或跳过 | 调度器 completed、pending_valid、requested_frame | 同步完成结果；结合失效/错误/时间目标决定保留、丢弃或准备显示。 |
| 显示提交 | frame_start、display_bank、display_valid | 仅在安全帧边界更新显示 bank；下一帧读取使用已确认完成的数据。 |

练习时给三只 bank 分别写出“显示”“待提交”“写入/空闲”，再在请求失败、Seek、目标时间跳变时重画。上表说明成功帧路径；取消路径可能在未写完时报告 failed 并清理，不能把所有 done 都解释成可显示。

## 4. 文件系统与媒体寻址：两个路径不要混为一谈

### 浏览和资源加载路径

[fat32_volume_scanner.v](../../src/SD/fat32_volume_scanner.v) 读取卷信息与目录元数据；[fat32_file_streamer.v](../../src/SD/fat32_file_streamer.v) 沿簇链提供文件字节流；[fat32_media_loader.v](../../src/SD/fat32_media_loader.v) 和 [song_index_db.v](../../src/SD/song_index_db.v) 完成索引与媒体元数据加载。

该实现需要按它支持的卡布局使用。当前扫描器只读取根目录首簇的首个 512 字节扇区，不继续遍历簇内其余扇区或根目录簇链；所需短文件名目录项应位于这一扇区。源码头部“首簇”注释比实际范围宽，判断以 ST_ROOT_REQ → ST_ROOT_WAIT → ST_DIR_SCAN 的实际转移为准。它不是完整通用 FAT32 文件浏览器。

当前歌词正文、时间戳和字形经 PC 侧工具预生成到 song_text_rom/song_font_rom，再进入歌词显示流水；INDEX 中的歌词标志不表示运行时从 TF 卡解析任意 LRC 文本。

### 连续播放路径

INDEX 保存了连续媒体数据的定位信息，音频和 MV 运行时可以直接按 LBA 连续读取。文件系统路径的目标是找到并装载元数据，连续播放路径的目标是稳定供数。不能把“播放每一帧都遍历 FAT 簇链”当成实际实现。

## 5. 控制路径：旋钮动作如何成为选曲

典型链路：

~~~text
物理输入
  → 同步/消抖/编码器或 NEC 解码
  → expansion_io_hub
  → ui_event_bus（缓存和仲裁）
  → ui_command_router（策略检查并映射业务事件）
  → ui_event_bridge（50 MHz 源域逐类 toggle 编码，编码器差值重放）
  → 接收模块的目标域同步/检沿
  → browse_fsm / cover_navigation / play_ctrl / seek_controller
~~~

建议从 ui_event_bus 的编码器步进事件开始：找到事件码、参数和辅助字段，再跟踪命令路由怎样处理 DIP/红外/blank 策略，最后看顶层如何将事件送入播放域。对每类事件分别记录源域、目标域、是否排队、是否可能合并。

旧注释中的按键历史命名可能与产品说明中的键位文案不完全一致。以当前顶层连接、当前解码表和实物交互记录复核，不以注释单独定性。

## 6. 参数持久化链路

参数输入经事件/参数控制器写入 ui_param_csr，随后分成并行两路。运行时分支用 u_ui_params_cdc 将原子快照从 50 MHz UI 域送往 25 MHz 视频/音频域，ROT 还经 u_rotation_param_cdc 送往 100 MHz 调度域。保存分支保持在 50 MHz UI 域，由 ui_param_persistence 对 CSR 当前参数取快照，经 [W25Q64 参数存储](../../src/io/w25q64_param_store.v) 和 [SPI 事务](../../src/io/nvm_spi_transaction.v) 写入用户 Flash；启动恢复则由 restore_valid/restore_data 回写 CSR。运行时 CDC 与 Flash 保存之间不是串行上下游关系。

该工程保存的参数集合是音量、亮度、对比度、幻灯片间隔和 WS2812 亮度。双槽、版本/范围检查、CRC、提交和读回用于提高参数记录的可靠性。它是专用用户参数 Flash，不是 FPGA 启动配置 Flash；这不等同于保存当前歌曲位置或实现断电续播。

## 7. 最值得盯住的四类工程难点

### 跨时钟域

先列出源时钟、目标时钟、数据位宽和握手方式。单比特状态可用同步链；多位数据要检查握手/稳定窗口/原子快照。音频缓存和 MV 请求的跨域设计，不能只看“有两个触发器”。

### 背压和共享资源

SD 扇区读取和 SDRAM 操作具有不同排队与完成语义。音频优先级、MV 配额、FIFO 满/空以及写入 owner 的保持共同决定实时性。分别画“谁向 SD 提交请求”和“谁向 SDRAM 发起读写”。

### 时间一致性

音频样本消费是媒体时间的重要来源；MV 帧目标据此调度。不要把 HDMI 像素时钟、实际 PCM 消费和文件读取速度当成同一时间基准。

### 复位与取消

检查每个域 reset 的断言和释放；检查暂停、切歌、Seek 如何处理中途事务。状态机回到 IDLE 不代表外设已结束；资源复用必须等物理请求或数据通道完成清理。
