## 2. 三条需要能从头讲到尾的链路

### A. 声音到媒体时间

顶层计划采样tick → wav_stream_player缓存与ready判定 → buffer_read / sample_consumed → timebase_48k → cur_time_ms → 歌词/进度/MV目标时间。

先读F03–F08，再沿顶层搜索wav_sample_consumed、lyric_time_ms、play_track_restart_vid。暂停、欠载、尾部有效样本和Seek分别改变哪些条件，是答辩中的关键追问。

### B. 卡片到完整画面

INDEX元数据给出地址/格式 → background_sector_mux获得扇区owner → mv_stream_player读300扇区并解包 → 写入FIFO/SDRAM → 写完成标记 → mv_frame_scheduler维护可显示帧 → frame_start更新display_bank。

重点核对F13–F18。文件系统只承接对应索引/封面路径，运行音频/MV/背景数据另走扇区访问。绘图时分别标“文件流”和“raw LBA”，便于解释当前媒体格式。

### C. 设置到重启恢复

物理输入 → 同步/解码/事件 → 参数控制器 → CSR当前快照 → ui_param_persistence → w25q64_param_store → 下次启动load_valid → CSR恢复 → 运行参数CDC/帧边界生效。

重点核对F19–F26。保存和恢复在UI域有直接连接，运行消费者再做相应跨域；参数保存不能简单画成“从视频域经CDC写Flash”。

## 3. 可直接写入报告的理论计算

| 项目 | 算式与结果 | 单位和条件 |
|---|---|---|
| 单声道PCM净数据率 | 48000×16/8=96000 | B/s，不含协议开销 |
| 一个音频扇区样本数 | 512/2=256 | 样本/扇区 |
| 一个扇区覆盖时间 | 256/48000≈5.333 | ms，按当前格式 |
| 默认PCM缓存物理容量 | 4096×2=8192 | B；全部容量与可用余量分别理解 |
| PCM缓存全部容量换算 | 4096/48000≈85.33 | ms理论容量，不是已证明可抗任意卡顿时间 |
| MV卡上单帧大小 | 320×240×2=153600 | B=300个512B扇区 |
| MV净数据率 | 153600×10=1536000 | B/s；10fps源素材 |
| 音频+MV净数据率 | 96000+1536000=1632000 | B/s，仅两个媒体负载，不含卡协议、背景和存储放大 |
| MV解包后字跨度 | 320×240=76800个32bit字 | 307200B物理字跨度；图像使用高24bit |
| 10fps目标帧间隔 | 1000/10=100 | ms，与HDMI扫描刷新率分别说明 |

用这些计算解释为什么需要缓存和仲裁。实际吞吐、延迟、同步误差、掉帧、欠载、功耗等指标，使用10中的待填表记录条件和方法后再填结果。

## 5. 写文档时的六类数值标签

1. **设计规格**：当前代码和媒体格式约定，如48kHz、四曲、10fps。
2. **理论换算**：按上述规格推算的B/s、扇区覆盖时间和容量。
3. **归档仿真**：对应输入、模型、刺激与结果文件的通过项。
4. **归档物理实现**：特定策略、种子、约束及工具版本下的资源和STA。
5. **现场观察**：本次录像可观察到的动作与结果。
6. **现场测量**：写明仪器、方法、样本数量、原始记录和不确定范围的数字。

不同标签可以共同支持一个论证，但正文中保留各自来源。这样既能展示工程完成度，也便于回答评委的量化追问。
