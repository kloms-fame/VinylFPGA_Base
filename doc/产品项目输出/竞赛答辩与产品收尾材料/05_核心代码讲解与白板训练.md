# 05｜核心代码讲解与白板训练

> 日期：2026-10-19。用途：看懂项目、现场答辩、撰写技术章节。本轮只读当前关键 RTL 并制作学习材料，不运行测试、构建或烧录。练习中的数值推导是依据源码规格的计算，不能冒充实板测量；资源/时序引用见 [归档结论](../23_最终综合评审与收尾结论.md)。

## 一、先知道自己要学到什么程度

学习目标不是记住四万多行仓库文本。目标是能独立说明：

1. 一个媒体字节从哪里来，经过哪几种单位，最后如何成为样本或像素。
2. 一个用户动作如何改变系统状态，什么时候旧事务退出，什么时候新状态生效。
3. 多时钟域如何保证事件不误配、配置不撕裂、缓冲不覆盖。
4. 可见功能背后的关键不变量是什么，源码在哪。
5. 哪些结论来自当前 RTL，哪些来自历史归档，哪些必须由实物材料证明。

本文八项练习按依赖排序；先画图、口述、做例题，再查代码。白板练习是学习活动，本轮没有执行对应硬件操作。

## 练习 2｜从 PCM 字节推导可用样本、缓存和媒体时间

### 题目

设卡上字节 0x34、0x12 依次到来。解释拼样本、缓存写入、缓存读取和时基更新。再计算一扇区样本数、4096 样本理论时长，说明“计划节拍来了但缓存不可用”的结果。

### 参考答案

1. little-endian，先到低字节，后到高字节，得到 16'h1234。有符号解释由最高位决定；此例是正值 4660。
2. 仅在合法填充状态、有效字节对、未跳过、remaining 非零时写入样本数组。
3. read 侧使用 `buffer_read = rd_rst_n && sample_tick && sample_ready && buffer_available`；实际消费就是该事件。
4. 若 sample_tick 到来但 buffer_available 为假，不读指针、不产生 sample_consumed；输出路径以零保持静音契约，媒体文件位置不增长。
5. 顶层 timebase_48k 端口名是 sample_tick，实参却是 wav_sample_consumed；只有实际消费且 running 时计数。

~~~text
512 B / 2 B = 256 samples
256 / 48,000 s = 5.333... ms
4096 / 48,000 s = 85.333... ms
BUFFER_HIGH_WATER = 3072 -> 理论64 ms
BUFFER_LOW_WATER  = 2048 -> 理论42.666... ms
~~~

**必须补一句：**这些是容量/阈值换算，不是并发负载下已验证的最大断流容忍时间。当前低水位用于紧急服务判定，不应讲成写侧补数恢复阈值；写侧节流围绕高水位判断。

**源码链路：**[wav_stream_player](../../../src/audio/wav_stream_player.v)第 56 行起水位、第 132–173 行缓存读写→[top 时基接线](../../../src/top_tf_hdmi_audio.v)第 2876 行→[timebase_48k](../../../src/audio/timebase_48k.v)。

### 例题

已经消费 47 个有效样本，再来一个计划节拍但缓存不可用。答案：媒体毫秒仍不进位；下一次真正消费第 48 个有效样本时才进位。不能为了画面顺畅虚构一次媒体消费。

## 练习 3｜手算 Seek，画清定位后的重新启动

### 题目

一曲 total_samples=1,000,000，当前实际位置 900,000。接受一个 +5s 步进后目标是多少？该目标对应第几个扇区和首扇区跳过多少样本？画出新会话开始之前的条件。

### 参考答案

~~~text
STEP_IR = 240,000 samples
未经钳位目标 = 900,000 + 240,000 = 1,140,000
合法上界 = total_samples - 1 = 999,999
最终目标 = 999,999
sector_offset = floor(999,999 / 256) = 3,906
skip_samples = 999,999 mod 256 = 63
新的物理LBA = 曲目start_lba + 3,906
~~~

当目标为最后一个样本时，剩余有效样本数及尾部处理须按当前顶层计算与播放器契约配套，不能再按完整扇区全部播放。

~~~text
定位事件
 -> 扩位有符号加法 / 钳位 / 提交target
 -> restart请求
 -> 停止旧会话供数与读者
 -> 等 storage_busy=0、video_busy=0、同步reader_idle=1
 -> 稳定等待 / 新session start_toggle
 -> 按新LBA与skip_samples供数
 -> timebase.load_sample重定位
 -> 有效储备后消费
~~~

**源码链路：**[seek_controller](../../../src/audio/seek_controller.v)→[top 目标到扇区/跳过样本接线](../../../src/top_tf_hdmi_audio.v)→[stream_session](../../../src/audio/stream_session.v)→[wav_stream_player](../../../src/audio/wav_stream_player.v)。

### 易错点

seek_controller 的文件头/端口注释保留了旧“EC2、F8/EA/F6”映射，不能拿来写当前用户操作手册。当前物理输入应追 [ui_command_router](../../../src/io/ui_command_router.v)和顶层；内部 ±2s、±5s、replay 事件含义与外部键码是两个层次。

### 追问答案

- 负目标：钳位到 0，不能让无符号下溢绕到曲尾。
- 忙时新步进：继续向最新目标累加/合并，检查 pending 路径，不是所有输入都直接覆盖当前 transaction。
- 清空指针不能解决迟到返回：旧存储事务必须排空，见下一练习。

## 练习 4｜共享 SDRAM 的 lane、地址和事务排空

### 题目

音频缓存 slot=7、offset=511，当前映射的 SDRAM 字地址是多少？如果这一地址的高 24 位是图像，写音频 0xAB 后什么内容应被保留？若发出读请求后超时，能否立即切给新会话？

### 参考答案

~~~text
word_address = slot*512 + offset = 7*512 + 511 = 4095
word[31:8] = RGB888
word[7:0]  = audio_byte

音频写数据 = {24'd0, 8'hAB}
音频mask = 4'b1110，保持高24位
图像mask = 4'b0001，保持低8位
~~~

字地址 4095 不是字节地址 4095。该逻辑窗口中的第 4095 个 32-bit 字，对应按字节计算的总线跨度偏移 16,380B；音频实际只使用其中一个 lane。

~~~mermaid
stateDiagram-v2
 [*] --> IDLE
 IDLE --> LOCK: 收到稳定mailbox
 LOCK --> READ: 已取得资源并等静默
 READ --> READ_DRAIN: 本块命令发出
 READ_DRAIN --> YIELD: 返回齐全并静默尾部完成
 YIELD --> LOCK: 下一个块
 READ_DRAIN --> DONE: 最后块完成
 READ --> FAIL: watchdog过期
 READ_DRAIN --> FAIL: watchdog过期
 FAIL --> RECOVER: 已有在途命令
 RECOVER --> IDLE: 返回与尾部排空
 DONE --> IDLE
~~~

超时后仍保留 read_owner，把迟到数据隔离；恢复状态不向 staging 发布新有效 payload。若应有返回永不出现，不能安全释放给下一事务，需要协调复位处理。

**源码链路：**[audio_prefetch_sdram mailbox](../../../src/audio/audio_prefetch_sdram.v)→[audio_sdram_dma 地址、mask、recover](../../../src/audio/audio_sdram_dma.v)→[audio_sdram_arbiter 尾部mask](../../../src/audio/audio_sdram_arbiter.v)→[top PRESERVE_LOW_BYTE](../../../src/top_tf_hdmi_audio.v)第 1721 行。

### 判分

答出四条不变量：写图不破坏音频、写音频不破坏 RGB、返回只能归原 owner、失败不等于外部事务撤销。仅背“仲裁优先级”不算讲清该练习。

## 练习 5｜两层仲裁的边界条件推演

### 题目

在 SD 空闲边界，同时有 audio_req、video_req、background_req。分别讨论音频紧急、音频健康且 video_quota=14、音频健康且 video_quota=15 的获胜方。再解释为什么 SDRAM 层还需要另一套仲裁。

### 参考答案

| 条件（video 允许且有请求） | 本次选择 | 原因 |
|---|---|---|
| audio_urgent=1 且 audio_req=1 | audio | 紧急音频优先 |
| audio_urgent=0，video_quota=14 | video | 配额未到15，允许健康储备期间MV前进 |
| audio_urgent=0，video_quota=15 且 audio_req=1 | audio | 音频获服务并清零配额 |
| 无音频请求、无可服务视频，背景准入且请求 | background | 低优先级背景获得机会 |

要同时检查 owner_valid=0、sector_busy=0；已有扇区事务不会因新紧急请求中途变更 owner。没有音频请求时，配额到 15 也不强制空转等待音频。

**SDRAM 层不同点：**需要保护已经在途的图像 burst、音频 DMA 的锁和 read_owner、掩码写尾；它不直接决定 TF 卡下一扇区的 LBA。

**源码链路：**[top 活动仲裁和水位准入](../../../src/top_tf_hdmi_audio.v)第 2330 行→[background_sector_mux](../../../src/video/background_sector_mux.v)→[audio_sdram_arbiter](../../../src/audio/audio_sdram_arbiter.v)。

### 延伸题

为什么不能把 MV 的 request 写成 `state==REQ && !busy`？答案：对仲裁器隐藏需求，可能破坏加权选择，使客户端在“看不见需求→不给服务”的循环中饥饿。当前 mv_stream_player 保持请求，由 `!sector_busy` 接受。

## 练习 6｜MV 三缓冲与三种完成事件

### 题目

bank0 正在显示，bank1 是已写完但还没到播放时间的 pending，bank2 正在写入。现在 bank2 完整写好：能否直接覆盖 bank0？暂停、Seek 或旧帧已过时时分别应讲什么？

### 参考答案

- 不直接覆盖 bank0；当前扫描仍在使用它。完整帧在 frame_start 满足 show_ready 等条件才提交。
- 若 pending 仍是未来帧且没有可退役空间，完成 mailbox 可停留，不能把唯一空闲身份凭空释放给新写入。
- 当前显示 bank、pending bank 与写入 bank 的身份必须互不冲突；只有空闲 bank 才能发起新帧写。
- 暂停时普通帧提交/请求受限，首帧有单独规则；需要逐条核对 `(!paused || first_frame)`，不宜概括为“一暂停全部逻辑立即停止”。
- Seek/restart 时 invalidating、discard、clear_pending 使旧任务失效；在途任务仍需完成/隔离，失效完成不得作为新帧显示。
- 过时帧允许跟随音频时间跳过，避免视频积压越来越多；不能声称每个编码帧都必定显示。

~~~text
最后SD字节到达
   ≠ SDRAM已写完
   ≠ 当前显示bank已经切换

300扇区正常读完
 -> DRAIN等待write_finish_toggle变化
 -> done_toggle交还任务
 -> 调度器判定完成有效、媒体时间已到
 -> frame_start提交display_bank
~~~

**格式换算：**320×240×2B=153,600B=300 扇区；SDRAM 76,800 字/帧。10fps MV 净载荷 1,536,000B/s，加 PCM 后净媒体载荷约 1,632,000B/s；这不是实际 SPI 线速，尚未计协议、空闲、重试和其他资源。

**源码链路：**[mv_stream_player](../../../src/video/mv_stream_player.v)第 59–73 行→[mv_frame_scheduler](../../../src/video/mv_frame_scheduler.v)→[s6_video_layer](../../../src/video/s6_video_layer.v)→[top bank 地址和帧读时序](../../../src/top_tf_hdmi_audio.v)。

## 练习 7｜给三类跨域信号选择合适结构

### 题目

下列信号如何跨域：①一个参数快照；②一次切换事件；③连续 PCM 样本缓冲进度？说明目标域单独复位和忙时连续更新时的风险。

### 参考答案

| 对象 | 结构 | 必须检查的契约 |
|---|---|---|
| 慢速多位参数状态 | 稳定bundle+req/ack | payload保持直到确认；忙时可合并最新值 |
| 离散事件 | toggle/事件桥 | 目标域同步后还原；事件频率不超过桥接承载能力；相邻toggle须留足目标域同步捕获间隔 |
| 连续样本缓冲进度 | 双时钟存储与Gray指针 | 空满、水位、同步延迟和复位一致性 |

`cdc_bundle_latest` 目标端收到同步请求后整体采样 src_data_latched，并回 ack；源端忙期间只记有更新待发送，完成后发最新状态。它不是保存每次中间修改的 FIFO。

目标域单独复位会清 dst_data；当前模块用 dst_alive 回传触发源端重新发布，避免目标永远停留在复位值。复位同步释放模块有助于管理域内释放，但不能概括成“彻底消除所有亚稳态”。

**源码链路：**[cdc_bundle_latest](../../../src/cdc_bundle_latest.v)→[sync_2ff](../../../src/sync_2ff.v)→[ui_event_bridge](../../../src/io/ui_event_bridge.v)→[wav_stream_player Gray 指针](../../../src/audio/wav_stream_player.v)→[reset_sync](../../../src/reset_sync.v)。

### 口头追问

为何不用一套结构处理所有东西？答案：状态只需最终值，事件关心发生次数，流数据关心顺序与连续容量；丢失/合并的允许条件不同。看见多级同步器还应核查源端稳定时间、目标捕获窗口和复位。

## 练习 8｜五参数保存，画清提交点与断电边界

### 题目

画出五参数从旋钮写入、应用、自动/手动保存、重启恢复的完整路径。假设写新槽 payload 后断电与提交成功后断电，启动接受记录的条件有什么不同？

### 参考答案

~~~mermaid
flowchart LR
 INPUT[操作事件] --> CSR[50MHz参数CSR]
 CSR --> CDC[运行快照CDC]
 CDC --> USE[音量 / 图像 / 灯效 / 轮播]
 CSR --> PERSIST[同域持久化控制]
 PERSIST --> SNAP[稳定snapshot]
 SNAP --> NEW[擦除目标槽 / 写payload]
 NEW --> VERIFY[回读payload比较]
 VERIFY --> COMMIT[单独写A5 5A]
 COMMIT --> VERIFY2[回读完整记录]
 VERIFY2 --> DONE[save_done / 已保存]
 BOOT[上电读取两槽] --> CHECK[格式 / 版本 / 范围 / CRC / commit / seq]
 CHECK --> CSR
~~~

- 五参数为 `{WSL[2:0],ROT[2:0],CON[2:0],BRI[2:0],VOL[7:0]}`，共 20bit；默认值 WSL4、ROT2、CON2、BRI3、VOL200。
- 自动保存要求使能、dirty、稳定时间与存储就绪等条件；手动保存通过 pending 执行，不是按键直接组合拉 SPI。
- 新槽只有 payload 无有效 commit 时不应被当成完整新记录；旧有效槽仍是恢复候选。
- 提交后仍要有格式、CRC、范围与完整核对；序号决定两条有效记录的新旧。这里是记录选择机制，不能泛化成任何掉电波形都绝对安全。
- 恢复默认走 defaults_pending；默认记录提交后还有旧槽清理路径，应按该分支讲清。
- user_write/defaults 在启动期间可抑制迟来的旧值恢复，尊重当前用户操作。
- 软重启恢复与物理断电自启是两种展示证据；用户 Flash 保存不等于 FPGA 配置 Flash 自启，且当前没有播放位置续播。

| 数据与单位 | 混淆样本/字节/字/LBA | 主路径正确但边界不全 | 能独立推导并指出转换处 |

## 五、白板成果如何写入正式技术报告

每个技术章节采用同样六段：**输入约束→系统问题→设计机制→关键状态/不变量→证据→权衡与扩展**。图下说明单位和时钟域；表中标注归档结果或待测量。引用源码应对应当前活动路径，厂商 IP、生成 ROM、课程基础和本人改动分别说明来源。这样技术材料、答辩语言和可见演示才能保持一致。
