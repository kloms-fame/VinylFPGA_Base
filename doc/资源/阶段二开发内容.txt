#### 2. 第二阶段（选歌浏览界面）核心矛盾与最优解法

* **核心挑战**：选歌浏览态（`STATE_BROWSE`）需要完整呈现 **曲目序号、歌名、歌手与歌曲总时长**。然而当前安路 EG4S20BG256 的 BRAM9K 已占用 47 块（余量仅 17 块），PLB/MSlice 处于 87%+ 的敏感水位。如果为了选歌界面重新例化一套中文字库 ROM、新增一套文本解析引擎或建立新的行缓存，将直接导致 BRAM 枯竭并在 Native 布局阶段触发 `PHY-9009` 超限错误。


* **最优解法（时分复用单体渲染架构）**：
在 `STATE_BROWSE` 浏览态下，五行歌词滚动、实时音频波形及 320px 播放进度条处于 **完全关闭与静默状态**。此时，位于 `video_clk` 域的 `song_text_rom`（曲目元数据 ROM）、`song_font_rom`（16×16 点阵中文字库）以及底层的光栅流水线算力存在 **100% 的时分空闲窗口**。
因此，最优方案是**直接在 `playback_page.v`（或统一界面渲染器）内部开辟浏览态渲染通道**：


1. 共享同一套 `song_text_rom` 与 `song_font_rom`；


2. 共享 `playback_progress.v` 在场消隐期解算完成的 `total_time_ascii`（总时长）；


3. **0 额外 BRAM 消耗、0 新增乘除法器、仅增益约 70~100 个 LUT4**。

#### 2. 半透明暗化底衬的零开销硬件实现

如果文字直接悬浮在多变的封面上，浅色封面会导致白字被吞没，深色封面会导致暗调文字辨识度下降。
为了在零乘法器消耗的前提下实现毛玻璃暗化效果，采用**单拍无乘法算术右移**：

```verilog
// 当处于信息栏区间且无文字笔画覆盖时，底层封面像素亮度衰减 50%
wire in_browse_bar_bg = (pixel_x >= 10'd32) && (pixel_x <= 10'd607) && 
                        (pixel_y >= 10'd416) && (pixel_y <= 10'd456);
wire [23:0] dimmed_cover_rgb = {1'b0, rgb_in[23:17], 1'b0, rgb_in[15:9], 1'b0, rgb_in[7:1]};

```

该结构在综合时直接映射为导线剥离，**完全不消耗逻辑 LUT 与 DSP，且不引入组合逻辑级联延时**。

### 三、 跨模块极致复用与接口契约设计

```
                    ┌────────────────────────────────────────────────────────┐
                    │               top_tf_hdmi_audio.v 顶层                 │
                    └────────────────────────────────────────────────────────┘
                                                 │
                  active_ui_song_id = play_active ? play_song : browse_song
                                                 │
                        ┌────────────────────────┴────────────────────────┐
                        ▼                                                 ▼
          ┌───────────────────────────┐                     ┌───────────────────────────┐
          │     song_text_rom.v       │                     │    playback_progress.v    │
          │  (单体 ROM, 提取当前曲目) │                     │   (V-blank 32拍解算总长)   │
          └───────────────────────────┘                     └───────────────────────────┘
                        │ title/artist glyphs                             │ total_time_ascii[39:0]
                        └────────────────────────┬────────────────────────┘
                                                 ▼
                               ┌───────────────────────────────────┐
                               │        playback_page.v            │
                               │  (时分复用: PLAY态 / BROWSE态)    │
                               │  - 共享 16x16 song_font_rom       │
                               │  - 共享 1拍硬件流水线与色键合成   │
                               └───────────────────────────────────┘

```

#### 1. 曲目身份（Song ID）的全局仲裁

* **现状分析**：当前 `song_text_rom` 的输入引脚绑定的是 `song_id_frame`，该信号在旧实现中仅由 `lrc_window_controller` 在播放态驱动，浏览态处于锁定状态。而在选歌浏览态，当前选中的封面焦点是由 `disp_buf_idx` 决定，并通过 CDC 同步到像素时钟域的 `song_metadata_video[1:0]`。


* **统一仲裁契约**：在顶层定义并分发全局 UI 活动曲目：
```verilog
// 播放态使用锁存的播放曲目，选歌态无缝跟随当前浏览焦点
wire [1:0] active_ui_song_id = (play_active_v2) ? song_id_frame : song_metadata_video[1:0];

```


将 `active_ui_song_id` 接入 `song_text_rom` 的 `song_id` 端口，保证用户旋转编码器或按上下键切歌时，`song_text_rom` 能即时吐出当前选中曲目的歌名与歌手信息。



#### 2. 时长（Duration）解算总线的完全复用

* **现状分析**：`playback_progress.v` 在阶段一中已内置了场消隐期（`vs` 沿）的轻量恢复移位状态机，用来计算音频总时长并转化为 ASCII 字符串输出在 `playback_time_ascii[103:0]` 中。


* **共享契约**：
`playback_time_ascii[39:0]` 稳定对应最后 5 个字符，即总时长 `"MM:SS"`。
在浏览态，即使未发生样本消费（`elapsed_samples = 0`），只要 `total_samples` 稳定输入，该状态机每帧消隐期都会刷新总时长 ASCII 码并保持锁存。选歌界面直接截取这 40 位总线送入 ASCII 渲染流，**省去独立的二进制转 BCD 逻辑及 ASCII 转换器**。



#### 3. 字符点阵流水线时分复用（Time-Division Multiplexing）

* 在 `playback_page.v` 中，文字光栅化模块在 $Y \in [424, 439]$ 扫描期间工作：
* 计算相对横坐标：`browse_x_rel = pixel_x - 10'd164`；
* 根据字符索引提取 `title_glyphs` 或 `artist_glyphs` 的字模索引；
* 送入已有的 `song_font_rom` 寻址端口，读出 16-bit 行点阵；


* 提取点阵位：`glyph_bit = font_row_bits[15 - browse_x_rel[3:0]]`；


* 笔画命中时输出对应前景色，未命中且在底衬区时输出 `dimmed_cover_rgb`，其余区域直通 `rgb_in`。


* **结论**：字库 BRAM 与点阵流水线完全共享，消灭了任何多余的存储与控制开销。
