## 6. 可优化项与建议顺序

### P0：先建立“同一输入、同一口径”的基线

冻结当前 `.al`、RTL、SD 歌词素材和约束的 SHA-256，连同 TD 版本 `6.2.168116` 与 SynthPilot 的 gate/place/route 报告归档；之后每个候选只改一个资源杠杆。SynthPilot 单次 route 用于诊断和快速比较，正式资源/时序签核仍按方案要求走固定 native `area_prior + seed5 + fix_hold + final`，并将两套数字分栏记录。

### P1：R3 删除缩略图选曲（RTL/工程清理与 SynthPilot route 已完成，等待人工验收）

本轮已删除 `thumbnail_controller`、`thumbnail_view_reader`、`thumbnail_layout`、`sdram_rd_arbiter` 和顶层相关请求/数据/FIFO/仲裁分支，保留中央大图复用封面读取路径；KEY7/KEY11 在播放态都回到中央大图选曲。实际 route 比此前工作区减少 286 Slice、6 PLB、641 LUT、2 BRAM、1 DSP，Setup WNS 改善 2.299ns；Hold WNS 仍为 −4ps。历史 O6 层次报告中的 `u_thumbnail_view_reader` 约 292 LUT、243 个序列单元、2 BRAM、1 DSP 只是旧层级估计，不代表本次精确节省量。还需人工确认切歌、播放进入/退出、自动轮播和封面回退。

### P2：修复外存写 FIFO 控制路径（方案 R2）

先从当前 route 的两个极短 Hold 违例入手，核对 native `fix_hold` 是否会自动修复 HDMI 音频 FIFO 的 RAM 地址路径；避免直接改厂商 HDMI IP。随后以新的关键路径为依据做 R2：当前 `sd_card_clk` 最差 Setup 路径在 FAT32 音频索引扫描，net delay 占 72%；`ext_mem_clk` Setup WNS 已为 +0.474ns，之前 `frame_fifo_write` 是负裕量路径的旧基线不再是当前主要靶点。任何修复都需保持约束不变并复查 route、Hold 与拥塞。

### P3：SD 卷扫描路径

当前门级关键 SD 路径的 `audio_active` 最大扇出 60、net delay 约 66%。考虑让匹配条件局部化、提前一拍产生稳定控制，或减少跨层广播；以 FAT32 扫描状态和挂载时序不变为前提逐项测量。不要未经协议分析就插入周期或错误地加 multicycle。

### P4：歌词窗口连接度与显示控制

`u_lrc_window_controller` 是唯一超过 Rent 0.7 的层次模块。先看 768-bit 六行字形总线、窗口发布/代次控制、像素端重复译码是否形成额外扇出；可以评估局部寄存/更窄接口/减少重复比较，但需保住同曲、Seek、暂停和相邻行平滑滚动语义。避免把“一套 ROM 读口”扩成五套扫描器。

### P5：小项清理与歌词数据架构

- 核查 8 个 dangling `syn_keep` 实例由何处产生，只移除确认无功能/无调试用途的实例；不能批量删 `keep` 属性。
- D11/D12 当前只有演示词；拿到正式素材后重新生成并测量字符数、行数和字库 BRAM。
- 歌词加载方案 C 已选，排在 R3/R2 后做小原型。参考 F2 估算动态字形与元数据约 7–9 个 BRAM，替换当前约 8 块编译字库；主要收益是免重烧和 PC 侧维护，资源净变化预计接近 0。PC 转换器、SD 预载及 FPGA 写入 RAM 的实现增量和 SD 时序都需实测。
- 保持现有蜂鸣反馈效果，不把蜂鸣器重构列为主优化项。

### 暂缓功能

- 亮度/对比度/浮窗等已有功能不再扩展图层；播放页和歌词小改动先以综合增量为门禁。
- D13 方案预算约 +300 Slice、+3 BRAM；当前 BRAM 47，单看 BRAM 预计约 50，但 Slice/PLB 和 Hold 仍没有充足余量。必须等 R3/R2 后完整 route 达标再立项。

## 7. 推荐阶段安排与门禁

1. **冻结本轮综合基线**：留存当前 SynthPilot gate 报告和输入哈希，确认正式/演示素材边界。

3. **R2 收敛**：先确认 HDMI 音频 FIFO 极短 Hold 路径的正式 `fix_hold` 处理，再按当前 `sd_card_clk` 最差路径做一项资源/时序优化；route 后要求 Setup/Hold WNS≥0，并尽可能增加 Slice/PLB 余量。
4. **R1/D11-D12 固化**：补齐定向验证记录、输入哈希和真实歌词配置的资源报告；确认演示歌词不误当正式曲目。
5. **R4/D14**：按独立候选实施有符号峰值修正，完整检查暂停、Seek、静音和正负满幅。

用户确认的**硬放行门槛**是 route 资源不得超器件容量、Setup/Hold WNS 均≥0；同时希望尽可能多回收资源，为后续功能留余量。方案中的 Slice≤85%（≤8,330/9,800）、PLB≤2,400、BRAM≤52、Setup≥+0.2ns/Hold≥+0.05ns 可作为更积极的**优化目标**，不作为第一轮必须停线的硬门槛。当前距 Slice 优化目标仍差约 1,114 个 Slice，距 PLB 目标差 43 个；R3 实测虽有改善，但远未到可放心叠加 D13/F2 的余量，后续应继续对关键控制路径和高占用层次做实测优化。

## 8. 歌词数据更新方案比较

参考方案 F2 给出的低资源做法是：PC 工具将 UTF-8/LRC 预处理成每曲 `TRACKn.FNT` 并写入 SD 卡；FPGA 加载本地字形编号、点阵和歌词时间记录，不在芯片内解析 Unicode。用户已确定采用方案 C，并要求排在 R3/R2 后做小原型。下表保留 A/B 作为被比较过的备选，当前开发路线以 C 为准。

| 方案 | 换词流程 | FPGA 资源与时序 | 维护与风险 |
|---|---|---|---|
| A. 编译期 RTL/ROM | 改 LRC/歌词源、重新生成 RTL、综合、烧录 | 现有 4,096×16 字库约 64 Kibit，粗估约 8 个 BRAM9K；无运行时加载器，时序风险最低且最可预测 | 实现最简单；每次换词都需要重烧，操作繁琐 |
| B. SD 卡直接存原始 LRC，FPGA 运行时解析 | 修改文本并复制到卡，不重烧 | 需要 UTF-8/时间戳解析、字符映射和缺字处理；还需要完整或较大的字库。相较 F2 会增加解析逻辑和状态，可能加重 SD 域时序/CDC 风险 | 文本易编辑；编码、格式边界、非法行与缺字的硬件处理复杂，不建议先做 |
| C. PC 预处理为每曲 `TRACKn.FNT`，FPGA 从 SD 预载（参考方案 F2） | 改 `.lrc`，运行工具生成 `.FNT`，把新文件复制到 SD 卡；不重烧 | 预计 6–7 BRAM 放本曲字形、1–2 BRAM 放行与元数据，替换当前约 8 BRAM 字库，净变化约 −1 至 +1 BRAM。会增加轻量加载逻辑和 SD 路径，需要完整 route 验证 | PC 端工具负责 Unicode/LRC 检查；FPGA 端只处理定长二进制和本地字形号。可在播放前装载，播放时不读歌词 SD，资源与体验较平衡 |

现有 BRAM 为 47/64，虽然总 BRAM 余量有 17 块，但 Slice 与 PLB 仍接近满载，不能因为 BRAM 数字够就直接加 F2。方案 C 的主要收益是换词免重烧、歌词维护脱离 FPGA 工程；它不是明确的逻辑减负项目，也不保证 Slice/PLB 下降。F2 应放在 R3/R2 后做小规模原型，先测可写字形 RAM 是否映射为预期 BRAM、加载逻辑的 LUT/PLB 增量，以及 `sd_card_clk`、`ext_mem_clk` 的 route WNS。

推荐的文件流程是：PC 仍保存可读 `.lrc` 源；工具校验字数、时间单调性和单曲字形上限，并输出 `TRACKn.FNT`；卡内 INDEX 提供文件簇/大小；FPGA 在选曲稳定或进入播放前将本曲字形和歌词记录装入 RAM，加载完成后帧边界切换显示。播放/MV期间不访问该歌词文件。缺文件或旧 INDEX 应显示短占位文字。该流程与方案的 v1/v2 兼容回退、焦点代次取消和播放前驻留原则一致。
