## 0. 结论摘要

**第一轮已把时序做到收敛（Setup WNS +31 ps / 违例 0），但资源不降反升（LUT +28）。**
本轮的核心发现是：**上一轮把注意力放在"降 LUT"，但真正的约束是 Slices 与布线拥塞。**

| 关键事实 | 数值 | 含义 |
|---|---:|---|
| LUT | 16062 / 19600 = **81.95%** | 剩 3538，且不等于可布通空间 |
| Slices | 8723 / 9800 = **89.01%** | **已越过方案 §3.3 的 88% 减负阈值** |
| REG | 10152 / 19600 = 51.80% | 尚有余量 |
| BRAM9K | 46 / 64 = 71.88% | 大头是厂商 IP 与 Logo，属不可压缩项 |
| DSP | 16 / 29 = 55.17% | **不是瓶颈，不动** |
| Setup WNS | +31 ps（布线后） | place 阶段为 **+2719 ps** |
| 布线损失 | 2688 ps | **占 place→route 裕量的 99%** |

**三条结论：**

1. **瓶颈是布局布线拥塞，不是逻辑深度。** R1 最差路径 `rgb_byte_cnt[2] → pixel_end_reg[26].ce` 只有 7 级逻辑，但 **net delay 占 68%（6.573ns / 9.689ns）**，典型拥塞特征。
2. **`sd_card_clk` 域是资源与拥塞的双重热点**：该域独占 **3509 LUT**（全设计 27.8%），而它跑在 100 MHz（10ns 预算，最紧的非 PLL 输入时钟域）。
3. **本轮找到第一轮完全遗漏的一批"纯死逻辑"，合计可释放约 560 FF + 200~350 LUT，且零功能行为改变。** 集中在 `song_index_db`——它是 `sd_card_bmp` 内第三大模块（LUT 1231），却是全项目最容易安全瘦身的地方（详见 §1.4 A1）。

> **口径声明**：本文所有数值取自 `OPT_R1_mul_v1/gate.area`（综合后层次分解）与 `final.timing`（布线后时序）。
> 顶层 `gate.area` 的层次 LUT 为**累计值**（含子实例），本文表格已注明是累计还是独占。
