## 0. 摘要（先看结论）

### 0.1 本轮做了什么

1. 复核工作区状态与 HEAD，记录未提交修改，确认不清理、不回滚、不混入本次提交。
2. 从候选池中选定 **候选 E** 作为唯一的第一项实现（选型理由见第 13 章）。
3. 只改 `src/SD/fat32_media_loader.v` 一个文件：删除 32 位 `pixel_byte_cnt` 及其复位/装载/自增，LD_DATA 的字节消费守卫改为 `pixel_count < expected_pixel_count`。**逐行、逐拍等价**（证明见第 4 章）。
4. 先跑定向仿真（7 项）与新增边界用例（2 项），再跑 53 项回归套件的前后对照。
5. 建隔离工作副本，跑 **native 正式流程**（`map_mode area_prior` + `set_param place seed 5` + `route` + `fix_hold` + `update_timing -mode final` + `report_qor/report_area -verbose/check_timing`）的 before/after 两次完整 route，并做了一次独立复现轮。
6. 同时用 SynthPilot MCP 的默认单 run build 做 before/after 诊断对照（after 跑了两次）。
7. 达到用户给的**硬门槛**后提交，提交信息为简体中文，只包含本项改动。

### 0.2 关键结论（十条）

1. **native 硬门槛通过**：Setup WNS `-0.127ns/2 EP` → `+0.116ns/0 EP`，TNS `-0.154ns` → `0`；Hold WNS `+0.030ns/0 EP` 保持不变；资源不超限。
2. **改动是可证明的等价替换**：进入 LD_DATA 前 `pixel_count=0`，且只在本分支每 3 字节加一，记已消费字节数 `N`，则 `pixel_count=floor(N/3)`；`N<3P ⟺ floor(N/3)<P`，与原 `pixel_byte_cnt<pixel_end` 逐拍等价。无新增寄存器、无启动/Seek/暂停延迟变化。
3. **前 2 条（乃至前 9 条）native setup 违例全部以 `pixel_byte_cnt_reg[12]` 为起点**，net 占 72%~73%、扇出 36、7 级逻辑 —— 是"网延迟主导的单一扇出源"，不是泛化的音频元数据树。这是选择 E 的直接依据。
4. **仿真证据完整**：7 项定向 TB 全 PASS；53 项回归套件改动前后失败集合**完全一致**（各 13 项既有失败，均来自工作区未提交接口改动与陈旧 TB 的不匹配）；2 项新增边界用例前后输出一致。
5. **资源收益方向在 native 口径为下降**：final LUT `15780 → 15683`（-97）、reg `10507 → 10449`（-58）、PLB `2425 → 2422`（-3）、gate 寄存器 `10316 → 10271`（-45）；Slice `8518 → 8588`（+70）与 LE `16402 → 16522`（+120）轻微上升。
6. **"资源一定变好"是错的**：Slice/LE 在两个口径下都小幅上升；PLB 只降 3。真正的确定性收益是"去掉一个 32 位计数器（寄存器 -45~-58）"和"消除 native 的 sd_card_clk setup 违例"。
7. **两套口径出现严重分歧，必须并列披露**：同一份 RTL 差异，native 口径 Setup `-0.127 → +0.116ns`（变好），SynthPilot 默认诊断口径 Setup `+0.221 → -3.557ns / 46 EP`（变差）。**两口径从 gate 起就是两条不同的实现路径**（诊断 `map_mode=auto`、native `area_prior`）：诊断 gate after 更好（+115 → +210ps），native gate after 反而更差（−34 → −369ps），但 native 的 route final 最终反超为 +0.116ns；诊断口径的崩塌则发生在 **place 阶段**（`ext_mem_clk` 域 frame FIFO 写路径被放崩）。after 诊断跑了两次，数字逐位一致，不是抖动。
8. **四套隔离目录的源码/约束/工程参数哈希比对**证明：before 与 after 的唯一差异是 `src/SD/fat32_media_loader.v`；`constraints/timing.sdc`、`constraints/pin.adc`、`prj/VinylFPGA.al`（含 `<map_mode>area_prior</map_mode>`）四套两两完全相同。因此两口径的差异**不是** RTL 或约束文件不同造成的；但**有效 gate `map_mode` 不同**（MCP 单 run 实测 `auto`，native 显式 `area_prior`，第 2.2/7.3 节）是已确证的流程差异 —— 不能因为 `.al` 里写着 `area_prior` 就认为"两口径参数相同"。
9. **争取目标未全部达到**：native after Slice `8588`（87.63%，目标 ≤85% 即 ≤8330）、PLB `2422`（目标 ≤2400）、Setup `+0.116ns`（目标 ≥+0.2ns）、Hold `+0.030ns`（目标 ≥+0.05ns）四项均未达争取值。**PLB `2422/2450 = 98.86%` 是本工程真正的紧约束**。
10. **`sector_buffer` 不能用声明位数计资源**：RTL 声明 `reg [7:0] sector_buffer [0:511]`（512×8=4096 bit），本轮 TD routed 会话 `get_cells "*sector_buffer*"` 只返回 **125 个 cell**（位级展平，索引散布在 1~4095 之间），且 `#bram` 不变、`#DRAMHARDCON=0`。该计数依赖 netlist/流程，只能作为"实际结构远小于声明"的证据，不能反推精确面积。

## 2. 两套口径：本次复核最重要的前提

### 2.1 定义

| 口径 | 生成方式 | 用户定位 |
| --- | --- | --- |
| **native 正式签核口径** | 隔离工程 + `import_device eagle_s20.db -package EG4S20BG256` + `open_project -single_run` + `elaborate -top top` + `read_adc` + `read_sdc` + `optimize_rtl` + `set_param gate map_mode area_prior` + `optimize_gate` + `legalize_phy_inst` + `read_sdc`（gate 后重载，方案要求） + `set_param place seed 5` + `place` + `route` + `fix_hold` + `update_timing -mode final` + `report_*` + `check_timing` | **唯一签核口径** |
| **SynthPilot 默认单 run 诊断口径** | SynthPilot MCP 的 `td_build` 默认参数 build（同 `.al`、同约束文件，但**有效 gate `map_mode` 实测为 `auto`**，place/route 用工具默认值；见 2.2 / 7.3 节） | **仅诊断**，不作为签核 |

### 2.2 已复核的等价前提（哈希比对）

对四套隔离目录 `vinylfpga_sp_diag_before_v3`、`vinylfpga_sp_diag_after_v2`、`vinylfpga_optE_20261011b\before`、`vinylfpga_optE_20261011b\after` 做比对：

| 比对项 | 结果 |
| --- | --- |
| `src/**`（122 个文件）before vs after | **只差 `src/SD/fat32_media_loader.v` 一个文件** |
| healthy before 的 `src/**`（诊断 vs native 隔离） | **完全一致** |
| `constraints/timing.sdc` | 四套目录两两相同 |
| `constraints/pin.adc` | 四套目录两两相同 |
| `prj/VinylFPGA.al`（含 `<map_mode>area_prior</map_mode>`） | 四套目录两两相同 |
| `fat32_media_loader.v` SHA-256 | before = `903C2B76…CAD78`（E 之前）；after = `4EAF7C07…92AF`（E 之后） |

**结论：两个口径的差异不来自 RTL 集合、约束文件或 `.al` 工程文件本身，而来自流程参数。** 其中**已确证的一条是有效 gate `map_mode`**：SynthPilot 单 run 实测为 `auto`（`reports\c729450071155f24\review_gate_param.txt`），native 显式执行 `set_param gate map_mode area_prior`。`.al` 里虽然写着 `area_prior`，但工程自己的说明（`doc/实施方案_20261009/01_…`：*"不能认为 `.al` 写 area_prior 就实际生效"*）已指出 MCP single-run 不会自动采用它。gate 计数器给出独立佐证：同一份 before RTL，诊断 gate `#MACROs` 460 / `#slices` 2718，native gate `#MACROs` 266 / `#slices` 1560，两者 netlist 结构不同。此外 native 额外的 `set_param place seed 5` 与重复 `place/route` 也是流程差异来源。

| --- | --- | --- | --- | --- |
| route #slices | 8518 (86.92%) | 8588 (87.63%) | 9444 (96.37%) | 9420 (96.12%) |
| gate #luts | 12078 | 12031 | 11293 | 11324 |

### 2.4 使用规则（后续所有比较必须遵守）

1. 同一个候选的 before/after，必须在**同一个口径**内比较，且只改一个 RTL 文件（用哈希证明）。
2. 签核只引用 native `route + fix_hold + update_timing -mode final` 的 `final.qor` / `route.status` / `final_verbose.area` / `final.timing` / `final.constraints`。
3. 诊断口径的数字只能用于"路径定位、结构分析、方向性判断"，不能写进签核结论。
4. gate / place / route 任一阶段的数字都不能替代 native route + fix_hold + final。

### 4.2 等价性证明（逐拍）

记号：LD_DATA 阶段已消费的数据字节数为 `N`（只统计进入 LD_DATA 之后的字节），`P = expected_pixel_count`，`r = rgb_byte_cnt`。

1. `pixel_count` 在进入 LD_DATA 前被清零（`746-751` 接受加载请求时 `pixel_count <= 32'd0`，`709` 复位段同样清零）；在 LD_DATA 之外没有任何赋值点（全文件仅 `709/749/843` 三处）。
2. `pixel_count` 只在 `rgb_byte_cnt==2` 分支自增（`839-843`），即每消费 3 字节加一。因此 `pixel_count = floor(N/3)`，恒等式。
3. 原守卫：`pixel_byte_cnt < pixel_end`。`pixel_byte_cnt` 在头部完成时装载为 `data_offset`（原 `807` 行），随后每字节 +1，故 `pixel_byte_cnt = data_offset + N`；`pixel_end = data_offset + 3P`（`805` 行 `pixel_end <= data_offset + required_pixel_bytes`，而 `756-757` 行 `required_pixel_bytes_q <= ((W*H)<<1) + (W*H)`，即 `required_pixel_bytes = 3*W*H = 3P`）。于是原守卫等价于 `N < 3P`。
4. 新守卫：`floor(N/3) < P`。对非负整数 `N`、`P`，`N < 3P ⟺ floor(N/3) < P`（两边都是"N 落在第 P 个三元组之前"的同一判定）。
5. 因此在 `3P < 2^32` 且 `data_offset + N < 2^32` 的（唯一可实现的）区间内，两者**逐拍取值相同**；`pixel_count` 的自增时序、`bmp_data_wr_en` 的产生时序、`load_state` 的离开时刻均未变化。

关于 32 位回绕的严格说明：`pixel_end = data_offset + required_pixel_bytes` 与 `pixel_byte_cnt = data_offset + N` 都在 32 位加法下取模。只有当声明像素数 `P >= ceil(2^32/3) ≈ 1.43e9` 时 `3P` 才回绕；`W`/`H` 都是 16 位，最大 `P = 65535² = 4294836225`，其 `3P mod 2^32` 会回绕。在这种刻意构造的声明下，新旧守卫的取值可以不同：原守卫语义为 `(data_offset+N) mod 2^32 < (data_offset+3P) mod 2^32`，此时既不单调也不代表"未消费完"，本身就是无意义行为（源码注释亦把它记为"原有的 modulo-2^32 回绕"）；新守卫在该情形下会拒绝继续消费数据，最终走 `ERR_TRUNCATED`。结论：

- 对所有可实现的正经 BMP（`3P` 不回绕）：**逐拍严格等价**。
- 对 `3P` 回绕的病态声明：旧行为无意义（不会产生正确图像），新行为退化为截断报错；可观察差异仅存在于"声明超过 14.3 亿像素且文件真提供那么多数据"这一不可能场景。此点显式登记，不作为"无条件等价"宣称。

补充：

- 当 `P = 0`（宽或高为 0）：原守卫 `N<0` 恒假、新守卫 `0<0` 恒假；完整性判定 `pixel_count >= expected_pixel_count`（`852-853`）在两种写法下都是 `0>=0` 成立，行为一致。
- 溢出面：新守卫只比较 `pixel_count` 与 `expected_pixel_count`，两者都 `< 2^32`，**不再涉及 `3P` 的加法与 `data_offset + N` 的加法**，因此回绕面比原实现更小（原实现的回绕问题已在 4.2 节登记）。

### 4.3 `required_pixel_bytes` 与 `expected_pixel_count` 的关系（守护边界）

### 7.3 归因（分段定位 + 哈希证据）

1. **诊断流程内部，gate 阶段 after 更好**：Setup +115ps → +210ps，寄存器 10463 → 10418（`gate.qor`）。就诊断口径自身而言，崩坏不是综合造成的。
2. **崩坏发生在放置**：诊断 before 的 `place.qor` 是 Setup +2682ps/0 EP，after 是 Setup −5350ps/16 EP；此后 `route` 无法挽回。
3. **不是约束文件或 `.al` 差异**：四套隔离目录的 `timing.sdc`、`pin.adc`、`VinylFPGA.al` 哈希两两相同（第 2.2 节）。
4. **但两口径的有效 gate `map_mode` 不同（已确证）**：诊断流程实测 `map_mode=auto`、`pack_effort=medium`（`review_gate_param.txt`），native 显式 `area_prior`。佐证：同一份 before RTL，诊断 gate `#MACROs` 460 / `#luts` 11293 / `#slices` 2718，native gate `#MACROs` 266 / `#luts` 12078 / `#slices` 1560 —— netlist 结构不同。因此"两口径只差一个 place seed"的说法不准确。
5. **两口径在 gate 阶段方向相反**：诊断 gate after 更好，而 native gate after 更差（−34ps/8EP → −369ps/9EP），却在 native route final 反超为 +0.116ns。所以本文不笼统断言"gate after 都更好"或"差异只在 place"；两口径从 gate 起就是两条不同的实现路径，各自内部才可比较。
6. **不是抖动**：after 诊断跑了两次（v2/v2b），`route.qor` 逐位一致。
7. **背景**：诊断口径把器件放到 96% slice（native 只有 87%），place 阶段 Hold 违例 12 → 28，处于"高占用、对布局极敏感"的状态；微小的网表扰动即可把它推入坏的局部最优。native 流程用 `area_prior` + `set_param place seed 5` 并重复 `place/route`，落点是 87% slice、无拥塞溢出。

### 7.4 处置规则（建议）

- 如果项目的**发布/放行**实际上以 SynthPilot 默认单 run 的 `route.qor` 为准（例如"我们的验收脚本就是跑这个"），那么：**应回退候选 E**，因为它在该流程下把 Setup 从 +0.221ns 打到 −3.557ns。
- 如果 native `area_prior + seed5 + fix_hold + final` 是唯一签核口径（方案与用户在本轮任务中的表述），那么：**保留 E**，但必须在项目记录里保留本节的回归说明，并明确"默认诊断口径的 route 数字不作为放行依据"。
- 无论哪种选择，都不要把两种口径的 Slice/PLB/LUT/Setup/Hold 数字混在同一张对比表里。
- **流程提示（已确证）**：MCP 单 run 的有效 gate `map_mode` 是 `auto`，`.al` 里的 `area_prior` 不会自动生效（工程自己的 `01_…` 文档已警告过）。因此"用 MCP 单 run 的数字代表 native 收益"在本工程已被实测证伪 —— 这也正是 00/01 文档要求"统一比较配置＝原生 TD area_prior"的原因。后续候选（D 等）若要比较收益，必须一律走 native 口径。

## 8. `u_volume_scanner.sector_buffer` 复核（512×8 vs 125 cell）

RTL（`src/SD/fat32_volume_scanner.v:70`）：

```verilog
reg [7:0] sector_buffer [0:511];    // 声明 512 × 8 = 4096 bit
```

使用点（节选）：

```verilog
 103: le16 = {sector_buffer[offset+1], sector_buffer[offset]};
 110: le32 = {sector_buffer[offset+3], sector_buffer[offset+2],
              sector_buffer[offset+1], sector_buffer[offset]};
 206: sector_buffer[sector_byte_index] <= sector_byte;
 320-328/343-365: 只读固定偏移（0、11、13、16、450、510、511 …）
```

本轮实测（SynthPilot TD routed 会话，`get_cells "*sector_buffer*"`）：

```
get_cells num[125]
  sd_card_bmp_m0/fat32_media_loader_m0/u_volume_scanner/sector_buffer_reg[1]_syn_4
  … sector_buffer_reg[432]_syn_3、[3712]_syn_4、[4095]_syn_4 …
```

结论：

1. **不能按 4096 bit 计资源**。综合后只保留 **125 个位级 cell**（索引散布在 1~4095 的稀疏集合上），说明大量位被判定为"不必要"或被吸收进组合逻辑（`le32/le16` 的固定偏移读取会被展开成常量索引，只有确实需要保存的位才落成寄存器/单元）。
2. `#bram` 在两个口径的前后都是 47、`#DRAMHARDCON = 0`，说明 `sector_buffer` **没有**被推断成 BRAM/DRAM 硬块，也没有因为改动而增删硬块。层级表里 `u_volume_scanner` 的 `bram` 列是 0。
3. 该 125 是**本次 netlist/流程下的可复核实测值**，随综合流程/优化强度会变；不能用它反推"精确省了多少 LUT"。前一版交接里出现的 `118 cell` 与本次不一致，**以本次 125 为准并标注其依赖性**。
4. 该会话中还能查到 17 个 `pixel_byte_cnt` cell，说明该 TD 会话的 netlist 是 **E 之前**的（默认诊断旧网表），**不能**用它来证明 E 之后的内部结构；E after 的结构证据只认 native v4 的 `final.area` / `final.timing`。

### 11.2 边界判定

1. **无 IO delay 是"已知缺口"，不是"已经满足"**：33 个输入 / 38 个输出端口缺 input/output delay 意味着这些端口的板级建立/保持时间没有进入 STA。工程当前位置是"按方案要求不凭空补 0 或名义延迟"。要闭环，必须先拿到板级参数（SD 卡侧 setup/hold、HDMI 前向时钟/数据的走线与时序预算、以及显示屏/接收端），**本轮不虚构板级延迟**。
2. **PLL local feedback 是真实的补偿不确定性**：两条 CRITICAL-WARNING 说明两个 PLL 的反馈路径走局部网络，补偿延迟不可预测。它影响的是 PLL 输出时钟相对参考的相位精度，不是 fabric 内部路径；当前做法（用 `set_clock_groups -asynchronous` 把各派生域分组、同源 `video_clk`/`hdmi_5x_clk` 保留同步分析）是**保守且可接受**的，不应为了让数字好看而额外加宽泛 `false_path`/`multicycle`。
3. **不允许用约束掩盖真实路径**：本轮未新增任何 `false_path`/`multicycle`；`media_err_code → wav remaining` 这类跨域路径在诊断口径下出现 −1.123ns，应按"跨域握手/同步器结构是否合理"去查，而不是靠分组消掉。
4. **SDRAM 位置未 honored** 与 `PHY-5079` 时钟局部走线是既有的物理实现提示，与本轮改动无关，但后续若出现 SDRAM 读写异常，应优先复查这两条。
5. **不要为了让 WNS 变好看而动 SDC**：本域的 slack 由互连决定（第 6.4 节），放宽约束只会掩盖问题；放宽 HD SM `set_max_delay` 或给 sd_card 域加 clock group 都属于"改指标不改设计"。

## 13. 唯一推荐的第一项实现

### 13.1 本轮选定的第一项：候选 E（已实施、已提交）

选它的理由，按权重排序：

1. **失败机制被实测锁定**：native 的 2 条（乃至 9 条）sd_card_clk setup 违例全部来自同一个扇出源 `pixel_byte_cnt`（扇出 36、net 占 73%），属于典型的"单点宽网"问题。这类问题改 RTL 结构即可解决，不需要动约束、不需要新增流水。
2. **等价性可证明、可仿真**：守卫替换是逐拍恒等（第 4 章），不引入新寄存器、不改变启动/Seek/暂停延迟；7 项定向 + 2 项边界 + 53 项回归的失败集合零变化。
3. **资源方向可接受**：native 口径 LUT −97、reg −58、PLB −3、布线 −45k；唯一"变差"的是 Slice +70 / LE +120（<1%）。
4. **硬门槛通过**：native 正式签核 Setup WNS +0.116ns / 0 EP、Hold WNS +0.030ns / 0 EP、资源不超限。
5. **风险可闭环**：单文件、单提交、可 `git revert`；与用户未提交的 D11/D12 改动完全不重叠。

### 13.2 为什么不选其它候选作为"第一项"

- **A**：已实测失败（native −0.519ns / 18 EP，LUT +234），已回退，不能重选。
- **B/C**：寄存器成本高、语义风险高（快速切歌窗口、INDEX v1/v2/CRC/0 长度/非法簇/回退），在没有"结构证据"的前提下不适合作为第一刀；只读复核已把它们的族定为"次关键"。
- **D**：证据充分但有真实语义风险（末簇收敛、快速切歌），更适合作为**第二项**；而且 E 之后它的目标是"留 margin"而非"清违例"。
- **F/G**：只有网表/STA 线索，缺候选级综合与（G 还缺）信号级证据；直接实施容易白改。

### 13.3 如果数据不足，缺少哪些报告

本项（E）的门槛判定**没有缺口**：native before/after + 复现轮 + 双口径诊断 + 7/53/2 仿真都已齐备。

缺口在**下一项**：

1. post-E netlist 上 sd_card_clk 域的**信号级交叉探针**（用来确认族 A 的起点是不是 `blue_adj`，以及族 A 是否真的是 `mv_metadata_sd` 打包路径）。
2. 候选 D/G 的**候选级综合**（opt_gate/place/route 的 QoR + area，随 native 流程）。
3. `report_analysis -mode basic`（关键路径）与 `report_hfn`（高扇出网，`-mode gate|place|route`）在 E 之后的**完整输出**（目前只有 STA 路径文本 + 网表 fanout 观察）。
4. 板级 IO 参数（SD 卡侧、HDMI 前向）与接收端规格，用于把 33/38 个无延迟端口闭环。
5. D13/F2 的独立综合（若确实要评估）。

### 15.1 下一项：候选 D（`u_file_streamer` / `max_cluster` 簇范围判定）
