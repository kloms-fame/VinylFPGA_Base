## 3. 资源与时序：务必分清两套口径

### 3.1 唯一"布线后签核"数字（native area_prior + seed5 + fix_hold + final）
| 指标 | O0 基线 | O4 候选 | 器件容量/红线 |
|---|---:|---:|---|
| LUT | **13,734（70.07%）** | 13,604（gate） | 19,600；规划目标 ≤15,500 |
| Slice | **7,541（76.95%）** | **7,510** | 9,800；85%=8,330，90%=8,820 停加 |
| **PLB** | **2,360/2,450 = 96.33%** | — | **最紧的约束，不是 LUT** |
| BRAM9K | 42/64 | 42 | 规划上限 52 |
| DSP | 15/29 | **13** | 上限 20 |
| setup/hold WNS | **+121ps / +24ps**，违例 0 | +182ps / +21ps | 期望 ≥+200ps/+50ps（尚未达） |

> 同一份源码走 SynthPilot 默认 AUTO，final Slice 就变 86.19%、PLB 98.12%（比 area_prior 多 1,334 LUT/906 Slice）。**策略/打包影响极大，D 系列必须用同一 native area_prior 口径才能比收益。**

### 3.2 D 系列数字全是 SynthPilot **opt_gate（布局布线前）估算**，不能与上表 final 相减
| 阶段 | gate LUT（%） | BRAM/DSP | gate setup WNS / 违例端 |
|---|---:|---|---|
| D1 r5 | 14,150（72.2） | 42/13 | +207ps / 0 |
| D3 | 14,440（73.7） | 42/13 | **−281ps / 4** |
| D4–6 | 14,949（76.3） | 43/10 | +188ps / 0 |
| D7 | 15,307（78.1） | 43/10 | **−297ps / 7** |
| D8 | 15,379（78.5） | 43/10 | **−297ps / 2** |
| D9 | 14,866 | 42/10 | +123ps / 0 |
| D10 | 16,123（≈82） | 42/10 | **−297ps / 6** |
| D11/12（空歌词） | 15,921（81.2） | 42/10 | +148ps / 0 |

- gate 估算**各次独立快照间会跳动、非单调**（如 D9 低于 D8），属正常，**不代表布线后结果**。
- 反复出现的负 slack 最差路径都在**既有外存帧 FIFO 写读握手 / SD 卷扫描 / 歌曲索引校验**，**不经过新增 UI 模块**；但这说明时序余量已被既有链路吃紧，UI 改动会间接影响它。
- **从 D1 到现在没有任何一版做过 place/route/fix_hold/bit，也没有板级签核**；当前不存在"含 D1–D12 的签核固件"。

### 3.3 真实歌词会再推高 BRAM
本轮已用 48 行/178 字形重新生成字库：512×16 → **4096×16（约 8 块 BRAM9K）**，预计 **BRAM 42 → 约 49**（距规划上限 52 仅余 3）。LUT/DSP 不随字数线性增，**BRAM 才是歌词扩容的瓶颈**；精简用词、四曲复用字眼可省。

## 5. 发现的关键问题与风险（按优先级）

1. **工作区有一套"在途、未提交、未验证"的时序/资源优化重构（6 个 RTL，+187/−118），你即将出的 bit 会包含它：**
   - `song_index_db.v`：把 `entry_sel` 动态索引写/整字移位，改成 `case(entry_sel)` 显式写 + 小端按字节落位（消除宽读选择器，正对 D8 报告里歌曲索引 −57ps 路径）。
   - 歌词链（`lrc_window_controller / lrc_five_osd / lrc_scroll_controller / playback_page / top`）：六个**具名行寄存器**替代可变部分选择移位；行槽用 `y+offset` 的相位（phase 0/3/6/9/12/15）直接译码；高亮按几何位置推导。**删掉了 row_valid(6b)/row_indices(42b)/highlight_index 总线和有符号距离运算**，明显省 LUT/timing。
   - 我已核对：src 内**无悬空残留引用，可综合**；`highlight_index` 现为滚动控制器"输出但无人消费"（top 仍连线，预计一条未用警告）。
   - **但它未提交、未综合、无指标，且没有任何配套仿真**。按 `00_门禁` 这不能直接进 bit。
2. **D10–D12 整条歌词/播放页链没有定向 testbench**：`sim/` 下只有 D9 时代的 `tb_lrc_font_sync/tb_lrc_osd_equiv`，没有计划要求的 tb_lrc_window/five_osd/scroll/playback_page/song_text。你之前实拍的"文字横条"正是这类仿真本可拦住的 bug；当前链路靠 gate 综合+肉眼验收，风险偏高。
3. **PLB 96.33% 是第一红线**，且时序对策略/布局极敏感；D 系列 gate LUT 已到 ~81%、反复在既有 FIFO 路径报负裕量。**在没有一次 native area_prior 完整 route 之前，无法判断 D1–D12 整体是否还能稳定布线。**
4. **O1 时钟/CDC/约束专项未关闭**：2 条 PLL local feedback（USR-6135）、33 个 input/38 个 output 无 delay 仍只是记录；"0 违例"仅在现有约束覆盖内成立。
5. **D0 素材合同未满足**：四曲共用同一 AUDIO.PCM（约 4:05），不能作为"多曲独立曲目"验收证据；专辑名（album）字段当前不支持；进度条满幅约 232/240（右端留 8px）尚未拍板。
6. 真实歌词时间戳是"每 3 秒"演示节奏，非真实歌曲节拍；歌词/标题/歌手**编译进 bit 而非放 SD**。

## 6. 建议的下一步（顺序很重要）

1. **先处置在途重构**：确认其来源 → 补 window/five/scroll/playback/song_index 的定向仿真并跑全回归 → 用 native area_prior/seed5/fix_hold 完整 route，确认 setup/hold ≥0、overflow 0、PLB 不恶化 → 再单独提交。不要把它和真实歌词 ROM 混在一个无验证候选里。
2. **出第一个"D1–D12 全集签核 bit"**：含真实歌词，完整 route 后记录 LUT/Slice/**PLB**/BRAM(预计~49)/DSP/WNS，再按已交付的各阶段走查一次性板验（轮播/音量/亮度对比度/浮窗/ROT/WSL/播放页/五行滚动/Seek/切曲/MV/波形）。
3. 板验通过、余量允许再进 **D13（真实缩放，最难，先做吞吐/扇区准入预算）→ D14（波形极值，小改）→ D15（终验+Flash）**。
4. 若 PLB≥98% 或 route 出现稳定负 slack：**停止叠加 D13**，先回到既有 FIFO/索引路径做时序优化（在途重构正是这个方向，应先把它验证固化）。
5. 准备 D0 真实素材：4 个独立 PCM/标题/歌手/歌词；是否新增"专辑名"字段需你确认（要改生成器+播放页+布局）。

## 7. 一句话结论
主链成熟、计划严谨、O 系列优化合规收口；**D1–D12 功能代码已齐但全部停在"综合通过"，没有布线后签核、没有板验，歌词链缺仿真**；当前最该做的不是继续加 D13，而是**先把工作区里那套未提交的时序优化重构验证固化，再出一个完整布线的全集 bit 做一次整体人工验收**。
