### 5.1 最差 Setup 路径：SD 音频条目选择

| 最大扇出 | 33 |

相应 RTL 位于 `src/SD/fat32_media_loader.v`：

- 186–195 行：按 `song_sel` 从四首曲目的 64-bit 音频元数据中选择一首；
- 196–197 行：对选中的文件大小做 32-bit 非零判断，并检查簇号是否至少为 2；
- 361–370 行：索引完成/切歌时，条件选择后计算 `idx_aud_cluster - 2` 并锁存。

路线上的多个 LUT 与长网络符合“宽字段选择 + 有效性控制 + 地址偏移/条件锁存”可能串接的形态。具体优化必须由 Astra 对当前综合网表与 RTL 进一步确认，不能仅凭源码推断每个 LUT 的唯一逻辑功能。

**适合优先做的候选实验：**

1. 检查四路 64-bit 元数据 mux 是否可以只在实际需要时选择字段，避免未选中的 size/cluster 位参与后续控制；比较“先选字段再判有效”与“每曲预先形成窄有效标志再选”的综合结果。
2. 评估把选中歌曲的原始 cluster/size 先锁存、随后再做有效性与 `cluster−2` 归一化，增加最多一拍装载延迟以换取短路径。音频启动前有等待窗口，但必须验证 `song_sel_changed`、快速切歌和 `idx_done` 同拍条件下不会接受旧曲数据。
3. 评估在 INDEX 解析阶段形成逐曲 `audio_valid`/归一化 cluster，使播放启动路径只跨越窄控制位或较短数据路径。要保留 v1/v2 INDEX、CRC、缺字段、size=0、cluster<2 和扫描回退语义；比较新增寄存器是否抵消 Slice/PLB 收益。
4. 每个候选只改一类逻辑，比较同一约束下的 route WNS、PLB、Slice、LUT、BRAM 与路径扇出。Setup 目标至少保持 ≥0，争取 ≥+0.2 ns；不能通过放宽时钟或添加不正确的 false/multicycle path 报出“改善”。

### 5.3 Hold 和正式放行

- route Setup：WNS +0.221 ns，TNS 0，Setup 违例端点 0。
- route Hold：WNS −0.004 ns，TNS −0.008 ns，Hold 违例端点 2。
- 两个负 Hold 端点位于 HDMI 音频 packet FIFO 的嵌入式 RAM 地址端 `addra[11]` 与 `addrb[6]`；最差数据路径只有 0.341 ns，约 69% 是网络延迟，路径经过 `video_clk` 域的 `u_logic_ramfifo`。
- place 阶段单独的 Hold 统计明显更差，route 后大部分被物理布线修复；仍剩 −4 ps，属于需要正式物理签核处理的极短路径。

建议由 Astra/TD 流程拥有者先确认方案要求的 native `fix_hold`、多 seed 与 final 流程能否修复这两个端点，并保存最终 route 证据。不要先改 HDMI 厂商生成 RTL，也不要人为加 false path 掩盖它。只有最终 native Hold WNS≥0 才满足已确认的硬门槛。

### 5.4 SDC 健康度与覆盖边界

本轮 `td_check_timing`：无无时钟寄存器、无组合环、无无效约束、无悬空约束、无部分/异常 IO delay；两颗 PLL 都有输出时钟约束。但仍报告：

- 33 个输入没有 input delay；
- 38 个输出没有 output delay；

### 6.1 两个“看起来很大但收益可能很小”的对象

**FAT32 sector buffer。** RTL 声明 `sector_buffer[0:511]`，从源码看像 512×8 bit；但当前 TD `get_cells` 按 `sector_buffer_reg` 检索只返回 **125 个实例**，综合已裁掉大部分不可观察位。因此直接把完整数组改成 30 个字段寄存器不应预估节省 4,096 个触发器。仍可分析它对根簇 Setup 路径和写地址译码的影响，但应按实测门级差值评估。

**Boot Logo 色深。** 当前 ROM 使用 4-bit 调色板，源 ROM 实际 0–F 共 16 个索引都出现；按 3-bit 或 2-bit 色深压缩一定会改变显示。黑色背景索引 F 虽有 7,887 个样本，但要在任意像素地址下跳过背景，需增加 mask/压缩地址组织；理论 BRAM 收益可能只有约 1 个左右，且有额外地址和选择逻辑，暂不列为首选。原始像素数据共 79,864 bit，约 79.9 kbit（78.0 Kibit）。

### 6.2 歌词方案 C 与 D13 的资源含义

- 当前 `song_font_rom` 4096×16 bit，若按 BRAM9K 容量粗估约 8 块；方案 C 的 192 个字形子集约 192×16×16=49,152 bit，字形区约 6 块，再加行记录/元数据约 1–2 块。
- 因此 F2 主要解决换歌不重烧和素材维护问题，预计 BRAM 净变化接近 0（大约 −1 到 +1 的估算区间）；另外会增加装载器和跨域控制，不能把它当作确定的 Slice/PLB 减负。
- D13 方案估算约 +300 Slice、+3 BRAM。当前 BRAM 还剩 17 块，但 Slice 仅余 356、PLB 仅余 7；因此 D13 必须等逻辑空间先腾出，并重新 route。
