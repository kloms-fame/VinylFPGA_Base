## 3. 最重要的一条前提：两套口径不能混用

本工程同时存在两套流程，数字差异巨大，**混用会直接得出相反结论**：

| 口径 | 流程 | 用途 | 现基线数字 |
| --- | --- | --- | --- |
| **native 正式签核** | TD 命令行：`import_device` → `open_project -single_run` → `elaborate` → `read_adc` → `read_sdc` → `optimize_rtl` → `set_param gate map_mode area_prior` → `optimize_gate` → `legalize_phy_inst` → `read_sdc`（重载）→ `set_param place seed 5` → `place` → `route` → `fix_hold` → `update_timing -mode final` | **唯一放行门槛** | Setup +0.116ns / 0 EP，Hold +0.030ns / 0 EP，Slice 8588，LUT 15683，PLB 2422 |
| **SynthPilot 默认单 run 诊断** | SynthPilot MCP 驱动 TD 单 run（默认参数、默认 seed、无 area_prior、无 fix_hold） | 仅作快速诊断/相对归因 | Setup +0.221ns / Hold −4ps + 2 EP，Slice 9444，PLB 2443，LUT 17088 |

**用户之前引用的"Slice 9444/9800、PLB 2443/2450、MSlice 4721、LSlice 4723、LUT 17088、route Setup +0.221ns、Hold −0.004ns/2 端点"= 诊断口径、候选 E 之前**，不是签核口径。

**已实测的流程敏感性（关键）**：候选 E 这个同一份 RTL，在 native 口径下把 Setup 从 −0.127ns 提到 **+0.116ns**（2 → 0 违例），在诊断口径下却把 Setup 从 +0.221ns 打到 **−3.557ns**（46 违例）。这是**流程参数敏感性**，不是 RTL 对错。处理原则：**以 native 为准 + 显式披露诊断回归**。

**纪律**：不得用 `opt_gate` 或 `place` 的数字替代 `route`（第 5 章的候选 F 就是最好的反例：place 阶段数字最漂亮，route 直接失败）。

## 5. 我发现了什么

### 5.1 有直接证据的结论（可直接复核）

1. **PLB 是最紧的资源**（2422/2450 = 98.86%），比 Slice（87.63%）更紧。任何寄存器复制类方案都会撞 PLB。
2. **`pixel_byte_cnt` 是 native 违例的单点根源**：before 的 2 条 sd_card_clk setup 违例同源，扇出 36、net 占 73%。E 改掉它后违例 2 → 0。
3. **critcial path 的 slack 由互连决定，不由逻辑决定**：E native 最差路径 Data Path 9.604ns 中 cell 只占 31%、net 占 69%；D 的 9.588ns 里 net 占 84%。这意味着"减逻辑"的空间上限被互连压住。
4. **设计里的超宽网全是复位**（route 阶段 fanout 直方图：`u_exp_reset/s2` 753、`u_video_reset/s2` 668、`u_media_video_reset/s2` 460、`u_sdcard_reset/s2` 412），且工具已经复制过（`dup_*`/`s2`）。sd_card 域内最宽的网是 `u_song_index_db/chk_ok_reg_syn_dup_130`(239)、`media_status[22]_dup_1`(225)、`u_volume_scanner/sectors_per_cluster_shift_b[1]_syn_dup_7`(153)，也都已复制。
5. **关键路径上的"扇出 50/36/33"不是最宽的网**：所以该域瓶颈是"长互连 + 中高扇出 + 深逻辑"的叠加，而不是某一条超宽网。靠"治一条宽网"解决不了。
6. **place 阶段 QoR 不能预测 route**：候选 F 的 place 数字三项里最好（Slice 8461 最低、Setup +2856ps），route 却失败。**这是"不得用 gate/place 替代 route"的实测铁证。**
7. **`sector_buffer` 的 512×8 声明不能当资源算**：读侧**只有常量偏移**（字面量 0/13/16/450/510/511，加 `le16/le32` 的常量偏移 11/14/17/22/32/36/44/454），**没有任何变量索引读**；TD 只保下 **125 个位级 cell**。按 4096 bit 估资源会严重高估。（另：`#bram` 前后均 47、`#DRAMHARDCON = 0`，该数组没被推断成 BRAM。）
8. **cell count ≠ 面积**：用户引用的 `sd_card_bmp_m0(2590)`、`u_expansion_integration(1120)`、HDMI(997)、`u_playback_page(594)`、`u_song_index_db(563)` 是**实例个数**；对应 native after 的 `le/lut` 分别是 4275/3772、1908/1588、1766/1431、916/881、1020/944。决定放不放得下的是 Slice/MSlice/LSlice/PLB 与 LUT/reg。
9. **字库与 Logo 的真实成本**：`u_shared_song_font`（= `song_font_rom`）le 629 / lut 629 / bram 8，是"五行歌词"的核心资产；开机 Logo `u_boot_layer` le 158 / lut 118 / bram 10，成本很小。**两者都不该作为"降资源"的目标**（缩小字模/减色 = 砍功能或降质量）。
10. **SDC 现状是"已知缺口"而非"已满足"**：`check_timing` 报 33 个输入端口无 input delay、38 个输出端口无 output delay；两个 PLL 的反馈路径走局部网络（`USR-6135 CRITICAL-WARNING`，补偿延迟不可预测）。工程当前策略是"不凭空补 0 或名义延迟"，要闭环必须先拿板级参数。
11. **用户给出的"最差路径"是诊断口径、E 之前的**：`u_song_index_db/e_aud_by_reg[85] → audio_cluster_m2_d_reg[13]`，9.499ns、cell 28% / net 72%、7 级、扇出 33，逐字命中 `vinylfpga_sp_diag_before_v3` 的报告（Slack +0.221ns）。**它在 native before 里不存在**。
12. **E 之后 native 的最差路径是"元数据 → CDC 影子锁存"族**：`u_brightness_contrast_steps/blue_adj[5] → u_mv_metadata_cdc/src_data_latched_reg[4].b[0]`，+0.116ns、9.604ns、7 级、扇出 50；net 链可定位到 `u_song_index_db`（`song_mv0_b_n1`）→ `cdc_bundle_latest.v(12/18)`。

## 6. 当前问题

### 6.1 硬问题（阻塞签核之外的"更好"）

1. **PLB 98.86% 几乎没有余量**。这是全局最紧的资源，决定了"不能靠新增寄存器组来换时序"。

## 13. 术语与口径速查

| 术语 | 含义 |
| --- | --- |
| native 口径 | TD 命令行正式流程（`area_prior + seed5 + fix_hold + final`），**唯一放行门槛** |
| 诊断口径 | SynthPilot 默认单 run，快速但不作门槛 |

| cell count | 实例个数（含大量 1-bit cell），**不等于面积** |
| WNS / TNS | 最差负 slack / 总负 slack；≥0 表示无违例 |
| S-EP / H-EP | Setup / Hold 违例端点（Endpoint）数 |
| 族 A | "元数据（`u_song_index_db`）→ CDC 影子锁存（`u_mv_metadata_cdc`）"这条路径族，E 之后的最差路径所在族 |
