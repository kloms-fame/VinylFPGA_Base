## 三、参考文件需要修正的判断

1. **背景图片驻留不等于媒体与背景已能同时显示。** 顶层目前让 `frame_read_write` 在封面与 MV 之间选择一个源；`frame_fifo_read` 从一个基地址连续递增，只有一条显示 FIFO。单纯换成背景基地址，会失去当前清晰媒体源。必须补充区域读取或合成。
2. **显示带宽计算要乘帧率。** 640×480 每帧 307,200 个 32 位像素；按 60 帧/秒计算，约 18.432 Mword/s，即 73.728 MB/s，参考文件“每秒 307,200 Words”少了帧率因子。当前实际帧率由视频时序决定。
3. **单物理端口并不自动意味着死锁。** 是否供数不足取决于刷新、突发、FIFO 水位、写入负载和请求安排。当前不推荐直接增加第二条整帧读流，优先研究复用现有读口与 FIFO。
4. **KEY11 的单拍脉冲需要保留请求。** `frame_start && key_pulse` 会漏掉未与帧起点同拍的按键。应同步事件、记录待提交的模式，再在帧边界更新；已有 `s6_video_layer` 的事件保留方式可作为参考。
5. **灰度公式需要连续限幅。** 参考公式在 `vig` 接近底色值时会先减至极暗、随后跳回固定灰值，形成亮度不连续。采用单调、带下限的渐变，必要时使用固定空间抖动减弱色阶。
6. **资源与切换延迟须实测。** “只用 18 LUT”“零开销”“0 ms”均不能作为承诺。未就绪背景有加载延迟；已缓存背景在帧边界提交。
7. **本阶段以当前版坐标为准。** 参考文件中的旧版媒体位置、进度条颜色、40 像素剩余时间区域、波形重排和新播控图标均不属于本阶段背景需求。

## 四、技术路线比较

| 路线 | 优点 | 代价与局限 | 判断 |
|---|---|---|---|
| 全尺寸背景离线生成，SDRAM 缓存，复用现有 FIFO 分区域取像素 | FPGA 不做模糊；图片质量可在电脑预览；保留清晰封面/MV；目标不新增 BRAM、DSP | 需要背景加载、缓存标签及分区域地址/突发安排；读取控制需验证 | 推荐 |
| 小尺寸或压缩背景，显示时放大/解码 | 素材和显存占用小，有机会预缓存更多歌曲背景 | 增加放大/解包逻辑，可能需要行缓存；色阶与精细度需对比 | 满尺寸路线实测不合适时再评估 |
| FPGA 实时从媒体生成模糊背景 | 可跟随动态媒体 | 新增采样、滤波、缓冲与读写安排；当前资源紧张，开发和验证范围大 | 本阶段不采用 |

推荐方案的数据流：

```text
当前歌曲封面 → PC 缩放/柔化/调色 → 歌曲彩色背景素材
通用蓝紫光晕 → PC 生成 → 通用艺术背景素材
              ↓ SD 卡资源包与索引
     低优先级背景加载 → SDRAM 背景缓存
              ↓
背景像素 / 原清晰封面或 MV 像素
              ↓ 按区域安排取数，保持输出像素顺序
        现有显示读 FIFO
              ↓
播放页文字、进度、波形、系统层 → HDMI
```

## 五、显存与读取设计

现有 SDRAM 为 2,097,152 个 32 位 Word；来源为 `EG_PHY_SDRAM_2M_32` primitive 与 21 位地址接口。

| 区域 | 半开地址范围，单位 Word | 用途 |
|---|---|---|
| 四张封面 | [0, 1,228,800) | 原有 640×480 封面 |
| 三帧 MV | [1,228,800, 1,459,200) | 原有 320×240 三缓冲 |
| 彩色背景缓存，拟定 | [1,459,200, 1,766,400) | 当前歌曲一张 640×480 图 |
| 艺术背景缓存，拟定 | [1,766,400, 2,073,600) | 通用一张 640×480 图 |
| 剩余 | [2,073,600, 2,097,152) | 23,552 Words，94,208 Bytes |

两张全尺寸背景合计 2,457,600 Bytes，可放入现有尾部空闲区。四首歌曲的全尺寸背景无法与上述现有数据一起全部常驻，所以必须为当前彩色槽绑定歌曲 ID/代次与有效标记。

读取设计原则：

- 彩色/艺术模式下，媒体窗口内取原封面/MV，窗口外取背景；不重复读取最终被覆盖的背景像素。
- 在复用现有 FIFO 的方案中，每帧显示消费仍是一条按扫描顺序排列的像素流。地址生成要基于取数进度，不能直接拿可能落后于 FIFO 预取的实时屏幕坐标。
- 突发跨越“背景→媒体→背景”边界时，需要安排地址切换、短突发或分段读取；当前固定连续读逻辑无法原样实现此功能。
- 当前 SDRAM 控制器包含加密 IP，实际跳址、忙状态、读回延迟和突发边界需要通过适合的模型与板上观察验证。
- 灰/黑背景由像素坐标或常量生成；媒体画面仍通过原路径显示。完成读取设计后，可评估仅读取媒体窗口以减少这两种模式的显存流量。

## 六、素材、加载与按键

- PC 侧自动从四张现有封面生成四张静态彩色背景，并生成一张通用蓝紫底图；模糊半径、亮度和饱和度在素材预览阶段调整。
- `vinyl_packer.py` 当前仅包含封面/音频/MV 索引，尚无背景生成与背景资源加载契约。必须一起补充资源打包、索引/描述、格式检查和错误回退。
- 具体采用 BMP 文件或背景资源容器，实施设计时以能复用现有 FAT/BMP 流读取、少增加 RTL 为原则选择，并保留旧卡兼容。
- 开发时生成新的测试卡镜像；由用户自行写入测试 TF 卡并烧录 FPGA。完整图片模式需要包含新背景素材。
- 艺术槽加载后常驻；彩色槽按当前歌加载。优先利用浏览停留时间预取，在播放期间继续加载时按扇区安排、优先音频，再保障 MV，背景在剩余带宽下推进。
- 加载未完成时不发布有效标记；等待所有像素写入结束，携带歌曲标签同步到视频域，再允许帧边界显示。
- 切歌、重播、快速操作时，应丢弃旧代次的加载结果，避免把上一首背景显示到新歌。背景异常回到灰底，音频继续。
- KEY11 沿用现有消抖后的按下事件；跨域使用已验证的 toggle/同步方式，保留请求到帧边界。后台加载期间 KEY11 仍按四模式循环，记住用户最终选择。

## 七、资源目标与开发安排

目标：尽量复用现有 BRAM/FIFO、BMP/FAT 读取、SD 扇区仲裁、CDC 和视频寄存级；BRAM9K 保持 47 块、DSP 保持 10 个。新增 LUT/Slice 的预算需在具体模块设计和综合后确认，不能用固定小数字代替测量。

建议分两次可见功能验收：

1. **3A：背景基础与交互。** 做中等灰微渐变、近黑、KEY11 循环请求、开机内模式记忆、KEY7 返回及帧边界提交。图片槽未就绪的模式按定义使用灰底。验收清晰媒体、暂停/继续、切歌、歌词、波形、数字、音频和 HDMI 连续性。
2. **3B：完整四模式。** 做 PC 素材打包、背景缓存加载、分区域显示读取和图片模式；验收四种效果、每首封面衍生背景关联、快速 KEY11、切歌加载回退、MV 与背景共存、缺失/损坏背景回退、长时间音频稳定。

每次沿用：当前 main 上开发 → SynthPilot 分析/综合 → 源码与约束快照 → 后台 TD 实现/bitgen → 提供本轮固件路径与人工教程 → 用户板级确认 → Git 提交 → 下一任务。

阶段三总体通过条件：全屏背景铺满，清晰媒体与现有 UI 正确叠加；缓存就绪后背景在帧边界切换；未就绪或异常时有稳定灰底；KEY11 不再触发返回；KEY7 返回正常；音频与 MV 连续；本轮 routed Setup/Hold WNS 均不小于 0、TNS 为 0，资源仍能容纳后续开发。
