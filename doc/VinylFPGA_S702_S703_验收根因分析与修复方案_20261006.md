## 0. 结论速览（TL;DR）

| # | 验收现象 | 根因分类 | 根因一句话 |
|---|---|---|---|
| R1 | 红外全部无反应但串口有码 | **使用前提 + 可观测性缺陷** | DIP5（红外业务使能）拨在 0，router 门控丢弃所有 IR 命令；echo 打印不经门控所以"有码无动作"。**DIP5 上拨=1 后已验证恢复正常** |
| R2 | 左上角"1E00"被当成故障码 | **OSD 语义误解（不是 bug）** | OSD 左上 4 字符 = `[曲目号][a/e][err高4位][err低4位]`，"1E00"=曲目1+e+err=0，**根本没有错误** |
| R3 | 坏卡显示 1E34，换好卡仍 1E34，软重启才好 | **状态机/sticky + 复位不联动** | scanner 错误码锁存后只有全局 rst 才清；supervisor 只复位 SD 底层，不触发上层重新 scan_start |
| R4 | 播放中拔卡后封面在但音/MV 起不来 | **资源/时序（缺代次重挂）** | 没有 media_epoch/rebuffer 机制，wav/mv 播放器卡在旧 LBA 的完成等待上 |
| R5 | 播放中按两次 KEY07 返回后卡死 | **代码逻辑缺陷（事件双驱动竞态）** | KEY07 同时驱动"退出播放"和"翻转缩略图视图"两条 CDC 路径，时序不对称进入矛盾态 |
| R6 | 缩略图纯黑卡死、不能切不能退 | **状态机与错误码处理** | `key_confirm` 需 `image_complete[焦点]=1` 才生效；拔卡后该位图失效 → 永远退不出 |
| R7 | 播完偶发卡住/不从头播 | **代码逻辑缺陷（EOF 未实现）** | play_ctrl 完全没有 stream_end 输入，结束策略（S7-06）尚未实现；切曲后 SD 断则新曲数据永不到达 |
| R8 | 主界面 ENC1 SW 进缩略图而非播放；切歌慢带渐暗；缺返回键 | **交互设计与用户预期不符** | 这是 S3/S5 既定路由，需按用户新交互重映射 KEY9/11/12，并解耦 KEY07 |

## 1. 验收现象复述与日志证据

### 1.1 日志格式约定（先统一读数口径）

串口每 2 秒一行：

```
[hh:mm:ss] << STAT UR=xxxx BL=xxxx VF=xxxx OV=xxxx ERR=xx VER=07010001
```

| 字段 | 含义 | 本报告关注点 |
|---|---|---|
| `UR` | 音频 underrun 饱和计数（16bit，到 FFFF 停） | 播放中拔卡 → 快速饱和 |
| `BL` | buffer-low 计数 | 低水位次数 |
| `VF` | 视频/MV 取帧失败计数 | 坏卡时 =0001 |
| `OV` | 事件队列溢出计数 | 全程 =0000 |
| `ERR` | health_monitor 锁存的最近非零错误码（sticky） | **= OSD 后两位** |
| `VER` | 固件版本 0701_0001（S7-01 起） | |

关键事件行：`<< INFO DONE=x IDX=x PIC=x AUD=x`、`<< VERIFY IDX=.. FS=.. PRES=x`、`<< ERR xx`、`<< IR XXXXXXXX CMD FF`、`<< DIP INIT xxxxxx`、`<< DIP n x`。

## 2. 源码级根因分析

### 2.1 红外无响应（R1）—— 已证实为 DIP5 门控

**事件链路（自下而上）：**

```
ir_async
  → ir_nec_decoder.v            （解码出 ir_event / ir_code=0xBA45FF00）
  → ui_event_bus.v L165-171     （arbitrate: ev_arg=code[15:0], ev_aux=code[31:16]）
  → expansion_integration.v L256 u_ui_command_router
        ├─ echo 打印路径：ev_valid → exp_echo_reporter（不经门控，所以串口有码）
        └─ 业务路径：cmd_valid/cmd_code → ui_event_bridge
```

**门控点（`src/io/ui_command_router.v`）：**

```verilog
// L99-104 拆包正确：
wire [31:0] full_frame  = {ev_aux, ev_arg};      // = 0xBA45FF00 ✓
wire [7:0]  ir_addr     = full_frame[31:24];     // = 0xBA ✓
wire        ir_frame_ok = (full_frame[23:16]==~ir_addr) && (full_frame[7:0]==~full_frame[15:8]); // ✓

// L199 业务输出门控：
end else if (ir_x_valid && dip_level[4] && (ir_x_evcode != EV_NONE)) begin
              cmd_valid_c = 1'b1; ...
end
```

- `dip_level[4]` = DIP5（红外业务使能，上拨=1，见方案 §2.3）。
- `dip_level[4]=0` 时：IR 帧**仍被解码、仍被 echo 回显**，但 `cmd_valid_c=0`，下游 bridge 收不到任何翻译命令。
- 同文件 L177（息屏）、L204（repeat）、L256（清最近键）全部受 `dip_level[4]` 门控，设计自洽。
- `expansion_integration.v` L2900 附近 `DIP 5 1`/`DIP 5 0` 事件证明 DIP5 物理拨动能被采集；16:51:57 `DIP INIT 000001` 证明复测前 DIP5 确实在 0 位。

**附带缺陷（建议修复）：** DIP5=0 时收到 IR 帧，串口只回显原始帧、不提示"已被屏蔽"，导致验收者误以为解码器坏。建议在 echo 或 router 侧加一行 `IR BLOCKED (DIP5=0)` 或计数。

### 2.2 OSD 错误码语义（R2）—— 解释"1E00/1E01/1E34"

`src/display/status_osd_overlay.v` L91-99：

```verilog
case ((pixel_x - OSD_X) / 8)
  0: char_value = {2'b00, index_q} + 1'b1;   // 当前曲目号（1 基）
  1: char_value = auto_q ? 4'ha : 4'he;     // 'a'=自动轮播, 'e'=手动
  2: char_value = error_q[7:4];             // 错误码高 4 位
  3: char_value = error_q[3:0];             // 错误码低 4 位
endcase
```

左上角 4 个字符是拼出来的：

| 屏幕显示 | char0 | char1 | char2 char3 | 真实含义 |
|---|---|---|---|---|
| `1E00` | `1`（曲目1） | `E`（=e，手动） | `00` | **error=0x00，无错误** |
| `1E01` | `1` | `E` | `01` | error=0x01（supervisor 挂载失败） |
| `1E34` | `1` | `E` | `34` | error=0x34（FAT/索引扫描错） |

> 这解释了"浏览态拔卡显示 1E00 且串口无报错"——它本来就不是错误码。**真正需要关注的只有后两位**。建议下一版把曲目号与错误码在 OSD 上分开位置（例如错误码单独右下角两位，非 0 才亮红），避免再误读。

### 2.3 错误码汇聚与 sticky 缺陷（R3）

**错误码两路来源（`src/top_tf_hdmi_audio.v`）：**

```verilog
// L386-391 fat32_media_loader.v：
assign media_error = !scan_done ? 8'd0 :
                     (scanner_error != 0) ? scanner_error :
                     (idx_started && !idx_valid) ? idx_error :
                     (src_valid == 0) ? 8'h22 : 8'd0;

// L1369 优先级合并：
wire [7:0] osd_err_code_frame_eff =
    (media_err_code_frame != 8'd0) ? media_err_code_frame : osd_error_code_frame;
```

错误码表（`src/SD/fat32_volume_scanner.v` L50-54）：

| 值 | 含义 | 来源 |
|---|---|---|
| 0x00 | 无错 | |
| 0x01 | 挂载失败（5s 内 media_ready 不来） | media_supervisor.v L44 |
| 0x05 | 扇区读超时（250ms 无数据/结束） | sd_sector_adapter.v L32 |
| 0x10 | 扇区错（scanner） | volume_scanner L51 |
| 0x20 |  boot 签名错 | volume_scanner L52 |
| 0x21 | 不支持的 BPB | volume_scanner L53 |
| 0x22 | 资源缺失 / src_valid=0 | volume_scanner L54 + loader L391 |
| **0x34** | 坏卡实测值（=scanner_error/idx_error 在坏介质上的组合锁存值） | 需在仿真/debugger 中确认具体子码位 |

**三个 sticky 缺陷（这是 R3/R4 的核心）：**

1. **`media_supervisor.media_err_code` 只置不清**（`media_supervisor.v` L104-107）：
   ```verilog
   if (media_ready) begin
       mount_cnt     <= 0;
       mount_attempt <= 0;        // ← 只清计时，不清 media_err_code
   end
   ```
   挂载成功后，错误码仍保持旧值。

2. **`fat32_media_loader.scan_done/scanner_error` 靠 `scan_start` 才清**（`fat32_media_loader.v` L621）：
   ```verilog
   if (scan_start) begin
       scan_done <= 1'b0; ...
   end
   ```
   supervisor 的 `sd_rst_n` 只复位 SD 控制器（L95-100，100 拍脉冲），**没有向 loader 发 `scan_start`**，也不清 loader 内部错误锁存。

3. **`health_monitor.err_code` 只在"新的非零错误码到来"时更新**（`health_monitor.v` L103-107）：
   ```verilog
   if (osd_err_valid && (osd_err_code != 8'd0) && (osd_err_code != err_code)) ...
   ```
   它从不清零，且 toggle 同步只在变化时刷新 frame（top L1648-1653），恢复后错误码即便源头消失，frame 也锁存最后值。

> **R3 根因**：坏卡 → scanner_error 锁存 0x34 → 换好卡后 supervisor 即使在重挂窗口成功 `media_ready=1`，也不清 `media_err_code`、不触发 loader 重扫 → OSD 继续显示 0x34。只有全局 `rst_n`（软重启）才把这三处全部复位。

### 2.4 播放中拔卡无法恢复（R4）

**时序还原：**

```
播放中拔卡
  → sd_sector_adapter 250ms 无数据 → tmo_done=1, sector_error=0x05
  → media_supervisor L90 置 ERR_RD_TMO，sd_rst_n=0 复位 SD 控制器 1μs
  → sd 回 ST_WAIT_MOUNT 重新等挂载
```

**为什么音/MV 起不来而封面还在：**

- 封面 bank 已在 SDRAM（`[0,1228800)`），是已缓存像素，不依赖 SD → 封面还能切、唱片能转（用户观察吻合）。
- 音频走 `wav_stream_player`：它在拔卡前已拉到某个 LBA，FIFO 排空后 underrun（"琵琶音"=填充噪声），等待下一个扇区完成脉冲。SD 控制器被 supervisor 复位后，旧 LBA 的 `sd_sec_read_end` 永远不会再来 → **播放器状态机永久挂在等待态**。
- 方案 S7-02 要求的 `media_epoch`（代次切换）+ REBUFFER 状态机**未实现**：supervisor 只复位底层，没有通知 wav/mv 丢弃旧请求、清空 FIFO、重新定位。
- 歌词 timebase（48kHz）独立于 SD，所以"歌词能暂停、能动"。

### 2.5 KEY07 两次返回卡死（R5）—— 事件双驱动竞态

KEY07（`exp_key_n[6]`，key_index=6）按下产生 `EV_KEY_DOWN`，经 bridge L68：

```verilog
wire key_mode = is_key_down && (ev_arg == 16'd6);   // → mode_tgl 翻转
```

`mode_tgl` 同时进两条路径：

**路径 A：play_ctrl.v（播放态退出）**

```verilog
// play_ctrl.v L38 stop_tgl = KEY07
if (p_stop) begin
    play_active <= 1'b0;   // 退出播放
end
```

**路径 B：browse_fsm.v（视图翻转）**

```verilog
// browse_fsm.v L112
thumb_mode <= j2_mode | ((mb_mode | (j2_confirm & ~view_mode)) & ~mode_play);
//          ^^^^^^^^^^^
//          注意：j2_mode 单独 OR，不受 mode_play 门控！
```

> 播放态按 KEY07：A 路径 `play_active:1→0`；B 路径 `view_mode:0→1`（进缩略图）。
> 再按一次：B 路径 `view_mode:1→0`，此时 play_active 已经是 0。
> 两条路径各自走独立的 toggle→3FF→边沿检测 CDC，时延不等，且 `mode_play` 在 play_active 切换瞬间被同步时存在跨域亚稳窗。
> 结果：进入 `play_active=0` 但 `view_mode=1`（或中间态）的矛盾态，MV/vinyl/频谱图层与浏览/缩略图图层不一致 → **唱片消失、音乐停、音谱卡死**。

### 2.6 缩略图纯黑卡死（R6）

`thumbnail_controller.v` L54：

```verilog
if (key_confirm && image_complete[focus_index]) begin
    active_index <= focus_index;
    view_mode    <= 1'b0;       // 只有 image_complete=1 才能 confirm 返回
end
```

- 浏览态正常时，4 张封面加载完，`image_complete=4'b1111`，任意焦点都能 confirm。
- **拔卡后**：SDRAM 里的封面 bank 虽然还在，但缩略图视图的 `image_complete` 是由加载握手置位的；拔卡导致新加载握手失败，位图不完整。
- 用户在缩略图态按确认，`image_complete[focus]=0` → 不动作；KEY07 虽能翻 view_mode（L41 不受 image_complete 门控），但 view_reader 等不到 SDRAM 有效帧 → **纯黑、切不动、退不出**。
- 用户说"换一首歌才能恢复"——正好印证：需要一次新的有效加载握手重建 `image_complete` 位图。

### 2.7 播完卡住 / EOF 未实现（R7）

`play_ctrl.v` 端口表里**没有 stream_end / eof 输入**（L28-46 全部端口已读）。L11-18 注释：

> "暂停冻结时基，不停 SD 读请求"。

- 当前 wav 播完后，FIFO 排空，pcm 输出静音/停顿，但 `play_active` 仍=1、`sel_song` 不变、`paused` 不自动置位。
- 用户感知"音乐播完自动暂停"是 wav_stream_player 自己排空后的副产物；**没有"自动下一首/单曲循环/返回浏览"业务**，这正是 S7-06 范围。
- 切歌卡顿：播放中按 EC1 旋转 → play_ctrl L116 `track_step=1`，top 据此请求新曲；若 SD 通道已因拔卡挂死，新曲扇区永远不来 → "切歌不从头开始，卡住"。

### 2.8 交互与用户预期差异（R8）

## 3. 错误码 1E00 / 1E01 / 1E34 触发与恢复语义评估

| 错误码 | 触发条件 | 当前恢复路径 | 评估 | 建议 |
|---|---|---|---|---|
| **1E00**（err=0x00） | 任何正常状态；OSD 拼了曲目号+e+00 | 无需恢复 | **不是错误**。易误读 | OSD 重排：err=0 时不显示后两位或与曲目号分行 |
| **1E01**（err=0x01） | 5s 内 `media_ready(=scan_done)` 不来（空卡、拔卡后挂载超时） | supervisor 3 次重试→30s cooldown→sd_rst 脉冲→重挂；插好卡后能自动恢复（日志 16:15:29 证实） | **基本符合 S7-02 设计**，但恢复后 err_code 不清（见 2.3），OSD 会残留 | media_ready=1 成功时清 `media_err_code` 并 toggle |
| **1E34**（err=0x34） | 坏卡导致 FAT/索引扫描错误锁存（scanner_error/idx_error） | **当前只能靠全局软复位**；supervisor 的 SD 复位不触发重扫 | **不满足 S7-02"重插后自动恢复"要求** | supervisor 复位后必须联动发 `scan_start`；loader 重扫成功即清 scanner_error |
| 1E05（err=0x05） | 单扇区 250ms 无数据/结束 | supervisor 立即 sd_rst 脉冲 | 底层看门狗工作，但上层播放器未收到 epoch | 同 R4，补 rebuffer |

> **核心问题**：错误码体系是"sticky 锁存"而不是"活跃状态"。S7-02 目标是"有界事务、重插可恢复"，当前实现只做到了"报出来"，没做到"恢复即清除"。

### 4.2 切歌加速与去渐暗

- 当前主界面 EC1 切封面慢 = 每次 `fs_next` 都要从 SD 读新扇区 + `video_fade_transition` 渐暗。
- 方案：
  1. 预取：利用现有四封面 bank，提前 1 首后台预读下一封面到备用 bank，切歌时直接切 bank，不等 SD。
  2. 转场时长参数化：把 `video_fade_transition` 的淡入帧数做成可由 KEY09 循环切换的模式寄存器（0=硬切、1=快淡 8 帧、2=标准 36 帧）。
  3. KEY09 循环切换动效，默认快淡/硬切，满足"不要渐暗"。

### 4.3 KEY07 卡死修复（R5）

- 修改 `browse_fsm.v` L112：播放态（`mode_play=1`）下 `j2_mode` **只做退出播放**，不再翻转 `view_mode`；退出瞬间强制 `view_mode<=0`。
- 即：`thumb_mode <= j2_mode & ~mode_play | ...`，并由 top 在 `play_active` 下降沿同步清 view_mode。
- 这样播放态 KEY07 = 干净地回到主界面全屏浏览，不再进入"播放态缩略图"矛盾态。

## 7. 仍需在仿真/debugger 中确认的点（本报告不武断下结论）

1. **0x34 的精确子码**：volume_scanner 列出的错误码最大 0x22，0x34=52 超出该表。需在坏卡镜像下抓 `fs_error`/`idx_error` 的实际位，确认是 boot 签名错(0x20)+某索引位组合，还是 scanner 状态机里未列入 localparam 的路径。
2. **`sd_media_rst_n` 与 fat32_media_loader.rst 的极性/接线**：top L553 `sd_media_rst_n = sdcard_rst_n & media_sd_rst_n`。需确认 loader 是高有效 `rst`（L399 `posedge rst`），supervisor 的低有效 `sd_rst_n` 是否经过反相才接到 loader；若没接对，supervisor 复位根本没复位 loader，R3/R4 修复时要一并核。
3. **缩略图 view_reader 在拔卡后的具体挂死点**：`thumbnail_view_reader.v`（23KB）未逐行读，建议修 R6 时先看它等待 `image_complete`/SDRAM ACK 的超时路径。
4. **ENC1 切歌"慢"的量化分解**：是 SD 扇区读取耗时还是 fade 帧数耗时，建议用 health_monitor 的 BL/VF 计数 + 示波器量 ENC1→切歌完成时延，再决定预取还是缩帧。
