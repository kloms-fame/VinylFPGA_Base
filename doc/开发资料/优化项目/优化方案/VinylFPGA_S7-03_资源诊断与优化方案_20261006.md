> **阶段**：S7-03（统一事件、完整红外与 DIP 控制）

> **报告日期**：2026-10-06
> **本轮边界**：仅做资源梳理、瓶颈定位、优化方案制定，**不修改代码**。

## 0. 结论摘要（TL;DR）

| 维度 | 基线（S6_mv_v5） | 第一梯队优化后预期 | 余量变化 |
|---|---|---|---|
| LUT | **15102 / 19600（77.05%）** | ~13700–14000（**70–71%**） | -1100 ~ -1450 |
| FF（REG） | 9691 / 19600（49.44%） | ~8650–8800（44%） | -900 ~ -1050 |
| BRAM9K | 46 / 64（71.9%） | 49 / 64（76.6%） | **+3（仍余 15）** |
| DSP | 16 / 29（55.2%） | 不变（16） | 余 13 |
| Slices | 8175（83.42%） | ~7400–7600（**76–78%**） | -600 ~ -800 |
| Setup WNS | **+0.100 ns（100 ps）** | +0.30 ~ +0.50 ns | 翻倍以上 |
| Hold WNS | +0.003 ns | 预期不变或微改善 | — |

**一句话诊断**：
- 真正卡脖子的是 **LUT 77% + Slices 83% + sd_card_clk(100 MHz) WNS 仅 100 ps**；BRAM/DSP 反而宽裕。
- 三大"白白浪费"：
  1. `lrc_font_rom` 用 **422 LUT** 实现了本可以用 **2 个 BRAM9K** 的字库；
  2. 全片 **25 路 debounce_filter** 各跑一个 20 位计数器，合计冗余 ~1200 LE；
  3. `fat32_volume_scanner` 的 512 B 扇区缓冲被推成分布式 RAM（~350 LUT），本可放 1 个 BRAM。
- WNS 仅 100 ps 的直接原因不是组合逻辑太深（Logic Level=0），而是 **`reset_sync/s2` 在 sd_card_clk 域扇出 2443**，布线延迟吃掉 9.075 ns / 9.364 ns。

## 4. 瓶颈成因深度分析（带源码位置）

### B1 🔴 `lrc_font_rom` 用 422 LUT 实现本应是 BRAM 的字库

- **位置**：`src/display/lrc_font_rom.v:8`（`always @* case(addr)`）
- **数据规模**：960 字 × 16 bit = 15 360 bit ≈ 2 块 BRAM9K。
- **成因**：
  - 代码用组合 `case(addr) font_row = 16'h....` 描述，**没有时钟沿**，安路 TD 无法推断成块 RAM，只能把 case 树展开成 LUT 查找表。
  - 对照：同项目 `src/boot/boot_logo_rom.v:30` 用 `reg [7:0] word_mem[]` + `initial` + `always @(posedge clk)`，同样规模就被正确推断成 16 个 BRAM9K，只花了 40 LUT。
- **证据**：final.area 中 `u_font_rom: LUT=422, seq=0, bram=0`；对比 `u_boot_logo_rom: LUT=40, bram=16`。
- **影响**：白白占用 422 个 LUT（占总 LUT 2.8%），BRAM 还剩 18 个空闲。
- **像素路径延迟**：当前 `lrc_osd.v:170` 在像素期同拍查表（`font_row[15-col_pix]`），改成同步读会引入 1 拍延迟，需要在 `lrc_osd.v:137-170` 对 `pixel_x/col_pix` 打拍对齐。

---

### B2 🔴 `fat32_volume_scanner` 的 512 B 扇区缓冲用分布式 RAM

- **位置**：`src/SD/fat32_volume_scanner.v:70`（`reg [7:0] sector_buffer [0:511]`）
- **读写模式**：
  - 同步写：`sector_buffer[sector_byte_index] <= sector_byte;`（line 206）
  - 组合读：`le16()`/`le32()` function（line 100-113）直接索引读
- **成因**："同步写 + 组合读"是块 RAM 推断的反模式，TD 把它推成分布式 RAM（LUT 作为 Dram）。512×8 = 4 096 bit，约占 300–400 LUT。
- **影响**：该模块 LUT=1142 中有相当比例是这块 RAM；启动阶段才跑一次，平时不工作，却常驻 LUT。
- **改造方向**：
  - 加 `(* ram_style = "bram" *)`；
  - `le16/le32` 改同步读（`ST_BOOT_PARSE` 状态多 1 拍）。该状态只在 SD 挂载时跑一次，时序影响可忽略。

---

### B3 🔴 25 路 debounce_filter 各自独立跑 20 位计数器

- **位置**：`src/io/debounce_filter.v:15`（`reg [19:0] stable_cnt;`）
- **例化数量**（已在 `expansion_integration.v` 核对）：
  - `u_expansion_io_hub → u_key_dip_monitor`：12 KEY + 6 DIP = **18 路**
  - `u_board_key_sw_monitor`：母板 3 KEY + 4 SW = **7 路**
  - 编码器 SW 在 `encoder_monitor` 内另外消抖（2 路）
  - **合计约 25–27 路**
- **每路开销**：20 位计数器（20 FF + 20 位比较器 ≈ 25 LUT）+ sync_bit(2 FF) + level/pulse 寄存器 ≈ **45 LE**。
- **总开销**：25 × 45 ≈ **1100–1200 LE**，是 `expansion_integration` 2986 LE 的最大单项。
- **成因**：每路独立数 400 000 个 50 MHz 周期（8 ms），25 个完全相同的 20 位计数器冗余。
- **改造方向**：在 50 MHz 域建一个共享 `tick_1ms`（50 000 计数），每路滤波器只保留一个 **3 位计数器**（数 8 个 tick = 8 ms，时长不变）。
- **数学等价性**：8 ms × 50 MHz = 400 000；8 × 1 ms tick = 8 ms。**消抖时间不变**。
- **旁证**：S7-03 新增的 `ui_command_router.v:81-158` 已经用了同款 1 ms 预分频（`MS_CYCLES = CLK_FREQ_HZ/1000`），说明这套时基在工程里已经存在，复用成本低。

---

### B4 🔴 `reset_sync/s2` 扇出 2443 —— WNS=+100 ps 的直接原因

- **位置**：`src/reset_sync.v:18-30`；最差路径起点 `u_sdcard_reset/s1_reg_syn_5.clk`，终点 `fat32_file_streamer/add0_syn_170.sr`（final.timing line 86-94）。
- **证据**：
  ```
  Data Path Delay : 9.364 ns
    cell 0.289 ns (3%)
    net  9.075 ns (97%)     ← 布线占绝对大头
  Logic Level     : 0        ← 组合逻辑根本不深
  Max Fanout      : 2443     ← reset 网络扇出爆炸
  Clock Skew      : 0.136 ns
  ```
- **成因**：sd_card_clk 域只放了一个 `reset_sync`，它的 s2 输出扇出到全域 9142 个 FF（实测 2443 个直接连线）。布线拥塞吃掉 9.075 ns，周期 10 ns 只剩 0.1 ns 裕量。
- **注意**：这不是"组合逻辑太深"，是**复位树物理扇出过大**。S6 之前的流水化（cluster_offset 打拍）已经把逻辑深度压住了，现在的瓶颈纯粹是布局扇出。
- **改造方向**：在 sd_card_clk 域内复制 3–4 个局部 reset_sync，分别扇出给：
  - `fat32_media_loader`（含 scanner / streamer / song_index_db）
  - `sd_card_top`
  - `sd_sector_adapter` / `bmp_read`
  - 其他小模块
  - 每路扇出控制在 ≤ 600。

---

### B5 🟡 `song_index_db` 中间数组与输出寄存器重复

- **位置**：`src/SD/song_index_db.v:86-92`（中间数组 `e_cov_cl/e_cov_by/e_aud_cl/e_aud_by/e_mv`）与 line 319-326（输出 `song_cover0~3/audio0~3`）。
- **成因**：P_STREAM 阶段把目录条目解到中间数组，P_FIN 再搬到输出寄存器。两份存储位宽重叠：
  - 中间：4×(32+32) + 4×(32+32) + 4×64 ≈ 768 bit
  - 输出：8×64 = 512 bit
- **影响**：多花 ~500–700 FF + 搬运 mux。
- **改造方向**：P_STREAM 直接写输出寄存器的对应位段，去掉中间副本。
- **风险**：需位拼接重排，但对外端口 `song_cover0~3/audio0~3` 不变。

---

### B6 🟡 `exp_echo_reporter` 的 96 字节 UART 消息缓冲

- **位置**：`src/io/exp_echo_reporter.v:72`（`reg [7:0] msg [0:MSG_MAX-1]`，MSG_MAX=96）
- **成因**：每发一行 UART 文本都在 96 字节寄存器数组里拼装，串行移位发送。96×8 = 768 bit 寄存器 + 地址 mux。
- **影响**：该模块 LUT=669 / FF=302。这是 S1 调试遗留 + S7-01B 遥测扩展的合并体。
- **短期策略**：S7-01/S7-03 调试期间保留；R1 产品版通过 `ECHO_ENABLE=0`（line 29）整体关掉，可省 669 LUT / 302 FF。

### B7 ⚪ `video_rgb_to_axis_640x480` LUT=636 与代码量不符

- **位置**：`src/video_rgb_to_axis_640x480.v`（全文仅 67 行，约 41 个 FF）。
- **矛盾**：报告 LUT=636 / FF=111，但代码只有：
  - `S_x_cnt[10:0]` 11 bit
  - `S_vs_1d / S_de_1d / S_frame_arm` 3 bit
  - `O_video_data[23:0] / O_video_user / O_video_valid / O_video_last` 27 bit
  - 合计 ≈ 41 FF，与报告 FF=111 已不符，LUT=636 更可疑。
- **判断**：安路 TD 层级报告可能把该模块附近未归属的组合逻辑（波形/OSD/歌词混合器输出端）归并到此层级。**暂列观察项**，等第一梯队优化后再看它是否真实存在。

### B8 ⚪ `lrc_lines_rom` 也是组合 ROM

- **位置**：`src/display/lrc_lines_rom.v:10`（`always @* case(line) case(col)`）
- 规模小（16 行 × (32+8) = 640 bit），预估 LUT 占用 30–50，收益低。

### B9 ⚪ `ir_nec_decoder` 时间计数器位宽过宽

- **位置**：`src/io/ir_nec_decoder.v:34-36`（`reg [31:0] low_cnt, high_cnt, low_width;`）
- **实际需求**：最长 `MAX_LEADER = 50 MHz × 11 ms = 550 000`，需要 20 bit（2^20=1 048 576），不需要 32 bit。
- **影响**：32 位比较器比 20 位多吃若干 LUT，但综合工具可能已自动收窄。报告 LUT=272 主要是多组时间窗口比较。
- **改造**：把显式位宽从 32 改成 20，作为低优先级顺手项。

## 5. 关键路径与时序裕量（来自 final.timing）

### 5.1 最差路径（sd_card_clk 100 MHz）

| 项 | 值 |
|---|---:|
| Slack | +0.100 ns |
| Begin Point | `u_sdcard_reset/s1_reg_syn_5.clk` |
| End Point | `fat32_media_loader_m0/u_file_streamer/add0_syn_170.sr` |
| Data Path Delay | 9.364 ns（cell 0.289 + net 9.075） |
| Logic Level | 0 |
| Max Fanout | **2443** |
| Clock Skew | 0.136 ns |

### 5.2 路径解读

- 起点是复位同步链的第二级触发器，终点是 file_streamer 里某个加法器的 SR 端。
- **Logic Level=0** 说明从 s2 输出到终点寄存器之间没有组合逻辑，只是一根长走线。
- 9.075 ns 纯布线延迟 = 扇出 2443 的物理代价。
- **结论**：要把 WNS 从 +100 ps 拉回 +300~+500 ps，最有效的手段不是再流水化（已经做过），而是**复制 reset_sync、分散扇出**。

## 13. 新最差路径深度定位

### 13.1 sd_card_clk 100 MHz（37 个违例端点，WNS -0.791 ns）

| 项 | 值 |
|---|---:|
| Begin Point | `fat32_media_loader_m0/mult1_syn_3.clk`（**MULT18 乘法器输出**） |
| End Point | `fat32_media_loader_m0/rgb_byte_cnt_reg[2]_syn_125.a[0]` |
| Data Path | 10.720 ns（cell 5.072 + **net 5.648**） |

**路径链**（全部来自 `src/SD/fat32_media_loader.v`）：

```
mult1_syn_3 (MULT18, line 278 required_pixel_bytes_q)
  → add0_syn_135/136/137 (4 级加法器链, line 294)
  → lt0_syn_134/137/140/143/146/149/152 (比较器链, line 294)
  → header_valid_n2 / compression_reg (line 690)
  → rgb_byte_cnt_reg / file_len_reg / mux185 (line 717)
  → pixel_byte_cnt_reg / add6_syn (终点)
```

**根因**：
- BMP 头解析时 `required_pixel_bytes = width × height × 3`（MULT18，line 278）；

- 旧基线 S6 流水化时只处理了 `file_streamer` 的 LBA 加法链（`cluster_offset` 打拍），**漏了 media_loader 里这条像素字节计数链**；
- Slices 83% 时布线延迟刚好压在 10 ns 内（+100 ps）；Slices 98% 拥塞后布线延迟多了 ~0.8 ns，直接打穿。

## 14. Slices 98% 拥塞的根因分析

### 14.1 为什么 LUT 只涨 2268，Slices 却涨 1434？

安路 EG4S20 的 slice 是聚合块（含若干 LUT + FF + 进位链）。布局工具在 83% 占用时还能紧密打包，到 88% LUT 时：
- 跨层次连线变长（S7-03 新模块插在 expansion_integration 内部，与旧 io 模块交叉）；
- 拥塞导致工具被迫把逻辑分散到远处的 slice；
- wire length 从 1.01 M 涨到 1.94 M（×1.92）；
- 最终 slice 占用冲到 98.05%。

- clk（50M）域 LUT=1819，S7-03 新增模块都在这里。

## 15. 紧急修复方案（在原 O1–O5 基础上新增/调整）

### 🔴 新增第一优先：O6 —— media_loader 像素计数链流水化

| 项 | 内容 |
|---|---|
| **位置** | `src/SD/fat32_media_loader.v:278`（mult1/required_pixel_bytes_q）、`:294`（add0/lt0 加法比较链）、`:690`（rgb_byte_cnt_reg）、`:717`（mux185） |
| **问题** | MULT18 输出后接 4 级加法 + 比较 + mux，共 8 级逻辑，无流水 |
| **改法** | 在 mult1 输出后加一级寄存器打拍：`required_pixel_bytes_q2 <= required_pixel_bytes_q`；后续加法/比较基于 `_q2`。把 8 级切两段（4+4），每段 < 5 ns |
| **预期收益** | sd_card_clk WNS 从 -0.79 ns → **+0.3~+0.5 ns**；37 个违例端点全消 |
| **风险** | 低。BMP 头解析只在加载图片时跑一次，多 1 拍不影响数据流语义 |
| **验证** | 跑 SD 图片加载仿真 + 上板看 4 张封面能否正常切换 |

### 🔴 调整 O4 优先级

O4（reset_sync 复制）从"第一优先"降级为"与 O6 并行做"——它仍能改善扇出，但当前最差路径已不是 reset。

### 🟡 新增 O7 —— ir_nec_decoder 计数器位宽收窄

- 位置：`src/io/ir_nec_decoder.v:34-36`
- 新跑片实测该模块 LUT 从 272 → 425（+153），是 S7-03 合入后增量最大的单一模块；
- 把 `low_cnt/high_cnt/low_width` 从 32 bit 显式收窄到 20 bit（MAX_LEADER=55000 < 2^20）；
- 预期释放 ~80-120 LUT。

### 🟡 新增 O8 —— exp_echo_reporter 临时关 ECHO_ENABLE

- 位置：`src/io/expansion_integration.v:29`（`ECHO_ENABLE=1`）
- 该模块 LUT=882 / FF=359，是 S7-03 调试期间最大的非必要逻辑；
- **临时方案**：把顶层例化改成 `ECHO_ENABLE=0`，省 882 LUT / 359 FF，直接把 slices 从 98% 拉回 ~90%；
- **代价**：UART 串口遥测暂时静默，S7-03 调试时再开；
- **这是最快解 slice 拥塞的手段**。

## 18. 结论

1. **当前 best_result/VinylFPGA.bit 时序不收敛**（Setup WNS -1.125 ns，43 个违例端点），**不建议直接烧录上板**；
2. 危机根源不是 S7-03 新逻辑本身（只占 ~578 LUT），而是 **Slices 98% 拥塞把原本勉强收敛的旧路径打穿**；
3. 最快解：**P0 两步**——media_loader mult1 打拍流水 + 临时关 ECHO_ENABLE，预计一轮综合就能回到收敛；
4. 第一部分 O1–O5 方案全部仍然有效，但要让位于 P0 时序修复；
5. 时序收敛后再按 O1→O5 顺序降资源，最后重新打开 ECHO_ENABLE。
