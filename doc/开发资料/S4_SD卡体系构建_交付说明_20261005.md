## 1. S4 做了什么（一句话）

把"卡上固定 `PIC1~4.BMP + AUDIO.PCM`"升级为**定长曲目索引 `INDEX.BIN`**：
PC 侧工具解析 FAT32、把每首曲目的封面/裸 PCM 的簇号、字节数、进度与 SHA256
写进索引与报告；FPGA 侧扫描器找到 `INDEX.BIN`、`song_index_db` 流式校验索引，
封面与音频定位改由索引给出；索引缺失/损坏时**完全回退**到旧路径，不挂死。

### 2.3 为什么可以不改 `sd_card_bmp.v` / `top_tf_hdmi_audio.v`

报告第 6 节预计要改这两个文件；实际实施中发现**取数路径已经被 `fat32_media_loader`
完全封装**，因此把改动收敛在 loader 内部即可，`sd_card_bmp` 与顶层**一行未改**：

```text
扫描器 → (INDEX.BIN? 读索引→校验) ─┬─ 有效：封面簇/长度、音频簇/长度 取索引
                                    └─ 无效/缺失：原样取 PIC1~4 + AUDIO.PCM
        → scan_found_valid ×曲目数 → sd_card_bmp（四 bank 预加载/选图/轮播/转场一行未动）
        → 文件流器按簇链取封面 → SDRAM
        → wav_stream_player 按 start_lba/total_sectors 取音频
```

好处：S3 已验证的四 bank 预加载、`select_req/select_ack` 握手、转场边界、
音频 FIFO 语义全部不受影响；S4 的差异面只有 SD 读取层。

### 2.4 边界与不变量

- **封面支持碎片链**：条目只存 `first_cluster`，FPGA 复用已验证的 `fat32_file_streamer`
  走 FAT 链取数（自带 `ERR_FAT_LOOP / ERR_CLUSTER_RANGE / ERR_EARLY_EOF` 校验），
  所以封面可以是碎片文件；PC 侧同时把解析出的物理 LBA 运行段写进报告备查。
- **音频本阶段要求物理连续**：`wav_stream_player` 是"逐扇区 +1"读法（S0~S3 既有行为），
  所以打包工具默认拒绝碎片音频，必须显式 `--allow-fragmented-audio` 才放行并记风险。
  真正支持碎片音频播放属于 S5（报告把音频播放放在 S5）。
- **索引文件固定 512 字节**（1 扇区、占 1 簇），因此 RTL 只需读一个扇区；
  文件流器 `file_size=512` 会让"末簇必须 EOC"的既有校验自然成立。
- **根目录限制**：FPGA 只扫描根目录**首扇区**（16 个目录项），工具对每个被引用文件
  强制校验其目录项必须落在前 16 项内，否则直接报错（避免"PC 能生成、板子看不见"）。
- **索引超限必须报错**：`song_count` 上限 4；工具侧 `>4` 直接拒绝，RTL 侧
  `hdr_count>4` 判 `SIDX_ERR_COUNT` 并 `valid=0`，绝不静默越界。

## 3. INDEX.BIN 索引格式（RTL 与 PC 工具逐字节一致）

全文件小端，长度固定 **512 字节**。定义见 `src/include/song_index_defs.vh`。

### 3.1 头部（偏移 0..63）

| 偏移 | 长度 | 字段 | 说明 |
|---:|---:|---|---|
| 0 | 8 | `magic` | ASCII `"VINYLIDX"` |
| 8 | 2 | `version` | = 1 |
| 10 | 2 | `entry_size` | = 64 |
| 12 | 2 | `song_count` | 1..4（超限必须拒绝） |
| 14 | 2 | `max_songs` | 写入端声明（=4），读取端参考校验 |
| 16 | 4 | `entries_crc32` | CRC-32/ISO-HDLC，覆盖 `[64, 64+song_count*64)` |
| 20 | 4 | `flags` | bit0 = 由 `vinyl_packer` 生成 |
| 24 | 40 | reserved | 必须为 0 |

### 3.2 曲目条目（64 字节 × song_count，起始偏移 64）

| 偏移 | 长度 | 字段 | 说明 |
|---:|---:|---|---|
| 0 | 4 | `flags` | bit0 有封面 / bit1 有音频 / bit2 歌词 / bit3 MV |
| 4 | 4 | `cover_first_cluster` | 封面 BMP 起始簇（FAT 链起点） |
| 8 | 4 | `cover_bytes` | 封面文件字节数 |
| 12 | 4 | `cover_crc32` | 封面内容 CRC32（记录值，PC 侧校验） |
| 16 | 4 | `audio_first_cluster` | 裸 PCM 起始簇 |
| 20 | 4 | `audio_bytes` | 裸 PCM 字节数 |
| 24 | 4 | `audio_crc32` | PCM 内容 CRC32（记录值，PC 侧校验） |
| 28 | 4 | `audio_start_sector_hint` | PC 解析出的物理起始 LBA（追溯/S5 用） |
| 32 | 24 | `title` | ASCII，NUL 补齐（RTL 不消费） |
| 56 | 8 | reserved | 必须为 0 |

### 3.3 索引错误码（RTL 输出 `song_index_db.err`）

| 值 | 含义 |
|---|---|
| 0x30 | `SIDX_ERR_MAGIC` 魔数错 |
| 0x31 | `SIDX_ERR_VERSION` 版本不符 |
| 0x32 | `SIDX_ERR_ENTRY_SIZE` 条目长度不符 |
| 0x33 | `SIDX_ERR_COUNT` 曲目数为 0 或 > 4 |
| 0x34 | `SIDX_ERR_CRC` entries_crc32 不符 |
| 0x35 | `SIDX_ERR_CLUSTER_RANGE` 簇号越界 / 缺封面 / 长度 0 |
| 0x36 | `SIDX_ERR_STREAM` 文件流报错（含 FAT 链损坏） |
| 0x37 | `SIDX_ERR_NO_COVER` 保留 |

任一错误 → `valid=0` → loader 回退到 `PIC1~4.BMP + AUDIO.PCM`
（`USE_INDEX_BIN=0` 时直接走旧路径，不读索引）。

## 4. 串口输出格式（**无变化**）

115200 8N1、事件驱动、静止无输出；S4 **不新增任何串口行**。
索引的失败/回退通过既有 OSD 错误码路径体现（`bmp_error`/`osd_error_code`），
不占用串口通道。

## 5. 引脚约束片段（**零新增**）

S4 不新增任何管脚，`constraints/pin.adc` 与 `constraints/timing.sdc` **均未改动**：

- 索引读取复用 **已约束** 的 TF/SPI 四线（`sd_ncs=A12 / sd_dclk=A14 / sd_mosi=A13 / sd_miso=B14`）。
- 本阶段新增逻辑全部落在既有 `sd_card_clk`(100 MHz) 域，无新增时钟、无新增跨域关系。

```tcl

set_pin_assignment	{ sd_ncs }	{ LOCATION = A12; ... }
set_pin_assignment	{ sd_dclk }	{ LOCATION = A14; ... }

set_pin_assignment	{ sd_miso }	{ LOCATION = B14; ... }
```

（IO 报告仍为 `71/188`，与 S3 一致。）

## 6. PC 侧工具用法与可追溯报告

```powershell
# 1) 把封面/音频拷到卡上（或写入一个 FAT32 镜像文件），然后按 manifest 打包
python tools/vinyl_packer.py pack --image card.img --manifest songs.json --report INDEX.json

# 2) 沿用现有 PIC1~4.BMP + AUDIO.PCM 命名
python tools/vinyl_packer.py pack --image card.img --demo

# 3) 只读校验（不改卡）：回读 INDEX.BIN 并重算封面/音频 CRC32
python tools/vinyl_packer.py verify --image card.img --width 640 --height 480

# 4) 查看索引内容
python tools/vinyl_packer.py info --image card.img
```

manifest 格式：

```json
{"songs": [
  {"title": "Song A", "cover": "PIC1.BMP", "audio": "AUDIO.PCM"},
  {"title": "Song B", "cover": "PIC2.BMP"},
  {"title": "Song C", "cover": "PIC3.BMP"},
  {"title": "Song D", "cover": "PIC4.BMP"}
]}
```

`INDEX.json` 报告每首曲目给出：`first_cluster`、`bytes`、`sectors`、
**物理 LBA 运行段 `lba_runs`**、`crc32`、`sha256`，以及索引自身的
`index_cluster/index_lba/entries_crc32` —— 即"卡根目录资源与条目 SHA256 可追溯"。

封面约束与 RTL 完全一致：必须是 **24bit、未压缩、宽高与 `--width/--height` 相同**的 BMP，
否则工具直接拒绝（避免"PC 打包成功、FPGA 判 `ERR_HEADER`"）。

### 7.4 时序收敛过程（如实记录）

第一版索引解析器把两件 100 MHz 域不该有的东西带上来了，route 直接失败：

1. `fat32_file_streamer` 的 `file_byte_offset` 是一个 **32 位减法器**。在 S0~S3 里它**无人使用、
   被综合裁掉**；索引解析器一旦引用它，这个减法器就复活并进入 100 MHz 关键区域。
   → 改为解析器自带 9 位字节计数，该端口不引出。
2. 4 首歌的"簇号范围"检查原本在 `in_done` 当拍用一棵 **4 路 32 位比较器组合树**
   驱动大量寄存器使能（实测 `max_cluster → song_cover*_reg.ce` 超时）。
   → 改为 `P_STREAM → P_CHK` 逐拍校验，每拍只比一首歌。
3. 另外把 `idx_take` 里两个 32 位比较器（簇号/长度）删掉（同一件事由解析器做），
   并把"本次用于发 found 的有效位"落成寄存器 `src_valid`，从发 found 路径上移走 mux。

这三处改完后 seed 5 即收敛（`+47 ps`）。过程快照：
`S4_index/`（首版，seed 5 `-201 ps` + seed 扫描记录）、
`S4_index_v1/`（去减法器版，seed 5 `-334 ps`）、
`S4_index_v2/`（逐拍校验版，seed 5 `-148 ps`）、
**`S4_index_v3/`（正式产物）**。**未使用任何假路径或放宽约束。**

## 9. 开关与回滚

| 场景 | 操作 |
|---|---|
| 完全关闭索引、回到 S3 固定布局 | `fat32_media_loader` 参数 `USE_INDEX_BIN = 1'b0` 重新综合布线 |
| 临时只验旧路径 | 卡上删掉 `INDEX.BIN`（`PIC1~4 + AUDIO.PCM` 齐全）即自动回退 |
| 退回 S3 上电镜像 | 用 `S3_browse_v1/VinylFPGA_optimized.bit` 重烧配置 Flash |
| 退回主链路基线 | 恢复 `p05_s5` bit；撤销 `fat32_volume_scanner` 索引匹配与 loader 三态即可，`sd_card_bmp`/顶层无需改动 |

> 音频边界：S4 只交付"索引驱动的音频定位"，播放仍是既有单轨语义（取第 1 首）。
> 多曲切换、碎片音频播放、歌词时间轴属 S5。
