## 0. 结论摘要与执行顺序变更

### 0.1 一句话结论

主链路与 S7-01/02/03 已收口，**当前代码实际能力已超出 S7 方案文档的记载**：S7-06A（结束策略）与 S7-08A（切歌动效）的骨架已经提前落地；而 S7-05（状态反馈/数码管/WS2812）**执行器为零**——`exp_ws2812_data` 恒 0、`exp_led_n` 只是按键电平直通、`led_enable`/`ws_enable` 悬空、数码管仅显示诊断十六进制。用户要求的重排方向（先做基础拓展、后做菜单与统一调参）**与代码现状相符且可行**，但必须先解决 KEY04/KEY05 语义双占与 Slices 裕量两条硬约束。

### 0.2 阶段顺序变更

原 S7 方案顺序：`S7-04 菜单 → S7-05 反馈 → S7-06 播放策略 → S7-07 歌词 → S7-08 视觉 → (统一调参) → S7-09 Flash → S7-10 发布`。

本次按用户诉求重排为：

| 顺序 | 阶段 | 用户可见结果 | 优先级 / 发布归属 | 与原方案关系 |
|---|---|---|---|---|
| 0 | S7-00/01/02/03/03b **已收口** | 现有可下载基线 | 已完成 | 沿用，不重做 |
| 1 | **S7-R1 状态反馈与外设执行器** | J2 LED 四灯语义、数码管显示业务内容、WS2812 律动/进度 | 必须 | 原 S7-05 提前 |
| 2 | **S7-R2 播放结束策略/重播/seek** | KEY12 三态、±5 秒进度、红外进度键与重播键可用 | 必须 | 原 S7-06；A 部分已提前落地，B 部分新建 |
| 3 | **S7-R3 多曲歌词资产与三行显示** | 每首歌自己的三行歌词，KEY06 切模式 | 必须 | 原 S7-07 |
| 4 | **S7-R4 转场、界面层次与可选 FFT** | KEY09 三种转场、图层顺序统一、条件 FFT | 转场必须／FFT 条件 | 原 S7-08 |
| 5 | **S7-R5 扩展板控制项全量收口** | 切歌模式、播控方式、切歌动效、WS 灯效、返回主界面、WS 总控、红外接收、屏幕消隐、指示灯全部业务化并板验 | 必须 | 原 S7-05/06/07/08 中散落 DIP 与按键业务收口 |
| 6 | **S7-R6 EC2 旋钮 OSD 调参、参数统一与静音**（统一调参阶段） | 顶部浮窗旋钮调音量/亮度/对比度/进度 | 必须 | 原 S7-04 后置至此；**形态改为 EC11-B 式 OSD 浮窗，不建传统菜单**，详见独立设计文档 |
| 7 | S7-09 用户 Flash 与持久化 | 参数掉电恢复 | 参数保存为完整产品目标 | 不变 |
| 8 | S7-10 演示、长稳与发布 | 自动演示、24 小时稳定性 | 必须 | 不变 |

**重排的四条理由（基于代码事实，非主观偏好）**：

1. **S7-R1 是硬阻塞点**。`led_enable`/`ws_enable` 在 `ui_command_router.v:65-66` 已算出并引到顶层 `top:348-349`，但**全文无任何消费者**；`exp_ws2812_data` 在 `expansion_integration.v:443` 恒 `1'b0`。DIP3/DIP6 目前是"有状态、无效果"，不先补执行器，后续所有反馈类验收都无处落地。
2. **S7-R5 依赖 R1–R4 的产出**。切歌模式（DIP2/KEY07）、播控方式、切歌动效、WS 灯效、WS 总控、红外接收、屏幕消隐、指示灯这 8 项在原方案里被拆散在 S7-03/05/06/08 各阶段验收，**没有任何单一阶段对它们做整体板验**。重排后集中收口，可一次覆盖 DIP3/4/5/6 与 12 键的完整业务矩阵。
3. **S7-06A 与 S7-08A 事实上已提前完成**（见 §3.3），把它们排在 R2/R4 是"补齐真缺部分"而非"从零新建"，顺序调整不增加工作量。
4. **S7-04 菜单必须后置**。`param_menu_controller` 目前是母板 KEY1+KEY2 组合键的独立亮度/对比度副本（`param_menu_controller.v:48-49`，各 5 档 LUT），**不持有音量、转场、WS、歌词、结束策略**。在这些参数的业务写入点尚未统一前先建菜单，会立刻产生第二个多写入者——正是原方案 §3.1 明令禁止的。

### 0.3 路线比较及取舍

| 路线 | 优点 | 主要代价 | 本报告选择 |
|---|---|---|---|
| **先反馈与基础拓展，后菜单调参**（本次重排） | 执行器先就位，每一项都有独立可回退 bit；Slices 增量分散到多个小轮次；菜单一次成型不返工 | R1–R4 期间 OSD 提示能力有限，错误只能靠 UART 与画面提示 | **采用** |
| 严格按原 S7-04→S7-08 顺序 | 与既有文档一字不差 | S7-04 需在 WS/歌词/结束策略写入点未统一时先建 `param_csr`，必然返工；且 R1 的执行器缺失会让 S7-04 的"参数临时值显示在数码管"无法验收 | 不采用 |
| 一次性合并 R1–R5 为大合并 | 少几次构建 | 出问题无法定位；当前 Slices 85.84% 下一次性放量风险过高 | 不采用 |

### 5.0 公共约定

所有阶段统一执行：`需求/时序样例 → 独立仿真 → 集成回归 → 原生 TD 构建 → SRAM 板验 → 保存证据`。

共同放行条件（每阶段必须全部满足）：

1. 新功能定向仿真通过，覆盖复位、边界、并发、失败。
2. 与变更相关的原回归通过；共享存储/播控/图层变更需跑音视频并发 + 浏览回归。

4. 输入并发 + 连续灯效运行 1 小时，`cnt_underrun` 不增加。
5. LED 四灯物理灯位逐个点亮核对（E1 §7 明确未逐灯实测）；四类事件分别触发正确灯。
6. 数码管各显示项、使能与优先级逐项正确；`sw1=0` 时全灭。

**必须遵守的边界**：
- `target_sample` 钳位在 `[0, total_samples-1]`。
- PCM 每样本 2 字节，扇区内偏移必须跳过。
- 首版**限定已验证连续 PCM**；若音频允许碎片，必须用 FAT 文件偏移定位或受检验的片段表，**不能无条件用 `start_lba + offset/512`**。打包工具必须明确拒绝不支持的布局。
- 重播必须走完整流程：淡出 → 停止新请求 → 旧事务排空/取消 → 音频与 MV/歌词代次切换 → 媒体时间归零 → 预缓冲 → 淡入。**不能只将 `time_ms` 清零而仍播放原 FIFO。**

#### 验收标准

1. 三种结束策略每种 20 次：顺序下一首（含最后一首回第一首）、单曲循环、返回浏览。
2. 零曲目、文件尾不足一扇区、单曲文件边界分别验证。
3. ±5 秒连续往返 100 次；首尾钳位、暂停中 seek、切曲与 seek 同拍、旧应答延迟不得污染新曲。
4. 仿真比较实际输出样本起点，误差 ≤1 样本。
5. 实机正常供数恢复后 MV 时间差 ≤100 ms、歌词差 ≤100 ms。
6. REBUFFER：注入 SD 短暂超时后音频淡出、时间冻结、恢复后淡入，无样本跳序。
7. seek 失败时在规定超时后返回可操作错误状态（Err-05）。

### 6.1 为什么统一调参必须最后

`param_csr` 的核心价值是**单写入点**。若在 R1–R4 之前建立调参界面，以下每项都会立刻产生第二个写入者：

| 参数 | R1–R4 阶段的既有写入点 | 若提前建浮窗的后果 |
|---|---|---|
| 音量 | `play_ctrl.v:14-17` 参数 + `:92-93` 直写 | 音量与 mute 各自为政，取消静音无法恢复原值 |
| 亮度/对比度 | `param_menu_controller.v:153-154` 独立副本 | 与浮窗值不一致，退出后画面跳变 |
| 转场 | `effect_mode`（`top:593`）由 KEY09 直接循环 | 浮窗改值与 KEY09 循环互相覆盖 |
| WS 模式 | R1 新增的 KEY10 toggle | 同上 |
| 歌词模式 | R3 新增的 KEY06 toggle | 同上 |
| 结束策略 | `end_mode`（`play_ctrl.v:110`）由 KEY12 直接循环 | 同上 |

**上表也是浮窗只放 4 项（音量/亮度/对比度/进度）、不放转场/WS/歌词/结束策略的原因** —— 后四项保持 KEY 直循环，浮窗不重复暴露，避免 idx 循环过长。

E5 §3.3 定义的门槛：**Slices ≤88% 正常；88%～90% 先做减负评估；>90% 暂停再加重型功能。**

| 阈值 | Slices 值 | 距当前 |
|---|---:|---:|
| 当前 | 8412 | — |
| **88% 阈值** | **8624** | **仅 212 slices** |
| 90% 红线 | 8820 | 408 slices |
| 100% | 9800 | 1388 slices |

**这是本次重排最大的风险点**。Slices 已达 85.84%，距 88% 阈值仅 212 个 slice，约等于一个 `expansion_integration` 子树的 6%。

**历史上 Slices 已经因为流程口径剧烈波动**：E9 记录 S703_M0 为 8753（85.3%），而 GUI 默认流程构建曾达 9609（**98.05%**）—— 同一份源码，仅因 `map_mode` 从 `area_prior` 切到默认，ripple-LUT 就从 1535 涨到 2695（+1160）。**这 1160 的差异在综合阶段 `optimize_gate` 就已产生，不是用户逻辑膨胀。**

**强制约束**：
1. 所有快照必须用 `build_verified_round.py --map-mode area_prior`，**不得用 TD GUI 默认流程**作为交付依据。
2. 每个阶段结束后立即报告 LUT/Slices 增量，**不得攒到最终阶段再检查**。
3. 一旦 Slices >88%，立即做减负评估（不继续叠加功能）。
4. seed 是最后手段，不是结构裕量的证明。**不得用停音频、停 HDMI 或丢用户命令换表面流畅。**

### 7.3 各阶段资源预算与风险

| 阶段 | 预估 Slices 增量 | 预估 BRAM | 预估 DSP | 预算策略 | 风险 |

**减负不得触碰的红线**（E9 §1）：
- HDMI 1.4b 核与 PHY（加密 IP）、SD/FAT32 协议链、SDRAM 控制器内部不改。
- BRAM 大头（厂商 IP 16 块 + 固化字库 Logo 16 块 + 音频 FIFO 8 块 + 帧读 4 块 + 缩略图 2 块）属不可压缩项。
- DSP 非瓶颈（15/29），本轮不动。
- 6 位数码管、最多 4 曲、48 kHz/16 bit 单声道 PCM、MV 10 fps 320×240 RGB565、SDRAM 分区地址表全部冻结。
- `dib_size`/`compression` 字段收窄被首轮明确剔除（截断翻转判定属功能变化）。

### 7.4 时序风险

当前 `Hold WNS = +3 ps`，**裕量极小**。历史上已多次出现"某个 seed 收敛、换个 seed 就 Hold 违例"的情况（M5: −167 ps、M6_s5: −92 ps）。

S7-03b §9.1 记载：MCP 默认轮次最终 QoR 为 `Setup +107 ps / Hold −20 ps / Hold 违例 4 端点`，**该 bit 未作为交付物**；只有 seed 7 收敛。

**强制约束**：
1. 每次必须扫多个 seed 记录分布，**不得把偶然一个 seed 通过当成结构裕量充分**。
2. 新增运算（如 R2 的 seek 扇区定位）必须在 `sd_card_clk` 100 MHz 域做**流水化**，参考已有做法：`fat32_media_loader` 的地址运算已流水化、S7-03 做过 `mult1_syn_3` 外提收口。
3. R3 歌词装载、R4A 转场都在像素/控制域，须给出延迟表和像素边界测试。
4. **不通过放宽周期或新增无依据 false path 获得表面通过。**

### 7.5 带宽预算（不变）

- MV：`320×240×2×10 = 1,536,000 B/s`
- PCM：`48000×2 = 96,000 B/s`
- 最低媒体载荷合计 **1,632,000 B/s**
- 音频 FIFO 4096 样本，理论全满覆盖约 85.3 ms；高水位 2048 样本约 42.7 ms；低水位 1024 样本约 21.3 ms。**85.3 ms 不是正常运行保证可抗的最长停顿。**
- S7-00 建议实卡有效吞吐达到载荷 1.25 倍（约 2.04 MB/s）。E4 的约 2.719 MB/s 来自理想卡仿真，**不是实卡结果**。
