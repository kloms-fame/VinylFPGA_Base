当前目录存在旧稳定候选、失败实现和后续背景修改流程，不能用文件最近时间排序直接选比赛版本。选择已获得相应验证的组合，并把身份写在随身清单。

## 2. 最小验收矩阵

以下是建议执行的验收任务，次数和时长是排练建议，不是已完成结果，也不是官方要求。

| 项目 | 操作 | 观察与记录 |
|---|---|---|
| 冷启动 | 真实断电上电至少3次 | 不做PC下载，启动后画面、声音与参数一致 |
| 四曲浏览 | 每首前后浏览、确认 | 焦点、封面、标题与声音对应 |
| 自动轮播 | 选已验证间隔，观察数轮 | 模式、周期、转场与手动操作配合 |
| 暂停恢复 | 每首至少一次 | 声音与媒体时间冻结/恢复，无错误归零 |
| 正反Seek | 曲首、中段、尾部，快速连续旋钮 | 落点、数码管、歌词、MV一致，首尾钳位 |
| 结束策略 | 短测试素材或已验证曲尾 | 暂停、单曲循环、自动下一曲对应图标 |
| KEY6歌词模式 | 播放与暂停中切换 | 当前句/五行行为准确 |
| MV/封面 | 有MV与无能力状态分别检查 | 只显示完整可用帧，回退合理 |
| BRI/CON/VOL | 中间档与上下限 | OSD数值和效果一致，饱和不回绕 |
| ROT/WSL | OFF、最低、最高档 | 轮播与两路灯带符合当前设定 |
| 参数保存 | 手动/自动、保存期间再调参 | 忙、成功、dirty指示与恢复值对应 |
| 默认值 | 恢复默认并重启 | 运行与保存语义一致 |
| 唱针与暂停 | 播放时拨动、暂停时拨动 | 电机和灯效门控正确，音频因果清楚 |
| 息屏听音 | 手动/自动，首键唤醒 | 音频继续、首键是否吞掉符合实际 |
| 红外 | 方向、进度、音量、保存等逐键 | 与实际路由一致，连发/使能正确 |
| 长播放 | 自定不少于一次完整演示时长的连续运行 | 填实际分钟数、卡型、设备、错误与欠载观察 |

若选用最新双艺术缓存候选，还要单独检查：预热后模式三/四来回至少20次、静态背景中切歌、立即快速切换、暂停/MV切换、冷启动首次预热。不能将其状态记成旧字库候选已覆盖。

## 3. 只读核对命令

在工程根目录运行，以下仅作读取，不负责烧录：

```powershell
git status --short
git rev-parse HEAD
Get-FileHash -Algorithm SHA256 -LiteralPath '实际比赛固件.bit'
Get-FileHash -Algorithm SHA256 -LiteralPath '实际媒体镜像.img'
python -X utf8 tools/vinyl_packer.py verify --image '实际媒体镜像.img'
```

最后一条应看整体退出码与最终结论，不能以中途某个VERIFY_OK代替全项通过。这里的路径为待替换示例，不是已经存在的可直接执行固件路径。

`verify_closeout_candidate.py`针对其清单绑定的旧候选。当前源码有修改时拒绝匹配是有意义的保护，不应为了“全绿”手工改哈希冒充已重建。`--require-final`还要求清单待办满足，人工报告通过不一定代表所有工程待办清零。

## 5. 现场15分钟准备顺序

1. 按通知确认显示与声音设备，接线并观察电源状态。
2. 冷启动，核对开机、曲目、默认音量与当前背景。
3. 测一次播放、暂停、Seek、OSD和遥控。
4. 恢复约定的开场曲目、菜单状态、DIP和音量。
5. 打开一页架构图与比赛版本证据，避免答辩时满盘搜索。
6. 关闭会自动播放其他声音的软件；是否允许PC展示资料按场次规则执行。

准备结束后不反复切换全部功能把状态弄乱。主讲与操作员用同一张顺序卡。

## 6. 异常处置表

| 现象 | 先检查 | 再深入 | 对评委可说的话 |
|---|---|---|---|
| 黑屏无信号 | 电源、HDMI输入口、线缆、屏幕源选择 | PLL/复位、HDMI时序与固化版本 | “先确认输出链路是否建立，再检查媒体层。” |
| 有画无声 | 显示器是否支持HDMI音频、输入音量、静音 | 播放状态、PCM供数/ACR/源选择 | “画面链已建立，我先核对音频路由和当前静音状态。” |
| 旋钮无响应 | DIP1、当前页面、菜单与消隐首键 | 编码器计数/事件桥/目标域 | “这个操作受当前页面与使能控制，我先确认状态。” |
| 遥控无响应 | DIP5、电池、接收方向、业务使能 | 合法码、反码、repeat节流 | “先排除输入未被接受，再看具体业务命令。” |
| 歌词错位 | 固件与媒体是否匹配、当前曲号/位置 | Seek装载、样本时基、ROM时间 | “先核对资源版本，避免把不同曲库误当算法错误。” |
| 背景变灰 | 是否首次加载、当前图是否ready | 读取错误、失败回退、epoch | “未就绪时使用回退画面，接着确认是加载还是错误。” |
| 保存后值不一致 | 保存快照、LED2/3、是否保存中再调参 | 双槽有效性、回读/CRC、恢复优先级 | “保存完成对应当时快照，我核对当前是否还有未保存修改。” |
| 卡顿或噪声 | 当前卡和媒体、是否操作重启、音量 | 水位、欠载、SD错误和所有权 | “先记录触发条件和错误，再按服务链路定位。” |

不要把“可能原因”说成已经证实的根因。每次只改变一个条件，保留版本与症状；必要重启后清楚说明这一动作证明与未证明的范围。

## 7. 演示失败时仍能展示什么

可以展示实际架构、源码、对应版本的测试与已录制真实视频，并说明现场故障与恢复进展。视频是辅助证据，不能假装正在运行；不能加载多个功能单独镜像冒充一体化最终设计。

比赛前准备一段最短主链路：启动→选曲→发声→暂停/恢复→调参。复杂功能异常时，在规则允许范围内保持这一条已验证演示，回答机制与边界。
