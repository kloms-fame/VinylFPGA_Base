# SW4 告警与参数保存音效排查

日期：2026-10-21。范围：在已封版工程上进行只读根因排查与定向仿真，未修改生产 RTL、约束、工程配置或 bit，未重新烧录。

## 1. 结论

用户报告了两项现象：

1. `SW4 / sw4 / C5` 按《产品交互》应控制无 SD 卡或系统故障时的声音告警，实际感觉无效。
2. 参数保存没有音效。

两项均有明确的实现缺口：**SW4 输入已接通，但没有连接故障声音门控；参数保存请求与完成结果没有连接蜂鸣器。** 这与“保存没有成功”“SW4 电气损坏”是不同问题。本轮没有测量真实引脚电平，结论依据是当前源码、配置和可重复仿真。

当前实际行为：

| 场景 | 当前结果 | 预期的声音能力 |
| --- | --- | --- |
| 拨动 SW4 | 消抖后 bit3 改变，可触发普通拨动提示音 | 未形成告警总使能 |
| 媒体挂载/读故障 | 错误码可进入健康/LED路径 | 未触发故障音 |
| 欠载/视频失败 | 对应历史故障标志置位 | 未触发故障音 |
| 母板 KEY3 保存 | 请求可被接受、实际写入成功、已保存灯亮 | 无保存按键提示音，也无提交成功音 |
| 自动保存 | 可完成实际写入并点亮已保存灯 | 无自动保存完成音 |
| 红外 E6 保存 | 正常接收时可以有普通红外操作提示 | 普通接收音不代表 Flash 已保存成功；没有独立的完成音 |

## 2. SW4：断点在消抖之后

链路为：

```text
C5 引脚约束
  → top.sw4
  → expansion_integration.sw4
  → u_board_key_sw_monitor.dip_async[3]
  → board_sw_level[3]
```

`constraints/pin.adc:104` 将 `sw4` 约束到 C5。`src/io/expansion_integration.v:342` 将 `{sw4, sw3, sw2, sw1}` 送入同一输入消抖模块，第四位就是 SW4。

但当前顶层使用了 SW1 的数码管控制、SW2 的启动采样、SW3 的自动保存使能，**没有消费 SW4 电平作为告警使能**。

SW4 变化仍会进入：

```text
board_sw_change_pulse[3]
  → board_sw_change_any
  → dip_change_any
  → sound_events_q
  → buzzer_feedback 的 EV_DIP
```

因此拨动时可以听到提示音，而持续保持开/关不会改变故障时的声音输出。

`src/io/expansion_integration.v:461` 的 `sound_enable` 接的是常量参数 `BUZZER_ENABLE`，不是 SW4。`buzzer_feedback` 当前只有按键、拨码、编码器、红外和自动轮播等事件输入，没有故障或保存完成输入。

错误码由 `health_monitor` 汇总，`err_code != 0` 连接到扩展状态灯；母板 LED4 也能显示媒体/Flash 故障。这些 LED 路径没有接到发声事件。

## 3. HDMI 琶音也没有承担故障报警

项目中的两条发声通道要分别理解：

| 路径 | 物理输出 | 当前用途 |
| --- | --- | --- |
| `buzzer_feedback` | 母板 H11 `board_buzzer_n`，并镜像到 EXT1 | 方波操作提示音 |
| `pcm_media_tone` → 音源 mux → HDMI | HDMI 显示器/音箱 | 保留的 PCM 琶音产生器；当前未播放状态主要提供静音采样节奏 |

`src/top_tf_hdmi_audio.v:1970` 的 `audio_silent` 在启动、未播放、预填未就绪等状态成立；`audio_volume` 随之置 0。`src/top_tf_hdmi_audio.v:2156` 还会把琶音输入直接替换成零样本。

所以无媒体、未播放时 HDMI 仍可以保持 48 kHz PCM 与 ACR 节奏，但输出是静音。该路径也未引用 SW4。

原交互文档的“琵琶音警告”没有落实成当前任一输出链路。源码中的 arpeggio 指琶音旋律，不能仅凭生成器文件存在就认定故障告警已接入。

母板物理 `BUZ_SW/SW5` 是蜂鸣器供电回路开关，与 FPGA 上的 SW4/C5 分开。硬件开关即使接通，也不会补上缺少的故障触发逻辑。

## 4. 参数保存：请求、写入、反馈分别存在与缺失

母板 KEY3 请求链路确实存在：

```text
KEY3/B1
  → board_key_fall_pulse[2]
  → key3_save_pulse
  → ui_param_persistence.manual_save
  → w25q64_param_store
  → 回读/提交完成 store_done
  → 更新 saved_params / saved_valid / LED2
```

### 按下母板 KEY3 时

`src/io/expansion_integration.v:437` 的普通按键发声源为：

```verilog
assign key_press_any = (|key_fall_pulse) | board_key_fall_pulse[1];
```

这里包含扩展板按键和母板 KEY4，而母板 KEY3 是索引 `[2]`，没有纳入该发声源。因此保存请求可以产生，按键提示音却没有产生。

### 保存完成时

`ui_param_persistence` 内部接收到 `store_done` 后，更新已保存快照与状态；对外提供恢复数据、LED 状态和 SPI 引脚，没有保存成功/失败音效事件端口。顶层和 `buzzer_feedback` 也没有消费这一完成状态。

自动保存同样进入这条完成路径，因此也没有完成音。红外 E6 的普通红外提示音只能说明接收/操作事件发生，不证明擦除、编程、回读和提交已全部完成。

`阶段4_SPI_Flash参数持久化_交付与验收.md:72` 本来就说明成功反馈使用 LED，蜂鸣器保持原逻辑。这与用户现在期望的保存音效存在差距。

## 6. 后续最小修复方案（本轮尚未执行）

若决定让当前版本满足原告警定义与保存音效需求，建议复用板载蜂鸣器现有发声计数器：

1. **SW4 只控制故障音。** 由消抖后的 SW4 对当前有效媒体/Flash 故障做门控，关闭时停止故障音；普通按键提示、保存成功音保持各自语义。不要直接把 SW4 作为整个蜂鸣器的 `sound_enable`，否则会同时关掉操作音。
2. **故障来源明确。** 媒体当前错误和 Flash 故障可作为告警源；欠载/视频等历史 sticky 标志不能不加分类就永久触发告警。告警周期、持续时长和故障清除行为需先确定。
3. **保存完成后再发成功音。** 从持久化提交/回读成功的 `store_done` 产生一次事件；自动保存与手动保存共用。重复保存没有实际写入时，不冒充又完成一笔提交。
4. **失败与成功区分。** 保存失败可以产生不同提示并保持原 LED；母板 KEY3 的受理短音如果需要，也与最终成功音分开。
5. **明确音效输出。** 建议先用 H11 板载蜂鸣器/EXT1，保持现有 HDMI 静音保活路径。若要求告警从 HDMI 音箱发出，则需另行定义音源优先级、静音键关系和音量策略，变更范围不同。

该方案会改变封版 RTL，需要独立回归与物理构建后才有新 bit；当前只完成排查，原封版文件保持原样。
