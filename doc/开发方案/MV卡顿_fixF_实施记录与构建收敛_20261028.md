### 1.1 仲裁关键代码（`src/SD/sd_card_top.v`）

```verilog
106: localparam [1:0] OWNER_IDLE=2'd0, OWNER_AUDIO=2'd1, OWNER_MV=2'd2, OWNER_FAULT=2'd3;
108: wire sel_mv = (owner == OWNER_MV || owner == OWNER_FAULT);
109: wire sd_sec_read_eff  = sd_sec_read  && (owner == OWNER_AUDIO);
110: wire sd_sec_write_eff = sd_sec_write && (owner == OWNER_AUDIO);
111: assign sd_bus_grant = (owner == OWNER_AUDIO);
116:     OWNER_IDLE: if (cmd17_idle) begin
118:         if (sd_sec_read || sd_sec_write)          owner <= OWNER_AUDIO;
119:         else if (mv_burst_req && !mv_burst_abort) owner <= OWNER_MV;
121:     OWNER_AUDIO: if (sd_sec_read_end || sd_sec_write_end ||
122:                      (cmd17_idle && !sd_sec_read && !sd_sec_write))
123:         owner <= OWNER_IDLE;
124:     OWNER_MV: if (mv_burst_done) owner <= mv_burst_error==0 ? OWNER_IDLE : OWNER_FAULT;
125:     OWNER_FAULT: owner <= OWNER_FAULT;   // 只能由 media_supervisor 复位总线
```

三条不变量：

- **只有一个 owner 能驱动命令通道**：`cmd_req/cmd/cmd_r1/cmd_data_len/block_read_req/multi_*` 全部 `sel_mv ? mv_* : cmd17_*`（206–216 行）；回执按 `sel_mv` 分流（217–226 行）。
- **音频请求不会被 MV 抢占**：`sd_sec_read_eff` 只在 `OWNER_AUDIO` 下有效，MV 期间音频控制器根本看不到自己的请求在执行，也不会计时（见 1.2）。
- **暂停而不是打断**：`sd_card_top.v:176` `.abort(mv_burst_abort || (sd_sec_read && mv_burst_pause))` —— 音频到来时 MV 的 CMD18 只在**块边界**（`burst_pause = (buf_count == 2'd2)`，`mv_sd_burst.v:136`）停下，绝不在块中间发 CMD12。

### 1.2 看门狗根因修复（`src/SD/sd_sector_adapter.v`）

```verilog
parameter USE_BUS_GRANT = 1'b0;
input bus_grant;
...
else if (busy_reg && (!USE_BUS_GRANT || bus_grant))   // 等总线的时间不计入 250 ms
```

fixD/fixD2 的 `err=05`（`ERR_RD_TMO`）根因就在这里：MV 抢占总线时音频的 250 ms 看门狗仍在跑。修好之后，"等授权"与"总线坏"在时间语义上彻底分开。

### 1.3 CMD18 与双 bank（`src/video/mv_sd_burst.v`）

- `66: wire start_burst = allow_q && stream_active && sector_req && !buf_ready && !burst_req && !burst_active && !out_active && !out_pending && !err_pending && (buf_count != 2'd2);`
- `84: wire pause_stop = burst_req && burst_pause && (!stream_active || (!sector_req && !out_active && !out_pending && (idle_cnt == 12'd4095)));`
- `82: wire stale_full = (buf_count == 2'd2) && sector_req && (buf_lba0 != sector_lba) && (buf_lba1 != sector_lba);`（切歌/跳转导致两 bank 全过期 → 允许停流冲刷）
- 存储用**显式 `EG_PHY_BRAM32K` DP16K / 16 位**原语（1 024 B = 2 bank × 512 B）：设备 9K 块已经 64/64 全部分配（帧 FIFO、音频 staging、厂商 ROM/FIFO、ASCII 字库），再推一个 1 024×8 的推断 RAM 会变成 65/64。注释原文在 `mv_sd_burst.v:92-97`。
- 仿真模型由 `ifdef VINYL_MV_BURST_BEHAV` 提供同契约（一拍读）的 `reg [7:0] mem [0:1023]`。

### 1.4 seek 归零回归（fixF.1，实板发现后补修）

**现象**（用户在烧写了 §0 第 4 条那个 bit 的实板上直接复现）：转动进度条做 seek，数码管位置显示正确，但 MV 画面与歌词都回到 0，看起来“从头开始播放”。

**为什么基线没有这个问题**：基线里 `restart` 优先于 `load`，seek 时 `load_sample` 生效、`cur_time_ms` 拿到目标值，所以只有“切歌冻结 2.4–2.6 s”这一个缺陷；P1 把优先级反过来修切歌，就把 seek 一起清零了。

**根因链（四段，全部逐行核对）**

| # | 位置 | 机制 |
| --- | --- | --- |
| A | `src/top_tf_hdmi_audio.v:572` | `play_track_restart_vid = play_track_tgl_v2 ^ play_track_tgl_v3`：**seek 与切歌共用同一根 restart 脉冲**（`seek_controller` 拉 `restart_req` → `src/audio/play_ctrl.v:47` `restart_request = restart_request_int \| seek_restart_in` → `stream_session` 停/启一次 → `start_toggle` 翻转），二者只差 `load_sample` |
| B | `src/audio/timebase_48k.v`（P1 之后） | `restart` 分支先命中并清零 `cur_time_ms`，`load_sample = 目标样本` 被丢弃 → `lyric_time_ms = 0` → `lrc_window_controller` 回到第一行 |
| C | `src/video/s6_video_layer.v:74`（P2 之后） | `.seek_frame((restart \|\| track_changed) ? 16'd0 : seek_frame)` → seek 时 `seek_frame = 0` → `mv_frame_scheduler` 的 `rst_frame = 0` |
| D | 定位器时序（`src/top_tf_hdmi_audio.v:1408-1427`） | 目标样本 / 4800 是**逐拍串行减法**，5 分钟 MV（约 14 400 帧）要 576 µs 才稳定；而 `stream_session` 的重启只要 ≥32 个 sd 拍（约 330 ns）。`settle==4'd15` 只等 0.6 µs，重启后就能发请求，于是请求落在“中途的 rst_frame”上，闪一帧旧位置的画面。旧代码把 `seek_frame` 钉成 0，因此这条路径被掩盖（表现为“从第 0 帧开始”） |

**同一网表、同一 seed，只改这 9 条参数，WNS 从 −732 变 +116（848 ps 摆动）。** 这是本次最重要的工程结论：该设计在 95% 占用下，时序闭合由物理综合参数主导，不是 RTL 面积问题。

### 3.2 三条教训（不要重犯）

1. **`set_user_params -run phy_1 -params {{place seed 3}}` 不换 seed。** 它只打印 `PRJ-1106 : Update wild param phy_1 place::seed::3 succeed`，`run.log` 仍打印 `Settings Minimum Seed = 7`、`[1/1] Start running seed 7`。早期所有"换 seed"实验其实都是 seed 7。要换 seed 必须改 `prj/VinylFPGA.al` 里 `<Property ... Num="1" Init="N">` 的 `Init` 和 `<Seeds>N </Seeds>`（注意实际标签**没有** `select` 属性）。
2. **在 94–95% 占用的网表上，+44 LUT 就足以毁掉可布性。** 两处工艺流水线（`fat32_media_loader` 预移位寄存、`seg_business_mux` 采样寄存）综合只增加 `+44 LUT / +13 组合`（r6 `#lut` 17 653 → r8 18 105），却让 seed 3 直接 −1046 ps、seed 7 布线发散。这两条流水线**本来想修的正是闭合后最差的三条路径**——事实证明不加工艺流水线也能闭合，所以回退是正确的。
3. **布线发散的识别信号**：`Stage 2.4.1.2 Rip-up And ReRoute` 每轮 `time(s)` 从 47 s 涨到 81 s，同时 `over cnt` 从 555 涨到 641、`len` 从 3.2961e6 涨到 3.31379e6。看到这个组合立刻放弃，不要等。

| +0.190 ns | `fat32_media_loader_m0/audio_size_bytes_reg_reg[10]` | `u_seg_business_mux/remaining_reg[15]` | 9.53 ns |

**net 占 71–80%** 说明瓶颈是布线拥塞后的绕线，而不是逻辑级数。这解释了为什么加寄存器流水线（缩短逻辑）不但没用，反而因为网表变化把 seed 推进坏解。

> 证据链自洽性检查（已做）：`fixF_pr.timing` 里出现 `audio_cluster_m2_d_reg[12]`、且 `u_seg_business_mux` 起点直接是 `audio_size_bytes_reg_reg[10]`（**无** `sample_position_q`）—— 说明综合用的确实是回退后的源码；同时出现 `u_mv_cmd18_reader/cmd_reg`、`u_mv_sd_burst/buf_count_reg[1]` —— 说明新模块确实进了网表。
