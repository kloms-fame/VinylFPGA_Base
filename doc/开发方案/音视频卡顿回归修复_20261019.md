# 音视频卡顿回归修复（2026-10-19）

本轮以用户明确指定的稳定提交 `9fbbf5be75353debca4be674e1684dd315a50dfe` 为功能参照，直接修复 main。用户反馈：起播先出现封面，稍停后正常播放，随后间歇出现音视频卡顿。此前的内部时序/单模块 PASS 没有覆盖实际共享 SD 服务的储备恢复预算；本次补上该覆盖并恢复已上板使用的音频优先策略。没有改写物理 SD 卡，也没有退回已过时的 R5 诊断工程。

## 交接包与稳定版本核对

只读查看 `音频卡顿修复_教程与交接包_20261016_v2.zip`：执行教程、README、manifest、补丁及 8 个 R5 RTL 的内容/差异。ZIP CRC 检查正常，8 个 R5 源副本的 LF 哈希全部匹配包内 manifest。交接包的旧基线为 `1f9013a...`，R5 诊断候选内部 setup 尚未通过；不能直接拿该项目模板/旧 bit 替换当前工程。包中的命令作为历史流程资料理解，没有盲目应用旧补丁或覆盖现有 main。

交接资料记录：SD 卡曾在约 4.5–4.9 秒窗口内反复出现约 14.2–14.5 ms 扇区令牌等待；48 kHz、16-bit 单声道音频需 96,000 B/s。稳定方案使用 SDRAM 低字节平面的 1024 扇区环，预填 960、低水位 960、高水位 1008；初始在手 PCM 约 5.12 秒。**环容量没变，不等于持续竞争下仍能保有这些储备。**

对比 `9fbbf5b`，当前 staging、DMA、SDRAM 仲裁、frame_read_write、WAV 播放器和索引解析器均没有本轮功能改动。此前 R5 之后已经完成的时序优化、DMA 延迟返回隔离等保留。本次生产逻辑修复集中在 top 的两个连接：

1. `audio_urgent` 固定为 1，所有音频预取请求严格优先，恢复稳定版 SD 仲裁结果；不再把 15 个 MV 扇区/1 个音频扇区当作恢复带宽保证。
2. MV 允许条件恢复为 `!audio_play_enable_gated || (!mv_audio_low_sync[1] && !cache_prefetch_low)`，音频储备不足 960 扇区时停止准入新的 MV 扇区。已在途的 SD 事务仍完整排空，不中断事务。

原 `prefetch_critical` 384 扇区状态保留为晚期观测信号，生产优先级不再依赖它；注释已更正。960/1008 阈值、环大小、DQM、DMA burst/watchdog、时钟、ADC/SDC 均未改动。封面承接、PLAY 黑闪修复、三缓冲和歌词修复保留。

## 可重复复现与反例

`tb_audio_reserve_priority_top` 编译真实生产 top，只在硬 IP 边界使用 stub，并控制空闲 SD 边界。修改前该用例在“缓存健康但正在补数、音频和 MV 都请求”时失败；修复后 Icarus/ModelSim 均通过。它还检查低储备拒绝 MV、健康且无音频请求时放行 MV、输出 FIFO 紧急条件和非播放状态。

`tb_audio_mv_slow_window` 使用真实 audio_prefetch_sdram、staging、DMA、sector mux，外部使用合成 SD 令牌/字节模型和 SDRAM 读写延迟模型。先进行持续 MV 竞争，再注入 4.9 秒服务预算的慢窗口，随后检查缓存重新补到 960 扇区和 MV 恢复。PCM 每个字节的索引与数据、扇区完成/错误、512B 服务截止期都检查，不只比较计数器。

为缩短仿真，采用加速 HDL 时钟和统一抽象预算：10,000 SD ticks 对应一个 512B 音频扇区的 5.333 ms；慢读事务约 14.54 ms，慢窗口为 9,187,500 ticks。正常服务模型的吞吐上限约 0.94 MB/s，足以单独供音频，但不能持续承担 1.536 MB/s 的 10fps MV 加音频。它刻意验证带宽不足时音频必须受保护，不是本次实体 SD 卡的速度测量，也未完整模拟 SPI、视频 SDRAM 并发与 HDMI。

| 相同负载/模型 | 慢窗前环储备 | 4.9 秒慢窗结果 | 恢复 |
| --- | --- | --- | --- |
| 撤回的 384/15:1 策略 | 430 扇区 | 在慢窗约 2.767 秒处环耗尽并错过音频服务截止期 | 用例故意失败，保留反例日志 |
| 稳定版准入/音频优先 | 1005 扇区 | 完整通过，最低 399 扇区，无数据错序/截止期失败 | 1,555,919 ticks，约 0.830 秒内补足储备且 MV 恢复 |

该反例确认旧策略能导致与反馈相符的回归机制；没有新的实板同步日志，不能声称已唯一解释每次物理卡顿。`tools/verify_audio_service_budget.py --policy stable --output <新目录>` 默认应通过；`--policy regressed` 专门复现已撤回策略，预期非零退出及 `BUDGET_UNDERRUN`，不能混入“全部通过”计数。

`tools/verify_stable_sd_priority.py` 从指定 Git 对象读取不可变的稳定版 mux，只改仿真模块名，与当前 mux 在 `audio_urgent=1` 下逐拍比较全部输出。固定随机序列 100,000 cycles、9,472 次事务通过；这是有界仿真等价比较，并非形式化证明。真实顶层用例另外验证生产连接确实选择该策略。

## 第一轮物理失败与有界等价修正

`audio_video_reserve_repair_20261019_r1` 的 bitgen 虽然结束，但最终 setup WNS −1.838 ns、TNS −14.574 ns、24 个违例端点，保持 WNS +0.027 ns。自动放行检查明确拒绝该候选，未将它作为正式固件；最终物理报告、日志与 routed DB 保存在该轮 `failed_physical/`。没有更换 seed、降低时钟或添加例外来遮盖失败。

最差路径为 FAT 文件读取器 `state_reg[9] → remaining_bytes_reg[17].a`，4 级 LUT、数据扇出 32，数据延迟 11.558 ns，其中 net 延迟 9.810 ns。修正将每字节接受条件中的 32 位“剩余非零”判断保存为本地 `remaining_nonzero`：开始文件时随 file_size 装载，成功接受字节时随 remaining_bytes 在同一边沿更新。它始终等价于剩余计数非零，不增加请求/输出延迟、不改变 LBA、数据、错误或终止语义，并缩短宽计数控制锥。

`tools/verify_fat_counter_equiv.py` 读取 `9fbbf5b` 的原始 FAT RTL 作参考，在同一激励下逐拍比较全部外部输出；19 个场景通过，涵盖空文件、1/17/511/512/513B、跨簇碎片、错误、环、自环、簇范围及末字节/sector_done 同拍。该改动属于首轮失败后必要的时序修复，FAT 相关回归及包含 top 的仿真随后重新执行，不能沿用修改前的 top 输入哈希。
