1. **"已修复卡顿"成立，但只在一种配置下成立。** fixE 的 299.808 s 实板记录（1500 样本、7 次切歌、SD 错误 0、欠载 0、撤销 0、≥1000 ms 长卡顿 0 次）证明了三个独立缺陷都被修好；但这份 bit 是 **minimal-UI + 打开诊断** 的构建（Slice 8799/9800 = 89.79%）。它不能直接当产品固件：UI 是关掉的，UART 也被诊断模块占用。

## 2. 根因复核（三缺陷模型）

三个缺陷**互相独立**，必须分别修，缺一不可。这是本方案把 fixE 拆成 P1~P4 的依据。

### 2.1 缺陷 A：时基 `restart` 被 `load` 覆盖 → 切歌 2.4~2.6 s 冻结

`src/audio/timebase_48k.v`（e65bec4，70 行）里，第 45~50 行的优先级是 `load` 先于 `restart`：

```verilog
end else if (load) begin                 // 45 行：load 优先
    sample_count<=load_sample;
    quotient<=load_sample; remainder<=0; steps<=32; pending_samples<=0;
end else if (restart) begin              // 48 行：restart 永远进不来
    sample_count<=0; cur_time_ms<=0; sub_sample<=0;
    quotient<=0; remainder<=0; steps<=0; pending_samples<=0;
end else begin
```

切歌时 top 会**同一拍**同时拉起 `play_track_restart_vid`（→ `restart`）与 `seek_frame` 对应的 `load`。`load` 胜出后清掉了 `sample_count`，**却没有清 `cur_time_ms`**。接下来的 32 个 video_clk（约 1.28 µs）里，除法器把 `cur_time_ms` 重算成基于旧 `quotient` 的值，调度器看到 `time_ms` 早已越过 `next_time`，于是把 `target_frame` 推到 0x20 附近并把 `next_time` 锁在 3300 ms —— 画面冻结 2.4~2.6 s，直到 `next_time` 被再次追上。

**修复（P1）**：把 `restart` 分支整体移到 `load` 分支**之前**。一行顺序问题，零资源代价。

### 2.2 缺陷 B：陈旧 `seek_frame` 与 `transport_ready` 门控 → 切歌后调度器继续被拖

- `src/video/s6_video_layer.v` 在 `restart` / `track_changed` 的沿上仍然把**上一首歌残留的** `seek_frame` 送给调度器（fixB 用 `.seek_frame((restart || track_changed) ? 16'd0 : seek_frame)` 屏蔽）。
- `src/top_tf_hdmi_audio.v:2358`（e65bec4）把 `transport_ready` 接成 `stream_enable_vid[1] && !seek_frame_busy`；`seek_frame_busy` 由 `seek_frame_target_d` 的分频过程驱动（`1382~1393`），一旦分频器被切歌打断，`transport_ready` 会额外拖住调度器。
- fixA 试图在 `play_track_restart_vid` 分支里硬清 `seek_frame_target_d` / `rem` / `calc_reg` / `busy`——但非阻塞赋值在同一个沿之后才生效，清的是"下一拍"，实际输入仍是旧值，所以 fixA 单独无效。

**修复（P2）**：三处配合——seek 输入在 restart/track_changed 沿被屏蔽、`transport_ready` 去掉 `!seek_frame_busy`、`mv_frame_scheduler` 的复位条件由 `invalidating`（`!enable || restart`）收窄为 `restart`，避免 enable 掉电期间目标被反复重置。

### 2.3 缺陷 C：SD 控制器根本没有"所有权"概念

e65bec4 的 `src/SD/sd_card_top.v` 只有 127 行，是一条**单客户端**管线：`sd_card_sec_read_write` → `sd_card_cmd` → `spi_master`，谁拉 `sd_sec_read` 谁就发 CMD17，没有仲裁、没有 owner、没有"这次事务属于谁"的概念。

于是任何"让 MV 也读卡"的尝试都会踩两个坑：

1. **掐断**：MV 请求把 `sd_sec_read` 组合门控掉（fixD 用 `sd_sec_read && !mv_burst_req && !mv_burst_active`），进行中的音频 CMD17 被半途丢弃；
2. **看门狗误杀**：`src/SD/sd_sector_adapter.v`（90 行）的 250 ms 超时（`SECTOR_TIMEOUT_CYCLES = 32'd25_000_000`，第 10 行；计时在 72~86 行）**只要 busy 就累加**，不管底层是不是在排队等总线。于是"等总线"被当成"卡死"，返回 `ERR_RD_TMO = 8'h05`，`media_supervisor` 随即复位整条 SD 链。

fixD：244 行 `err=05`，8 段各约 1.8 s 后复位。
fixD2：只把门控从"进行中"改成"刚挂起"（`mv_burst_req && mv_cmd17_idle`），183 行 `err=05`，6 段都没完成一帧。
**教训**：用组合逻辑门控去表达所有权，永远会在边界上错；而且 `sd_card_sec_read_write` 的 `idle` 只是 FSM 停泊在 `S_WAIT_READ_WRITE`，**不等于"没有挂起的音频请求"**。

### 2.4 CMD18 不是"提高带宽"，是"摊掉每扇区固定开销"

这是 fixE 真正的技术支点，值得写清楚，否则后人很容易以为"换个更快的卡就好了"。

- SPI 高速分频 `SPI_HIGH_SPEED_DIV = 0` → SCK = 100 MHz / ((0+2)×2) = **25 MHz**。
- 一个 512 B 扇区在线上是 513 B（含 1 B token）≈ 513×8 = 4104 个 SCK ≈ **164 µs**，理论上限约 **6097 扇区/s**。
- 实测平稳段 CMD18 = **3026.5~3027.0 扇区/s**（约 50% 占空比，另一半让给音频/背景/暂停），已经贴近可用上限。
- 实测 CMD17 = **180~188 扇区/s**，即每扇区被分摊到约 **5 ms 级**的固定开销（CS 建立 + 命令 + R1 + 卡内 busy）。**这就是"慢卡"的真相：慢的不是数据搬运，是每条命令的固定成本。**

MV 播放需要 640×480 每帧 300 扇区、10 fps = **3000 扇区/s**，音频 187.5 扇区/s，合计 3187.5 扇区/s，而 3 帧缓存只够 300 ms。用 CMD17 服务 MV，物理上不可能喂饱；用 CMD18 一次命令搬 8 个扇区，固定开销被摊到 1/8，MV 立刻能吃满线速，3 帧缓存才真正"够用"。

**所以 P4（CMD18 突发桥）不是优化项，是必需项。** 只做 P1+P2+P3 可以消除 err=05、可以消除切歌冻结，但播放中"卡几秒"依然存在。

### 5.3 P3 —— SD 总线所有权 + grant 感知看门狗（关键设计）

这是整个方案里最容易做错的地方，fixD/fixD2 就是死在这里。**三条铁律**：

> 铁律 1：所有权必须由**寄存器**表达，不能用组合门控。
> 铁律 2：等待所有权期间**不得**累计超时。
> 铁律 3：CMD17 的挂起请求优先于 MV，且"挂起"要看 `sd_sec_read` 电平，不能看 `idle`。

**`src/SD/sd_card_top.v` 改造后的骨架**（照抄 fixE 的第 109~129 行，去掉 diag）：

```verilog
localparam [1:0] OWNER_IDLE=2'd0, OWNER_AUDIO=2'd1, OWNER_MV=2'd2, OWNER_FAULT=2'd3;
reg [1:0] owner;

wire sel_mv           = (owner == OWNER_MV || owner == OWNER_FAULT);
wire sd_sec_read_eff  = sd_sec_read  && (owner == OWNER_AUDIO);
wire sd_sec_write_eff = sd_sec_write && (owner == OWNER_AUDIO);
assign sd_bus_grant   = (owner == OWNER_AUDIO);   // 送给 sd_sector_adapter

always @(posedge clk or posedge rst) begin
    if (rst) owner <= OWNER_IDLE;
    else case (owner)
        OWNER_IDLE: if (cmd17_idle) begin                             // FSM 已停泊
            if (sd_sec_read || sd_sec_write) owner <= OWNER_AUDIO;    // 音频优先，含同拍
            else if (mv_burst_req && !mv_burst_abort) owner <= OWNER_MV;
        end
        OWNER_AUDIO: if (sd_sec_read_end || sd_sec_write_end ||
                         (cmd17_idle && !sd_sec_read && !sd_sec_write))
                         owner <= OWNER_IDLE;
        OWNER_MV:    if (mv_burst_done) owner <= mv_burst_error==0 ? OWNER_IDLE : OWNER_FAULT;
        OWNER_FAULT: owner <= OWNER_FAULT;      // 只能由 media_supervisor 复位整条链
        default:     owner <= OWNER_IDLE;
    endcase
end
```

然后把 `sd_card_cmd` 的激励源整体二选一：

```verilog
assign cmd_req         = sel_mv ? mv_cmd_req        : cmd17_req;
assign cmd             = sel_mv ? mv_cmd            : cmd17_cmd;
assign cmd_r1          = sel_mv ? mv_cmd_r1         : cmd17_r1;
assign cmd_data_len    = sel_mv ? mv_cmd_len        : cmd17_len;
assign cmd_keep_cs     = sel_mv ? mv_keep_cs        : 1'b0;
assign cmd_wait_busy   = sel_mv ? mv_wait_busy      : 1'b0;
assign block_read_req  = sel_mv ? mv_block_req      : cmd17_block_req;
assign multi_read      = sel_mv ? mv_multi_read     : 1'b0;
assign multi_sectors   = sel_mv ? mv_multi_sectors  : 8'd0;
assign multi_pause     = sel_mv ? mv_multi_pause    : 1'b0;
assign multi_abort     = sel_mv ? mv_multi_abort    : 1'b0;
assign block_write_req = cmd17_write_req && !sel_mv;
```

应答按同一条件反向分发：

```verilog
assign cmd17_ack  = cmd_req_ack && !sel_mv;     assign mv_cmd_ack  = cmd_req_ack && sel_mv;
assign cmd17_error= cmd_req_error && !sel_mv;   assign mv_cmd_error= cmd_req_error && sel_mv;
assign cmd17_block_ack = block_read_req_ack && !sel_mv;
assign cmd17_write_ack = block_write_req_ack && !sel_mv;
assign mv_multi_sector_done = multi_sector_done && sel_mv;
assign mv_multi_read_done   = multi_read_done && sel_mv;
```

**`src/SD/sd_sector_adapter.v` 的一行修复**（第 9~11 行加参数与端口，第 72 行改条件）：

```verilog
module sd_sector_adapter #(
    parameter [31:0] SECTOR_TIMEOUT_CYCLES = 32'd25_000_000,
    parameter        USE_BUS_GRANT = 1'b0
) ( ... input wire bus_grant, ... );

end else if (busy_reg && (!USE_BUS_GRANT || bus_grant)) begin   // 原：end else if (busy_reg) begin
```

含义：**只有拿到总线才开始计时**。等总线的 5 ms、50 ms 都不算超时；一旦拿到总线 250 ms 没动静，才是真卡死。

**`src/SD/sd_card_sec_read_write.v`**：新增 `output idle`，`assign idle = (state == S_WAIT_READ_WRITE);` —— 仅用于 owner FSM 判断"FSM 是否停泊"，**不用于判断请求是否存在**（见铁律 3）。

**`src/SD/fat32_media_loader.v`**：加 `parameter USE_SD_BUS_GRANT = 1'b0` 与 `input sd_bus_grant`，把 `USE_BUS_GRANT` 传给第 981 行的 `sd_sector_adapter` 例化；`src/SD/sd_card_bmp.v` 只做端口透传 + 在 595 行的 `sd_card_top` 例化里把 `sd_bus_grant` 接出去。

### 5.4 P4 —— CMD18 突发读 + 双 bank 桥

三块拼图：

**(1) `src/SD/sd_card_cmd.v`（353 → 约 528 行）** 新增 9 个状态：

| 状态 | 编号 | 作用 |
| --- | --- | --- |
| `S_CMD_BUSY` | 18 | R1b 后等卡释放 busy（`cmd_wait_busy`） |
| `S_MULTI_WAIT` | 19 | 等 CMD18 的第一个 `0xFE` token |
| `S_MULTI_READ` | 20 | 收 513 B；未满继续发时钟，满则 `sec_left-1` + `multi_sector_done` 单拍 |
| `S_MULTI_HOLD` | 21 | 桥要求暂停时**停掉 SPI 时钟**（`spi_wr_req<=0`），数据不丢 |
| `S_MULTI_SECTOR_END` | 22 | 等 `multi_settle` 一拍（桥的 bank 计数要晚一拍才对）再判 pause/sec_left |
| `S_MULTI_END` | 23 | 产生 `multi_read_done` |
| `S_MULTI_ABORT` | 24 | 中止后清请求 |
| `S_WAIT_REQ_LOW` | 25 | 等 `block_read_req` 落下，避免双触发 |
| `S_RELEASE` | 26 | 拉高 CS 并补一个 0xFF 收尾 |

三个最容易漏的细节：
1. `S_CMD_PRE` 里 `CS_reg <= cmd_keep_cs ? 1'b0 : 1'b1;` —— CMD18 之后要接 CMD12，**中间不能抬 CS**。
2. `S_WAIT_RESP` 里前 6 个字节不判 R1，且 CMD12 在第 7 字节多丢一个 stuff byte：`if(byte_cnt < 16'd6 || (cmd[45:40]==6'd12 && byte_cnt==16'd6)) byte_cnt<=byte_cnt+1;`
3. `block_read_valid` / `block_read_data` 的条件必须加上 `state==S_MULTI_READ`，否则 CMD18 的数据会串到 CMD17 的消费者。

**(2) `src/SD/sd_cmd18_reader.v`（新，242 行）** —— 有界 MBR 的所有者：发 CMD18 → 收块 → 结束时发 CMD12；`pause` 由桥在块边界拉起；`active` 用**寄存器**（`active_r`）而不是比较编码后的状态向量（综合工具会把状态一位热编码，和字面量 0 比较是错的——这一条 fixE 里已经踩过）。

**(3) `src/video/mv_sd_burst.v`（新，253 行）** —— 把"一次一扇区"的 `mv_stream_player` 接口，包装成"8 扇区突发 + 双 512 B bank"：

```verilog
localparam [7:0] BURST_SECTORS = 8'd8;
(* ram_style = "bram" *) reg [7:0] mem [0:1023];   // 2 × 512 B，推断成 BRAM
wire rd_match0 = full[0] && (buf_lba0 == sector_lba);
wire rd_match1 = full[1] && (buf_lba1 == sector_lba);
wire rd_sel    = rd_match0 ? 1'b0 : (rd_match1 ? 1'b1 : rd_buf);   // 按 LBA 命中选 bank
```

**为什么必须"按 LBA 命中"而不是"轮转"**：播放器可能在另一个 bank 还没填满时就把当前 bank 读完，被腾空的 bank 会立刻被填成"下一扇区"，此时若按固定轮转选 bank，读到的就是错的那一格。

**BRAM 推断坑（fixE 已踩过，务必照抄结论）**：`ram_style="block"` + 读写写在同一个 `always` 分支里 → `SYN-5042`（`u_mv_sd_burst/ramread0_syn_5`）。正确写法是 **专用写块 + 专用读块两个 `always`，`ram_style="bram"`**，得到 `SYN-1026 PDPW/SP BRAM`。

**(4) `top` 接线**：`mv_stream_player` 的 `sector_*` 从 `media_raw_*` 改接 `mv_sec_*`（即 `mv_sd_burst` 的输出）；`mv_sd_burst` 的 `burst_*` 接 `sd_card_bmp` 新增的 `mv_burst_*` 端口；`mv_sd_burst` 的 `abort` 先固定 0（只在块边界停），`allow` 接混合后的 `mv_video_allowed`。

### 5.5 附带修复 —— WAV 欠载误报

`src/audio/wav_stream_player.v` 的 `buffer_available`：起始阶段要求 `level_rd >= SAMPLES_PER_SECTOR`，但一个扇区尾部只剩 255 个样本时会被误判 underrun。改为三选一：

```verilog
assign buffer_available = (startup_ready && level_rd > 0) ||
                          (!startup_ready && level_rd >= SAMPLES_PER_SECTOR) ||
                          (finished_sync[1] && level_rd > 0);
```

这条与卡顿无关，但它让串口日志的 `underrun` 计数变成可信指标——**没有它，你就分不清"视频卡"和"音频卡"**。

## 7. 资源预算与降级阶梯

### 7.1 预算推算

| 项 | Slice | 依据 |
| --- | --- | --- |
| e65bec4 全 UI 基线 | 9317（95.07%） | 实测 QoR |

### 7.2 时序余量同样吃紧

基线 Setup WNS 只有 **+0.143 ns**、Hold **+0.037 ns**：任何超过约 143 ps 的新增关键路径都会让 setup 崩掉。而历史上 9570 Slice 构建给出 **route WNS −1.744 ns / 188 条违例**，最差路径是

```
sd_card_bmp/fat32_media_loader_m0/audio_size_bytes_reg -> seek_cur_sample_sd_reg
data 11.464 ns / net 8.587 ns / 7 levels
```

**这条路径本来就在 SD 子系统里**，而 P3/P4 恰恰要往这里加逻辑。所以本方案的态度是：先按最保守组合做一版（L1 必做），量出真实数字，再决定是否继续裁。

### 7.3 降级阶梯（先测后裁）

| --- | --- | --- | --- | --- |
| **L0** | 不裁剪，全 UI + P1~P4（去诊断） | 0 | 预计 98%+，大概率违例 | 仅作"量红线"的探针构建，不做产品 |

## 13. 需要你拍板的决策点

1. **L3 裁剪是否可接受？** 若 L1+L2 仍超 96%，就要动波形显示 / EC2 OSD / 播放页背景 / boot logo 这类可见功能。**这些是产品取舍，我不替你决定。** 建议顺序：先关波形（最不影响观感）→ 再关 boot logo → 最后才考虑播放页背景。
2. **是否接受"只做 P1~P3"的中间版本上架？** 该版本能消除 err=05 与切歌冻结，但播放中仍会出现秒级卡顿。技术上不建议，但如果交付节点紧，它是可用的降级点。
3. **是否把 MV 帧率从 10 fps 降到 8 fps？** 这是一个"绕过带宽"的选项：3000 → 2400 扇区/s，能给 SD 总线留出 25% 余量，代价是画面流畅度下降。**本方案未纳入**，因为 fixE 已证明 10 fps 可行；仅作为 L4 之后的备选。
4. **是否保留 `background_sector_mux`？** P4 之后 MV 不再走这个仲裁器，建议删除（L1）。若未来还想让 MV 走 per-sector 通路做对比，就保留但置空。
5. **诊断能力是否保留在独立分支？** 建议保留 `codex/mv-fixE-20261028` 分支 + `mv_diag_uart` 作为"下一轮排查的工具"，但**不与产品固件同流**。

## 结语

这次修复的价值不在"改了 13 个文件"，而在三个判断：

1. **三个缺陷是独立的**——切歌冻结（时基）、调度拖死（视频）、总线饥荒（SD）。把它们混在一起调，就会像 fixA/fixB 那样修一个掩盖另一个。
2. **CMD18 解决的是固定开销不是带宽**——CMD17 每扇区 5 ms 的命令成本，让"喂 3000 扇区/s 给 640×480@10fps"在物理上不可能。认清这一点，就不会再去纠结"换张快卡"。
3. **资源是这次落地的真正对手**——95.07% 的基线、只剩 143 ps 的 setup 余量，意味着"把验证过的 bit 直接搬进产品工程"必然失败。方案里的 L1~L4 不是保守，是被实测数据逼出来的。

fixE 已经证明这条路能走通（5 分钟零错误、零长卡顿），剩下的工作是把 89.79% 的"取证配置"变成 96% 以下、时序收敛、UI 完整的"产品配置"。**做完 Stage 0 再动手**，其余按阶段推进即可。
