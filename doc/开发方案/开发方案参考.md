# 第三阶段：为 FPGA 增加低开销串口诊断

## 3.1 先核实现有串口硬件条件

本项目是 FPGA RTL 工程，不能直接照搬 MCU 中 `printf()` 的使用方法。

请先检查：

1. 当前 FPGA 顶层是否已有 UART TX/RX 模块。
2. 原理图、PCB、引脚约束中是否存在可用的 UART 输出引脚。
3. 是否能够通过板载 USB-UART、下载器或外接 USB-TTL 访问串口。
4. 目标板使用的串口电平、波特率、引脚映射及复位条件。
5. 是否存在可复用的 UART IP、发送 FIFO 或调试接口。

如果没有可用的串口硬件路径，先说明需要增加的最小硬件连接或接口条件，不得凭空指定引脚。

尽可能只增加 UART TX 输出，不必为了监测而无必要地增加 UART RX。

如果已有可用接口，应优先复用。

## 3.2 诊断模块的结构

建议将诊断逻辑独立成模块，例如：

- `mv_stutter_monitor.v`：收集关键状态、计算耗时、检测异常。
- `uart_diag_tx.v`：负责串口数据发送。
- 顶层连接逻辑：提供必要的状态信号和事件脉冲。

实际文件名应先检查现有项目命名规范，避免重复建设。

要求：

- 诊断逻辑与核心音视频数据通路解耦。
- 不修改核心状态机的行为来适配日志输出。
- 采用事件触发、计数器或低频周期采样方式收集数据。
- 高频采集与低频发送分离。
- 诊断模块可通过参数或编译配置完全关闭。
- 关闭诊断后，核心播放行为不应发生变化。
- 不允许日志发送直接阻塞 SD 读取、音频供数、SDRAM 写入或视频调度。

建议采用固定宽度事件记录或预分配缓冲区。只有在资源允许且确有必要时，才引入更复杂的事件队列。

## 3.3 重点监测 SD 卡服务延迟

参考资料指出，当前生产路径使用 SD CMD17 单扇区读取，并在数据 token `0xFE` 到达之前等待。

请围绕实际生产路径监测：

- SD 请求开始时刻。
- CMD17 发起时刻。
- 收到数据 token 的时刻。
- 扇区读取完成时刻。
- 单次请求总耗时。
- token 等待耗时。
- 连续请求间隔及最大等待。
- 超时、错误及无进展事件。

同时记录必要的请求状态、扇区地址或媒体读取上下文。

应优先记录关键时间点和统计值，不要每个 SPI 时钟或每个字节都发送串口日志。

如果当前 SD 控制器内部状态无法直接输出，可增加只读的诊断信号或事件脉冲，但不得改变原有状态机时序。

## 3.4 重点监测音频储备

- `LOW=960` 扇区。
- `HIGH=1008` 扇区。
- 音频低水位时严格优先音频请求。

围绕以下链路记录关键事件：

至少监测：

- 暂停、恢复、Seek、切曲和重新启动事件。

如果已经有可用的帧号、ready bitmap 和写完成状态，应优先复用，不要重复实现整套监测状态机。

# 第四阶段：以证据为依据定位两个卡顿问题

## 4.1 先建立可重复的诊断基线

在修改核心播放逻辑前，先使用诊断版本复现问题。

分别执行：

- 正常播放。
- 播放中出现卡顿的场景。
- 连续切歌。
- 冷启动后首次播放。
- 热启动后再次播放。
- 暂停与恢复。
- Seek 与返回浏览。
- 关闭串口诊断后的对照测试。

记录实际使用的 Bit 哈希、媒体镜像哈希、歌曲编号、测试时长和发生卡顿的时间点。

如果尚未完成实板测试，应明确标记为模型结果或待实测，不得伪造硬件日志。

## 4.2 分析播放中的卡顿

首先围绕一次实际停顿建立事件时间线。

例如：

- T0：显示帧号停止推进。
- T1：MV 扇区请求开始。
- T2：SD token 到达。
- T3：最后一个扇区读取完成。
- T4：SDRAM 写完成。
- T5：帧进入 ready 队列。
- T6：下一帧实际显示。

同时记录同一时间窗口内的音频缓存占用、SD 请求状态、MV 准入状态和 writer 状态。

根据实际证据区分以下情况：

### 情况 A：SD 卡读取延迟

如果 SD token 长时间未到，或单扇区请求总耗时异常，则继续检查 SD 状态机、卡响应和请求仲裁。

### 情况 B：音频补缓存导致 MV 等待

如果音频储备降至低水位，MV 请求长时间未获准，则检查真实缓存变化、音频补缓存耗时与视频未来帧余量。

不能因为 MV 等待发生在音频 refill 期间，就直接认定应降低音频优先级。

### 情况 C：SD 已完成，但 SDRAM 写入迟迟未完成

如果 SD 数据已经读完，而帧完成 toggle 迟迟未到，则转向检查：

- 写 FIFO 是否排空。
- SDRAM 写请求是否被阻塞。
- 写入 mask 和 tail 处理。
- 帧写完成握手。
- 缓冲区与跨时钟域同步。

不要继续盲目修改 SD 配额。

### 情况 D：帧已准备完成，但调度器没有显示

检查：

- ready bitmap。
- 显示、pending、未来和写入 bank 的保护关系。
- 帧标签和目标帧号。
- vblank 更新逻辑。
- 过期帧清理。
- 暂停、Seek、restart 及旧事务排空机制。

### 情况 E：目标帧更新，但画面没有推进

检查显示帧号、显示 bank、垂直消隐边界以及帧切换条件，区分正常保持上一完整帧和调度异常。

### 情况 F：帧号持续推进，但视觉上仍有停顿

检查是否属于原始媒体中的重复帧或正常静止内容。

参考资料已列出部分重复帧时间段，应将它们作为内容侧排除项，而不是直接当作硬件故障。

## 4.3 分析歌曲启动时的 2–3 秒卡顿

建立从播放请求到音频稳定输出、MV 首帧显示的分阶段耗时表。

至少回答：

- 音频缓存预填充是否占用了主要时间？
- 音频输出是否在 MV 首帧准备完成之前已经开始？
- 是否存在同步等待导致音频和 MV 被不必要地绑定启动？
- 首次资源读取、解码器初始化、SDRAM 访问或任务启动是否产生长延迟？
- 热启动和冷启动是否存在明显差异？
- 第二次播放是否复现相同问题？
- 串口日志是否改变了问题的发生概率或耗时？

只有确定主要耗时阶段后，才能提出针对性优化。

如果现有播放架构允许音频先稳定启动、MV 在后台准备首帧，可评估这种方案；但必须确保不会破坏现有音视频同步、暂停、切歌和错误恢复机制。

| ------- | ------------ | -------- |
| LUT     | 18096        | 19600    |
| REG     | 12047        | 19600    |
| BRAM9K  | 64           | 64       |
| BRAM32K | 1            | 16       |
| DSP     | 10           | 29       |

以上数据不是当前基线的自动保证，必须在指定提交上重新构建后核实。

重点约束：

1. BRAM9K 已经没有剩余容量，不允许未经预算直接增加 BRAM9K。
2. LUT 和 REG 余量有限，新增串口和诊断逻辑应尽量轻量。
3. 优先使用已有状态、计数器和事件脉冲。
4. 评估是否能够通过 SDRAM 紧凑存储、bank 复用和访问效率优化提升视频抗延迟能力。
5. 任何复用封面或背景区域的方案都必须核对资源生命周期、显示切换、返回浏览和内存 mask。
6. 不得把 PCM 低字节环形缓存误认为可以无条件占用的空闲图像内存。

## 5.2 优先评估六帧缓存方案

参考资料记录的六帧缓存方案具有以下特点：

- RGB565 两个像素共用一个 32-bit word。
- 在既有 MV 分区内储存六帧。
- 满队列时最多保有五帧未来画面。
- 没有额外增加帧 RAM 或 DSP。
- 最终整工程 LUT 增加 132、REG 增加 128。
- 最终 setup WNS 只有 +0.001 ns。

请先确认这项优化是否已经存在于当前基线。

如果存在，优先分析实板仍卡顿的原因，不要重复实施同一套六帧缓存修复。

如果不存在，评估移植所需的完整依赖、资源地址、像素解包、读写 mask、帧调度和回归测试，再决定是否采用。

不要将六帧缓存视为能够无限吸收 SD 卡延迟的方案。有限缓存只能增加系统对短时服务波动的容忍度。

## 5.3 优先优化已测量的瓶颈

根据诊断结果选择适当方向：

- 若 SD 访问存在明显长尾，分析请求状态机、token 等待及传输开销。
- 若访问效率不足，评估受限连续读取或多块读取；必须保留正确的结束协议和有界音频等待。
- 若 SDRAM 写入存在瓶颈，优化 FIFO 排空、写入握手和资源仲裁。
- 若帧缓存不足，评估现有 SDRAM 区域内的紧凑布局与缓存深度。
- 若调度器存在无效等待，针对具体状态转换优化。
- 若启动阶段耗时过长，优化已经确认的初始化和预加载环节。
- 若内容存在固定重复帧，只在确认属于素材问题时处理素材，不修改无关 RTL。

禁止：

- 无条件恢复历史上曾导致音频回归的 15:1 视频配额。
- 无依据降低音频低水位或取消严格音频优先。
- 为掩盖卡顿而任意跳帧、插入固定延迟或伪造帧率。
- 为减少 LUT 而改变功能正确性或放宽时序约束。
- 在没有实际带宽预算时引入无限制多块读取。
- 通过降低时钟频率、关闭必要功能或修改器件配置来制造表面上的资源通过。
