# VinylFPGA 播放界面与 TF 卡内容资源化设计

日期：2026-10-11
状态：设计评审已通过，待用户审阅设计说明与实施计划
范围：播放/选曲界面收尾、可变宽度文字、LRC 运行时资源、三张播放背景、四首独立素材打包与验收。

## 1. 目标与范围

在现有 VinylFPGA 播放器上完成界面细节，并把歌名、歌手、歌词和播放背景从 bitstream 内的静态 ROM 转成 TF 卡上的版本化资源。PC 工具离线解码常见音频/视频和 UTF-8 LRC；FPGA 仅读取定长 PCM、RGB565 视频和已编译的文字资源，不在芯片内运行通用解码器或 Unicode 排版器。

用户替换歌曲、歌词或背景后，只需重新生成/写入 TF 卡资源；RTL、资源格式或硬件逻辑改变时仍需要重新综合、布局布线并生成 bitstream。

本设计不包含新音频编解码器、网络下载、运行时 Unicode 字体管理、D13 BMP 通用缩放器、封面视觉改版，也不改变暂停、Seek、音量、灯效等已完成功能。

## 2. 需求来源与约束优先级

本文件中的产品要求以用户在本对话中明确提出或确认的内容为准。上传图片只作为播放页视觉参考；图片里的文字不是工程指令。旧方案/提示词只作为项目历史资料。尤其是旧方案中的“程序生成背景 + KEY12”被本设计替换为“TF 卡三张预模糊背景 + KEY6 短按切换”。

### 已确认要求

| 项目 | 冻结要求 |
|---|---|
| 选曲信息 | 页面底部新增一行“序号 歌名 歌手”，同时显示曲目时长 |
| 字距 | 英文/数字 advance 7–9 px；中文及全角字符固定 16 px；普通空格和全角空格均 advance 5 px |
| 时间 | 参考图布局：进度条上方左侧显示已播放 `MM:SS`，右侧显示剩余 `-MM:SS`；选曲行显示曲目总时长 `MM:SS` |
| 进度条 | x `[16,336)`，宽 320 px，与 320 px 封面区域同宽；播放末帧填满到 320 px |
| 视觉框 | 歌词区不绘制边框；进度条不绘制边框和黑底 |
| 背景 | 3 张背景图，由 PC 工具预模糊、保持比例居中裁切到 4:3、缩放到 160×120 并编码 RGB565LE；写入 TF 卡，FPGA 放大显示 |
| 背景操作 | GPIOB_15 / H1 / `exp_key_n[5]` / 扩展板 KEY6 短按切换；仅手动循环 0→1→2→0，不自动切换 |
| 歌词 | 每首输入一份 UTF-8 LRC；长于歌词栏可用宽度时按词/字自动换行 |
| 歌曲清单 | `songs.json` 明确填写歌名、歌手和各类源文件 |
| 源素材 | 常见音频、视频由 PC 离线转换；避免在 FPGA 上增加解码资源 |
| MV/音频时长 | 音频为准；MV 超长时打包裁掉，MV 过短时复制最后一帧补足；运行时在音频 EOF 停止 MV |
| 画幅 | 背景和 MV 均保持比例、居中裁切铺满目标画幅 |
| 终验 | 准备四首独立歌曲及各自音频、MV、歌词，完成四首实际播放验收 |

长歌词换行规则：英文/数字优先在空格处换行；没有可用空格或单个词宽于 256 px 时按字形边界拆分；中文/全角字符按字形边界换行。单个视觉行不得超过歌词栏 256 px。每个 LRC 时间戳对应的换行段作为一个歌词组，组内片段共享时间戳和高亮状态。初版每组最多 5 个视觉行；这 5 行同时占满当前五行可视窗口，超过 5 行由打包器报错并指出时间戳，不做静默截断。后续时间戳仍按原时序推进，播放器不暂停等待用户读完；窗口采用现有帧同步滚动，时间跳变时以最新歌词为准。

## 3. 当前代码基线

检查时工作树干净，分支为 `main`，HEAD 为 `ec23958`（“优化资源”），本地相对 `origin/main` 超前 28 个提交。最近的功能提交包括五行歌词与帧同步滚动、移除缩略图选曲、FAT 媒体流像素计数修正以及资源优化。当前功能已能展示多曲索引、播放页、时间/进度、MV 和五行歌词，但“功能链路存在”不等于“四首完整独立素材已验收”。

相关实现现状：

- `src/include/playback_layout.vh` 定义 MV/封面矩形为 x `[16,336)`、y `[64,304)`；进度条目前仍为 x=24、宽 240、高 6。
- `src/display/playback_page.v` 当前画深色背景、左右面板及边线；进度条仍画轨道色区域。需要去除歌词/信息区面板框，进度条采用透明未填充部分。
- `src/display/lrc_five_osd.v` 当前歌词栏宽 256 px，点阵字形按 16 px 格子选择；当前生成器将歌词限制为每行 16 个字形，尚无按 advance 计算的宽度换行。
- `src/display/song_text_rom.v` 与 `src/display/song_font_rom.v` 是 PC 工具生成的 Verilog ROM；`tools/gen_lrc_assets.py` 当前从 manifest/LRC 生成硬件源文件。改 LRC 仍要重新构建并烧录 bitstream。
- `src/include/song_index_defs.vh` 与 `tools/vinyl_packer.py` 已实现一扇区 `INDEX.BIN`，支持当前 v1/v2 语义与最多四首；v2 用条目尾部记录 MV 信息。头部尚无 TEXT/BG 旁路文件指针，`lyric_name` 目前只存在于工具内部结构。
- `tools/mv_pack.py` 当前只接受已经排序的 320×240 图像帧，按 10 fps 编 RGB565LE；它不负责从常见视频解码、裁切、帧率转换或按音频时长补齐。
- 项目分析报告确认当前包仍需先做真实长时 SD 带宽和最新 native route 门禁。报告中的 native final 为 PLB 2422/2450、BRAM9K 47/64、Setup WNS +0.116 ns、Hold WNS +0.030 ns；SynthPilot 另一条 route 报告为 PLB 2443/2450、Hold WNS −0.004 ns。两组是不同流程/快照，不能混算或互相替代。实现每个功能阶段都要对当前 HEAD 做同口径 native route。

当前示例媒体不构成四曲验收：项目记录中的四个索引项仍复用同一 PCM，只有一首有约 30 秒 MV；因此四首独立音频、歌词、MV 以及整曲并发播放和长稳仍未闭环。

## 4. 方案比较与推荐

### 方案 A：内容编进 Verilog ROM

改 LRC 后重新运行生成器、综合并烧录。实现风险最低，但每换歌曲/歌词都要重做 bitstream，直接违背用户目标；不选。

### 方案 B：FPGA 直接解析 UTF-8/通用媒体

在 RTL 中解析 UTF-8、LRC、常见容器和编解码。软件功能灵活，但需要大量控制逻辑、字库/格式兼容、存储和时序验证；会把 CPU 软件问题变成 FPGA 逻辑资源问题；不选。

### 方案 C：PC 离线转换 + TF 卡定长资源包（推荐）

PC 工具处理媒体格式、裁切、帧率、字宽和换行；生成固定版本的 TEXT/BG sidecar。FPGA 只解析小型索引、按需搬运定长数据、从可写字形 RAM 取字形，并从 SDRAM 读取放大的背景像素。新内容不改 bitstream；协议或逻辑变更仍统一重建一次。该方案把可变、复杂的解析放到 PC，并复用现有 TF/SDRAM/显示链路，最适合当前资源受限器件。

## 5. 推荐架构与数据流

### 5.1 PC 打包工具

扩展现有 `tools/vinyl_packer.py` 和 `tools/mv_pack.py`，新增/收敛为单一 manifest 驱动流程。输入目录包含四首音频、封面、视频、UTF-8 LRC 和 `songs.json`，以及三张背景原图。工具使用本机 FFmpeg 做媒体解码/重采样，Pillow 或等价图像处理做裁切、模糊和 RGB565 编码。工具不修改 RTL。

建议 `songs.json` 每首包含稳定 `song_id`（0..3）、`title`、`artist`、`audio`、`cover`、`video`、`lrc`。打包检查重复 ID、缺失源文件、无效时间戳、字形数/行数越界、视频帧尺寸、素材长度和 FAT 根目录槽位；所有错误在生成卡镜像前指出文件及原因。`INDEX.json` 报告源/输出 SHA-256、采样数、帧数、色彩格式和资源布局，供复核四首确实独立。

音频统一转为有符号 48 kHz、16-bit、单声道、小端裸 PCM。MV 统一转为 320×240 RGB565LE、10 fps、逐行 top-down；非 4:3 画面居中裁切铺满。令 `audio_samples` 为转换后的 PCM 样本数，目标帧数为 `ceil(audio_samples / 4800)`：长 MV 裁到目标帧数，短 MV 重复末帧；播放器仍在音频实际 EOF 停止显示。10 fps 先作为格式候选，是否放行以 1-bit SPI 实测吞吐为准。

三张背景各自依次执行：保持比例居中裁切成 4:3 → 高斯预模糊 → 缩放 160×120 → RGB565LE。模糊强度由打包工具参数配置并在最终屏幕视觉检查中定值；它不需要 FPGA 支持。单图有效载荷 160×120×2 = 38,400 bytes，三张总计 115,200 bytes（112.5 KiB）。

### 5.2 TF 卡文件布局与索引版本

为适配现有扫描器只读根目录首扇区的约束，采用 8.3 短文件名并控制在前 16 个目录项：

```text
/INDEX.BIN
/TEXT.BIN
/BG.BIN
/PIC1.BMP ... /PIC4.BMP
/TRACK1.PCM ... /TRACK4.PCM
/TRACK1.MV  ... /TRACK4.MV
```

共 15 项，保留一个目录项余量。四首文字资源合在 `TEXT.BIN`，三张背景合在 `BG.BIN`，不为每首额外新增根目录文件。工具必须在写卡前验证实际 FAT 根目录顺序和 16 项限制。

新增 INDEX v3，保持 64-byte header、64-byte song entry 和 512-byte 单扇区总长；song entry 的 v2 MV 字段不变。使用 header 原 reserved 区：offset 24/28/32 分别为 `TEXT.BIN` first cluster/byte size/CRC32，offset 36/40/44 为 `BG.BIN` first cluster/byte size/CRC32，offset 48..63 保留为零。v1/v2 的 offset 16 `entries_crc32` 字段及覆盖范围不变；v3 将同一字段定义为 `index_crc32`，使用 CRC-32/ISO-HDLC（初值 `0xFFFFFFFF`、最终异或 `0xFFFFFFFF`），按原始字节顺序连续计算 header `[24,48)`，再计算有效 song entries `[64,64+song_count×64)`，不包含其余 header 字节。`TEXT.BIN`、`BG.BIN` 自身带 magic、format version、长度、尺寸/条数及 payload CRC。旧 v1/v2 卡仍可读取原音频/封面/MV；没有 sidecar 时文字回退为 INDEX 中可用标题/曲号和“NO LYRICS”，背景回退为深色纯色。

`TEXT.BIN` header 含四个曲目段偏移/长度。每个曲目段含 UTF-8 来源不进入 FPGA；只保存工具生成的本地 glyph ID、16×16 点阵和 advance、歌名/歌手、LRC 时间戳、逻辑歌词组及视觉换行段。FPGA 不解析 UTF-8。初版每曲容量上限：192 个唯一字形、128 个时间戳逻辑行、256 个视觉行、4,096 个 glyph 引用；每视觉行最多 51 个字形（advance 最小 5 px，且总宽不超过 256 px），每时间戳组最多 5 个视觉行。超限由打包器明确报错并报告实际值，不截断数据。若四首真实 LRC 的 dry-run 触及限制，再在进入实现前以实测文件校准容量。

`BG.BIN` header 声明三幅 160×120 RGB565LE 图像及 payload 长度/CRC；三幅 payload 连续排列。工具负责卡上文件分配和报告连续性；运行时加载器沿 FAT 链读取，不要求背景文件本身物理连续。

### 5.3 FPGA 运行时

1. 启动时解析 INDEX v3，校验 sidecar 描述符；背景 loader 将三张小图一次性预载到 SDRAM 中预留区域，验证 header/CRC 后置 `bg_ready`。载入失败时该 slot 标记无效并使用当前有效图或纯色背景，不阻塞音频初始化。
2. 浏览选曲时，焦点曲目 ID 变化后文字 loader 从 `TEXT.BIN` 读取该曲目段，将歌名、歌手、字形和时间/视觉行表写入可写双口 RAM，选曲行只显示与当前焦点 ID 匹配且已就绪的元数据。确认播放时若该曲目尚未就绪，先等待加载完成；曲目段容量由第 5.2 节的硬上限约束。播放期间不为歌词发起 TF 请求，避免和 MV/PCM 抢 1-bit SPI。
3. 文本显示采用片段预取和帧边界提交：片段只从已加载的 `TEXT.BIN` 活动曲目 RAM 取出，不触发 TF 读取；在显示窗口外完成当前歌词窗口填充，切歌/加载错误时保留旧有效画面或显示占位，不把旧曲目内容标记为新焦点就绪；不会在有效视频行中改写正在显示的行。
4. 背景显示使用现有 640×480 坐标域，以最近邻 4×水平/垂直放大 160×120 图像。小型源行缓存将每个源像素复用到 4×4 屏幕像素，避免每个 HDMI 像素都重新访问 SDRAM。背景层在当前 MV/封面区域和歌词/文本下面；现有 320×240 MV/封面区域与上层波形/OSD 优先级保持。
5. KEY6 作为短按事件，只在播放页消费。每次去抖后的按下沿只切换一次；持续按住不重复切换，释放后再次按下才可切下一张。有效背景索引加一并对 3 取模；新索引在下一帧起点提交，播放时钟、歌词时间与 MV 不变。不做自动循环计时、不记入持久化设置。
6. 所有 sidecar 读取只发生在初始化或曲目装载；播放期间 MV/PCM 连续流优先。SD 错误设置可观察的资源/装载错误状态，避免等待状态机永久阻塞。

### 5.4 界面排版细节

- 选曲底部信息行只使用已经确定的内容：序号、歌名、歌手和时长；`songs.json` 为歌名/歌手的单一来源。空间不足时优先保留序号和时长，歌名/歌手按字形边界缩短并使用省略号，不覆盖相邻控件。选曲时长按 `MM:SS` 显示。
- 变宽字使用 advance 表：普通 ASCII 英文字母/数字默认 8 px，可由工具按字符窄体类别输出 7–9 px；中文/全角 16 px；普通空格和全角空格均 5 px。字形仍使用现有 16×16 画布，advance 只控制下一个字形起点；播放时左侧已播放时间用 `MM:SS`、右侧剩余时间用 `-MM:SS`，均使用紧凑数字 advance，不额外插入字符间距。
- 进度计算目标为 `fill = floor(320 × elapsed / total)`，elapsed 先 clamp 到 total；起始 0，`elapsed >= total` 强制 320。端点宽度采用 9 bit，避免现有 8-bit/240 上限。填充轨道的未播放部分透明，进度条不绘制外框/黑底。
- 歌词区无面板背景、无边框；仅画歌词字形并使用已有激活/非激活颜色。基础播放背景替代目前的纯色 `BG_COLOR`。

## 6. 资源预算与门禁

- 背景卡数据固定为 115,200 bytes。若 SDRAM 以 32-bit word 装两个 RGB565 像素，净载荷约 28,800 words；若现有读路径每像素占一个 32-bit word，保守上限约 57,600 words。需在实现前对照当前 SDRAM 地址分区确认，不与 MV/封面 bank 重叠。旧实施文档估计约 637,952 个空闲 SDRAM word；该数字是旧快照，应在当前 HEAD 上复核后才可分配。
- 动态文字最大逻辑载荷约为：点阵加 advance `192×(16×16+8) = 50,688 bits`、glyph 引用 `4,096×8 = 32,768 bits`、时间戳/组表 `128×44 = 5,632 bits`、视觉行偏移 `256×13 = 3,328 bits`，合计约 92,416 bits（约 11 个 9-Kbit block 的理论容量，尚未计入器件 RAM 宽深映射造成的损耗）。4,096 个 glyph 引用额度包含歌名、歌手和歌词文本；标题/歌手没有额外引用表。此活动曲目 RAM 替换静态 ROM，而不是与其并存；目标净增不超过 5 个 BRAM9K，超过即先压缩/重构数据布局，不继续叠加功能。实际 BRAM 数以 TD 综合/route 报告为准。
- 当前 native route 的 PLB 空余很少；BRAM9K 约使用 47/64。动态字体 RAM 替代静态字库/文字 ROM，不并存复制；新缓存应有显式 BRAM 上限。任何新增逻辑逐阶段 native route，若 PLB 超器件容量、Setup/Hold 失败或发生功能回退，则暂停后续功能并先减逻辑/复核架构。
- 长整曲 MV/PCM 需要持续 1-bit SPI 读。10 fps RGB565 视频为 1,536,000 B/s，PCM 为 96,000 B/s，合计约 1.632 MB/s（未计协议/空闲开销）。约 4 分钟的一首 MV 裸数据约 368.64 MB；四首约 1.475 GB，另加 PCM 约 92 MB、封面与文件系统开销。打包 dry-run 必须报告总卡镜像大小、目标卷容量和剩余空间，并在超容量时失败。实施前以 30 秒、3 分钟、全长分级验证连续播放和最差跨簇场景；带宽不足时先量测 8 fps 等降级方案，不凭估算签收 10 fps。
- 背景 preload 在播放开始前完成；文字按选曲预载；两者不占播放期 SPI 带宽。SDRAM MV 帧、音频扇区和显示刷新之间的仲裁仍需实测。

## 7. 错误行为

| 条件 | 行为 |
|---|---|
| INDEX v1/v2 | 保留既有媒体播放；缺失的动态文字/背景采用明确占位/纯色 |
| INDEX v3 描述符或 sidecar 损坏 | 设置可诊断错误；不使用越界 cluster/offset；无效背景 slot 不切入；歌词回退占位 |
| LRC 编码/时间戳/资源容量错误 | PC 打包失败并报告文件、行号和原因，不生成可刷卡最终镜像 |
| 音频读取失败 | 既有媒体错误路径终止本曲，不让 MV 无限运行 |
| MV 短于音频 | 重复最后一帧填到目标帧数；音频 EOF 后结束播放画面 |
| MV 长于音频 | PC 端裁切至目标帧数；即便残留帧，运行时仍以音频 EOF 为准 |
| 背景图读取失败 | 纯色/最后一个有效背景兜底，仍可继续音频播放 |
| 按 KEY6 时背景尚未 ready | 忽略切换请求，不阻塞按键和播放 |

## 8. 分阶段验收

### 阶段 A：现有页面微调

- 选曲信息行字段、位置和时长可读；中英文混排按度量表累计 advance。
- 进度条 x `[16,336)`；验证零点、中点、最后一帧三种填充值分别为 0、约 160、320 px。
- 歌词/进度不出现边框或黑色矩形底；`MM:SS` 紧凑且不溢出。

### 阶段 B：动态文字与 LRC

- 修改 `songs.json` 的标题/歌手/LRC 后，只替换 TF 资源即可更新显示，同一 bitstream 能显示新内容。
- 四首各自标题、歌手、UTF-8 LRC、高亮、滚动、长句换行正确；英文在词边界优先换行，长词才按字形拆开；一组多段歌词保持同一时间戳/高亮。
- 缺失和损坏文件可恢复，不串用上一首的文本，不在播放中访问 SD 装载文字。

### 阶段 C：三张背景

- PC 输出恰为三份 160×120 RGB565LE payload，大小/字节序/hash 与预览一致；居中裁切后主体位置可接受，模糊强度按实体屏视觉确认。
- FPGA 背景边缘铺满 640×480、横纵各 4×，无拉伸比例错误/撕裂；MV/封面、歌词和波形层级正确。
- 播放时 KEY6 每次去抖后的按下沿按 0→1→2→0 切换一次；保持按下不重复，释放后再次按下才切下一张；停止播放无自动切换。

### 阶段 D：四首素材与整机终验

- 四首 PCM、封面、MV、LRC、歌名/歌手在 manifest 和打包报告中一一对应，文件 hash/大小独立记录；无共享示例 PCM 的隐性映射。
- 四首分别完成启动/选曲/播放/暂停/Seek/切歌/EOF；MV 与音频错时按离线规则补齐/裁切；四首全长验证无音频欠载、MV 花屏或 FAT 读死锁。
- 完成最新 HEAD 对应的 native `area_prior → seed 5 place → route → fix_hold → final`；记录 route 版器件资源、Setup/Hold WNS/TNS/失败端点；生成 bitstream/hash 后做板上冷启动和人工验收。

## 9. 主要风险与应对

1. **PLB 路由余量不足**：先落地低成本几何改动；动态字库替换静态 ROM，不叠加一套同尺寸存储；每阶段完整 route，失败即暂停后续。
2. **SPI 长时吞吐不够**：先做持续播放分级试验；必要时降低 MV 帧率，并由打包器重新计算帧数/文件大小。
3. **可变字宽的像素时序路径变长**：PC 端输出 advance/换行元数据，RTL 避免每像素解析 UTF-8；如果组合选字路径拉长，考虑按行预计算 glyph 起点/行缓存，先做 gate 和 route 测量。
4. **四首歌词超过容量**：192 唯一字形/128 时间行作为初始硬上限；实际四首素材应先由打包器 dry-run，若触发则调整压缩/容量并重新评估 BRAM，不静默截断。
5. **INDEX 兼容和目录槽位**：v3 不改变 64-byte entries；保留 v1/v2 媒体路径；工具保证 INDEX/TEXT/BG + 12 个媒体文件落入可扫描目录范围。
6. **显示/加载跨时钟域**：数据总线用稳定握手/双口 RAM，状态采用同步或事件桥，所有可见内容在帧边界提交，不新增裸多位 CDC。

## 10. 实施顺序

1. 固定当前 HEAD 的综合/完整 native route 和四首源素材的工具 dry-run；先暴露 PLB/BRAM/SD 带宽真实余量。
2. 单独做页面几何/文字度量的低资源改动并 route。
3. 新增离线打包输出与 PC 自检，再扩 INDEX v3 和运行时文字 loader；先单曲资源加载与仿真，再四曲。
4. 新增 BG.BIN 生成/验证和 SDRAM preload/4×显示，再接 KEY6 帧同步切换。
5. 完成四首独立全长素材转换，跑长时 SD 带宽/端到端测试和整机签核。

每一阶段都可独立回归或回退；不能因为 opt_gate 或 gate WNS 好看就跳过完整 native place/route。代码、工具和卡格式的详细文件级任务在配套实施计划中列出；此设计通过用户审阅后才进入实现。
